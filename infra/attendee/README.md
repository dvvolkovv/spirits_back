# Attendee — мост в встречи Google Meet

Attendee держит в встрече Chrome-бота и обменивается с нами звуком по
вебсокету. Через него ассистент попадает в площадки без LiveKit.

Живёт на **отдельном хосте**. Не на проде: каждый бот — полный Chrome со
страницей Meet, а на `212.113.106.202` уже API, Postgres, Redis, Neo4j и
LiveKit; конкуренция за CPU ударит по SFU.

## ⚠️ Читать первым: Celery-режим не годится для продакшена

Дословно из README проекта (проверено 07.09.2026):

> By default, Attendee launches bots as Celery tasks. This mode is convenient
> for local development and testing, **but it is not suitable for production**
> for two reasons.
>
> The correct way to run Attendee in production is with Kubernetes, where each
> bot runs in its own isolated pod. Enable this by setting the environment
> variable: `LAUNCH_BOT_METHOD="kubernetes"`
>
> **Our paid self-hosting plan** includes official directions and support for
> running Attendee with Kubernetes.

Две причины непригодности:

1. **Перетекание звука.** Несколько ботов в одном Celery-контейнере делят
   аудиоустройства, и звук разных встреч может смешаться. В переговорах с
   клиентами это неприемлемо — не «шум», а утечка одной встречи в другую.
2. **Рестарт убивает живых ботов.** Деплой или перезапуск контейнера
   выбрасывает бота из идущей встречи.

Kubernetes мы не держим, а официальные инструкции к нему — в платном плане.
Поэтому решение на v1 (см. ниже) — **жёсткий потолок в одну одновременную
встречу**: при одном боте перетекать нечему.

Потолок держится с нашей стороны, а не надеждой:

- диапазон портов в `voice-host/.env` сужается до одного:
  `ATTENDEE_WS_PORT_MIN=8140`, `ATTENDEE_WS_PORT_MAX=8140`. Второе
  одновременное задание не найдёт свободного порта и честно откажет;
- та же регулярка в `nginx-attendee.conf` сужается до `8140`;
- на бэкенде стоит явная проверка: `MeetingService.join()` считает встречи
  Meet в эфире **до** создания записи звонка и отвечает `409` с
  `reason: 'meet_busy'`. Без неё второй пользователь получал бы невнятный
  отказ через несколько секунд — когда воркер не найдёт свободного порта.

Потолок задан константой `MEET_CONCURRENCY_LIMIT`, а не жёсткой единицей.
**Поднимать её можно только вместе с переходом на изоляцию ботов по поду и
одновременно с диапазоном портов.** Иначе потолок снимется, а утечка звука
между переговорами разных клиентов появится — тихо.

Когда одной встречи станет мало — либо платный план и Kubernetes, либо по
хосту Attendee на встречу. Это решение владельца, не техническое.

## Деплой во время живой встречи: окно короче встречи

`deploy.sh` перед выкаткой ждёт, пока опустеет эфир (`wait_for_calls_drain`),
и встречу Meet он **видит**: ручка `/webhook/voice-call-status/active` считает
все `voice_calls` со статусами `dialing`/`active`, без фильтра по провайдеру.

Но ждёт он не бесконечно. `CALL_DRAIN_SECONDS` по умолчанию **900 секунд**, и
после них скрипт печатает предупреждение и **идёт дальше**. Окно выбиралось под
звонки один-на-один — в комментарии там так и написано, «наш собственный потолок
звонка — час». У встречи потолок **два часа** (`HARD_CAP_MS` в
`voice-host/src/occupancy.ts`), а реапер добивает её через 130 минут.

Значит деплой на шестнадцатой минуте перезапустит воркер и выбросит бота из
идущей встречи. Это не специфика Meet: то же верно для своих комнат и Taler ID,
просто там оно до сих пор не всплывало.

Что с этим делать, пока встречи редки:

- перед выкаткой смотреть глазами:
  `SELECT id, provider, started_at FROM voice_calls WHERE status IN ('dialing','active')`;
- если встреча идёт и выкатка не пожарная — подождать;
- если ждать нельзя, поднять окно на этот запуск:
  `CALL_DRAIN_SECONDS=7200 bash scripts/deploy.sh`.

Поднимать дефолт до двух часов **не стали**: это заблокировало бы любую
выкатку на всё время чужой встречи, включая срочные фиксы. Решение про
постоянное окно — за владельцем, когда встречи перестанут быть редкостью.

## Сквозной прогон на стенде 09.09.2026: цепочка держится

Attendee поднят на тестовой ноде, стенд переведён на ветку `feat/meeting-meet`.
Прогон с **несуществующим** кодом встречи — чтобы проверить весь путь, кроме
собственно звука:

```
статус=failed  бот=bot_ImG1uiz1u9UYMNBl  причина=Звонок не состоялся: бот Attendee: fatal_error
[attendee] жду звук на :8140, callId=03c3aad7-…
[meet] бот в состоянии fatal_error до подключения звука — выходим
```

Подтверждено на живой системе: вход с `provider=meet`, диспатч в комнату,
занятие порта воркером, вызов подписанной ручки `meet-bot`, создание бота
через API Attendee, приём им наших адресов по TLS, реальная попытка входа
(события бота `join_requested` → `could_not_join_meeting`), доставка вебхука,
**проверка подписи**, передача события в комнату по дата-каналу, выход воркера
с настоящей причиной и запись отказа в `voice_calls`.

**Проверка подписи подтверждена не тестом, а трафиком:** Attendee записал
четыре попытки доставки, и у всех проставлен `succeeded_at` — что невозможно,
если бы ручка отвечала 401.

Звук в обе стороны на этом прогоне не проверялся: для этого нужна живая
встреча и человек, который впустит бота. Проверен отдельно — ниже.

### Четыре дефекта, которые нашёл только запуск

Все четыре были невидимы для 1398 тестов бэкенда и 111 тестов воркера.

| Дефект | Чем был опасен | Почему тесты молчали |
|---|---|---|
| Ключ подписи брался как base64-**текст**, а не его байты | Ни один вебхук не прошёл бы проверку. Присутствие не приходило бы вовсе, гейт по имени срывался бы в solo, ассистент отвечал на каждую реплику | Золотой вектор использовал секрет-строку с обеих сторон: он проверял канонизацию, а не обращение с ключом |
| Контроллер входа не передавал провайдера `meet` | Фича недостижима через API: встреча уходила искать свою комнату и получала 404 | Все тесты зовут `MeetingService` напрямую, минуя контроллер |
| `attachBot` не убирал бота при отказе после его создания | Chrome остаётся в переговорах клиента навсегда: `external_bot_id` пуст, реапер такого не найдёт | Ловушка была закрыта в `join()`, а `attachBot` — отдельный метод. Сценарий **произошёл вживую**, когда миграция ещё не была накатана |
| Обработчик `DataReceived` регистрируется ПОСЛЕ ожидания звука | Провал входа бота виден только через двухминутный таймаут и под чужой причиной («звук не подключился») | Порядок регистрации обработчиков в юнит-тесте не воспроизводится |

### Что ещё выяснилось

- **Attendee требует TLS на обоих обратных каналах** и проверяет валидатором:
  `webhooks: does not match '^https://.*'`, `websocket_settings.audio.url:
  URL must start with wss://`. Прод-схема с nginx — не удобство, а
  единственно возможная форма.
- **Секрет вебхука двоичный.** Интерфейс отдаёт его в base64, подписывает
  Attendee декодированными байтами.
- **Состояния бота**: реальный набор в `bots/models.py`, `BotStates`. Комната
  ожидания — `waiting_room`, и она НЕ отказ. Состояний `denied_entry` и
  `removed_from_meeting`, которые были в нашем коде, у Attendee не существует.
- **Запись по умолчанию — mp4 в S3.** Отключается `recording_settings:
  {format: 'none'}`, что и сделано: транскрипт мы ведём сами, а видео
  переговоров клиента в чужом хранилище — лишняя утечка.
- **Миграции на стенд надо накатывать руками** (`psql -f`), общий
  `npm run migrate` застревает на `base/001`. Забытая миграция и вскрыла
  третий дефект из таблицы выше.

## Живая встреча 09.09.2026: звук прошёл, встреча оборвалась на 95-й секунде

Владелец создал встречу, кинул ссылку в чат, впустил бота из комнаты ожидания.

Что подтвердилось:

- бот вошёл под именем «Роман · ассистент Дмитрия», состояния
  `joining` → `joined_recording` приехали вебхуками;
- звук ОТ встречи дошёл: **9244 куска** за ~185 секунд, ровно тем ритмом,
  который держит микшер;
- Роман говорил: сегмент **12,0 с** ушёл в вебсокет;
  ⚠️ **«слышен во встрече» здесь было моей догадкой, а не проверкой.** Владелец
  этого не подтверждал, а третий прогон 09.09.2026 показал обратное: звук от
  нас доходит до Attendee, но во встрече его не слышно — микрофон бота остаётся
  выключенным (см. раздел про обязательную локальную правку выше);
- транскрипт, резюме и списание — как на своих встречах, отдельного кода не
  потребовалось;
- бот убран из встречи по выходу, Chrome не остался висеть.

И три дефекта, которых не показал ни один прогон на стенде.

| Дефект | Как выглядел во встрече | Почему тесты молчали |
|---|---|---|
| События состава уезжали в пустоту: обработчик `meet_*` стоял ПОСЛЕ ожидания звука, а оно длится до двух минут | `[гейт] участников: 0 → строгий гейт` — Роман весь разговор считал, что во встрече никого. `meetingFirstHuman` не дёрнулся: звонок остался `dialing` и запер владельцу следующий вход до реапера (130 минут) | Порядок регистрации обработчиков в юнит-тесте не воспроизводится. Тот же класс дефекта, что четвёртый в таблице выше — исправление там было половинным: гонку с провалом входа закрыло, состав нет |
| Хаб отдавал соединение наружу ровно один раз, поэтому переподключение Attendee получало отказ | Вебсокет оборвался на 95-й секунде, Attendee постучался снова через мгновение — `[attendee] соединение не для нас` — и встреча кончилась на середине разговора | Тест проверял «дождались соединения», а второго соединения в нём не было вовсе |
| После обрыва задание не уходило из комнаты | Тикало тишиной **ещё четырнадцать минут**, держа единственный порт под Meet, и вышло только по вердикту `never_started`. С исправленным составом вердикт был бы `stay` — и задание висело бы до двухчасового потолка | `session.close()` в тестах выглядит как конец работы; в задании @livekit/agents конец — это `room.disconnect()` |

Исправлено в `fix(voice-host): встреча Meet переживает обрыв звука и не теряет
состав`: обработчик `meet_*` теперь один и регистрируется сразу после
`ctx.connect()`; сокетом владеет хаб, и вход с выходом сессии работают через
него, не замечая переподключений; наружу выходит только «бот не вернулся за
полторы минуты», и эта ветка, как и терминальное состояние бота, разъединяет
комнату. Добавлены тесты на переподключение, на потерю по истечении окна и на
подписку поверх уже случившейся потери.

**Причина самого обрыва на 95-й секунде не установлена.** `proxy_read_timeout`
у nginx — 7200 с, звук в этот момент шёл непрерывно. Как страховка от таймаута
по бездействию добавлен пинг раз в 30 секунд: звук ОТ Attendee идёт всё время,
а наш конец молчит, пока ассистент не говорит. Если обрыв повторится — смотреть
логи `attendee-worker` в момент разрыва, там ведётся его сторона вебсокета.

### Второй прогон 09.09.2026: что показал разбор

Вход запускался дважды, и оба раза бота никто не впустил — но именно это
объяснило обрыв из первого прогона и вскрыло ещё три дефекта.

**Обрыв на 95-й секунде был не сетевым.** В логе `attendee-worker` видно
всё: в 15:32:13 Meet отдал хозяина встречи со `status: 8`, Attendee счёл это
уходом (`only_one_participant_in_meeting_at set to …`), а через 60 секунд
одиночества сам нажал «выйти» — `Auto-leaving meeting because there was only
one participant in the meeting for 60 seconds`,
`AUTO_LEAVE_ONLY_PARTICIPANT_IN_MEETING`. Мы видели только закрывшийся
вебсокет. Дефолты автовыхода Attendee (`bots/automatic_leave_configuration.py`)
строже наших правил из `voice-host/src/occupancy.ts` и потому решали за нас,
поэтому теперь бот создаётся с явными `automatic_leave_settings`: одиночество
300 с вместо 60, тишина 1800 с вместо 600, потолок аптайма 7500 с — чуть выше
нашего двухчасового `HARD_CAP_MS`, чтобы причину называли мы, но Chrome не мог
пережить воркер.

| Дефект второго прогона | Как выглядел | Исправление |
|---|---|---|

Читалось как «состояние неизвестно», и реапер перебирал четыре мёртвых бота каждые 5 минут, не очищая `external_bot_id` никогда | На 400 спрашиваем состояние и убираем запись только на терминальном; на `joining` и в комнате ожидания по-прежнему `null` — такой бот ещё может войти. Настоящая причина лежала в вебхуке: `event_type: could_not_join_meeting`, `event_sub_type: request_to_join_denied` | Код едет по дата-каналу полем `sub`, воркер переводит его в человеческую строку («во встречу так и не впустили») и оставляет код в скобках. Ранние исправления при этом подтвердились работой: второй бот получил

причиной, — прежняя редакция досидела бы всё окно ожидания и сообщила бы

`UiRequestToJoinDeniedException` → `fatal_error` с подтипом

## ⚠️ Обязательная локальная правка: микрофон бота в Google Meet

**Без неё ассистента во встрече не слышно вовсе.** Правка —
`patches/mic-label-tolerant.py`, применять после каждого обновления Attendee:

```bash
python3 patches/mic-label-tolerant.py ~/attendee
cd ~/attendee && docker compose -f dev.docker-compose.yaml restart attendee-worker-local
```

Что происходит без неё. Наш звук доходит до Attendee и проигрывается в
виртуальный микрофон страницы — это видно в логе воркера
(`RealtimeAudioOutputManager: Audio thread started`, а «Audio thread exited»
ровно через длину реплики). Но `playPCMAudio()` перед проигрыванием зовёт
`ensureMicOn()`, а тот ищет кнопку строгим совпадением:

```js
document.querySelector('button[aria-label="Turn on microphone"]')
```

На экране перед входом такая подпись есть — поэтому питонья часть Attendee
кнопку находит и глушит микрофон перед входом. **В самой встрече** Meet
добавляет к подписи горячую клавишу («Turn on microphone (ctrl + d)»), и
селектор не находит ничего: микрофон бота остаётся выключенным, участники
слышат тишину. Правка ищет кнопку терпимо — по началу `aria-label`, по началу
`data-tooltip` и по `data-is-muted`, который Meet держит прямо на кнопке
микрофона и который не зависит ни от языка интерфейса, ни от того, что Meet
дописал к подписи.

Правка живёт в нашем репозитории, а не в форке: форк Attendee — это второй
источник правды и обязанность его вести. Как только апстрим исправит поиск
кнопки, скрипт нужно удалить.

## Установка

Опубликованного образа **нет** — собирается из исходников. Postgres и Redis
Attendee поднимает своим compose, наши трогать не нужно.

```bash
git clone https://github.com/attendee-labs/attendee.git
cd attendee
# Зафиксировать коммит: Attendee ходит по живой вёрстке Meet, и обновление
# «когда-нибудь потом» ломает встречу в неожиданный момент.
git log --oneline -1   # записать sha сюда, в этот файл

docker compose -f dev.docker-compose.yaml build          # ~5 минут

# Сгенерировать .env
docker compose -f dev.docker-compose.yaml run --rm attendee-app-local \
  python init_env.py > .env

# Дописать в .env хранилище записей и продовые настройки (см. ниже)
$EDITOR .env

docker compose -f dev.docker-compose.yaml up -d
docker compose -f dev.docker-compose.yaml exec attendee-app-local \
  python manage.py migrate
```

Дальше через UI на `:8000`: создать аккаунт (письмо подтверждения приходит **в
логи контейнера**, не на почту), войти, в разделе «API Keys» выпустить ключ.

### Что дописать в `.env` Attendee

`init_env.py` генерирует основное. Руками добавляются:

- **Хранилище записей** — в инструкции это AWS S3. Записи нам не нужны, но
  переменные требуются. Подставить наш MinIO (он уже есть на проде и в
  `docker-compose.minio.yml`), а не заводить AWS: лишний платный аккаунт ради
  функции, которой мы не пользуемся.
- Оставить `LAUNCH_BOT_METHOD` пустым (Celery-режим) — осознанно, см. шапку.

### Что дописать в наш `.env`

Бэкенд (`~/spirits_back/.env`):

```env
ATTENDEE_BASE_URL=https://<хост attendee>
ATTENDEE_API_KEY=<из UI>
ATTENDEE_WEBHOOK_SECRET=<из UI, раздел вебхуков>
ATTENDEE_WEBHOOK_URL=https://my.linkeon.io/webhook/meet/attendee
```

Воркер (`~/spirits_back/voice-host/.env`):

```env
ATTENDEE_WS_PORT_MIN=8140
ATTENDEE_WS_PORT_MAX=8140
ATTENDEE_WS_PUBLIC_BASE=wss://my.linkeon.io
```

`ATTENDEE_AUDIO_WS_URL` не нужен: адрес вебсокета собирает воркер сам — порт
свой у каждого задания.

### Nginx на проде

Положить `nginx-attendee.conf` в конфиг сайта `my.linkeon.io`, заменив
`ATTENDEE_HOST_IP` на адрес хоста Attendee. Диапазон в регулярке обязан
совпадать с `ATTENDEE_WS_PORT_MIN/MAX`.

## Проверка

```bash
# API отвечает
curl -s -o /dev/null -w '%{http_code}\n' https://<хост attendee>/

# Ключ рабочий
curl -s https://<хост attendee>/api/v1/bots \
  -H "Authorization: Token $ATTENDEE_API_KEY" | head -c 200

# Наш вебсокет достижим снаружи через nginx (ожидается 400/426, не 502:
# это значит, что nginx дошёл до порта, а там нет апгрейда)
curl -s -o /dev/null -w '%{http_code}\n' https://my.linkeon.io/attendee/8140
```

## Обновление

Attendee ходит по живой вёрстке Google Meet, поэтому обновляться придётся —
но осознанно, а не по `latest`:

1. Проверить активные встречи: `SELECT count(*) FROM voice_calls WHERE
   provider='meet' AND status IN ('dialing','active')`.
2. `git fetch && git checkout <новый sha>`, пересобрать, накатить миграции.
3. Провести живую встречу до того, как объявить обновление успешным: сборка и
   миграции не проверяют, что бот всё ещё умеет входить в Meet.
4. Записать новый sha в этот файл.
