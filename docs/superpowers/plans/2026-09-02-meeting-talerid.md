# План: ассистент во встрече Taler ID

**Спека:** `../specs/2026-08-27-meeting-bridge-talerid-design.md`, раздел
«Возобновление 02.09.2026».

**Суть:** всё поведение встречи уже написано и обкатано на своих комнатах.
Остаётся подключить вход и выход голосовой сессии к чужой комнате по публичному
токену. Отдельный процесс-мост, заложенный в исходном дизайне, не нужен.

**Предыдущий план** (`2026-08-27-meeting-bridge-talerid.md`) отменён вместе с
мостом; задачи по гейту, микшеру и промптам из него выполнены в рамках своих
комнат.

---

## Задача 1. Клиент комнат Taler ID

`src/meeting/talerid-room.client.ts`

- `info(code)` → `{ code, title, roomName, isActive, requiresPassword, creatorName }`
  или `null` на 404.
- `join(code, displayName)` → `{ token, roomName }` или `null` на 404.
- База — `TALERID_BASE_URL` (на проде уже `https://api.talerid.io`), путь
  `/api/voice/rooms/public/{code}` и `/join`.
- Адрес LiveKit собирается из той же базы: хост базы + `/livekit/`. Не хардкодить
  `api.talerid.io` — на стейдже хост другой.
- Таймаут короткий: ручка чужая, висеть на ней в обработчике чата нельзя.

**Проверки:** 404 → `null`, а не исключение; `requiresPassword: true` отдаётся
наверх как есть (решение о поддержке — на вызывающем); битый JSON не роняет.

## Задача 2. Ссылка Taler ID в чате → карточка

`src/meeting/meeting-link.ts` — рядом с существующим разбором ссылок Linkeon.

- Регулярка на `https://api.talerid.io/room/{код}` и на их edge-домены.
- Точка перед доменом обязательна, как и в разборе ссылок Linkeon: иначе
  `notapi.talerid.io` пройдёт проверку.
- Код у них — hex-строка, не наш алфавит без похожих букв. Отдельная валидация.

**Проверки:** чужой домен с похожим именем не проходит; ссылка внутри длинного
текста находится; код регистронезависим.

## Задача 3. Вход во встречу с провайдером

`src/meeting/meeting.service.ts`, `meeting.controller.ts`

- `join()` принимает провайдера. Для `talerid`: сходить в клиент за токеном,
  положить `provider = 'talerid'`, `external_room = <код>`, токен и адрес
  LiveKit — в metadata диспатча.
- Наша комната создаётся пустой, только ради job: жизненный цикл, учёт и reaper
  завязаны на `voice_calls` и на disconnect из неё.
- `requiresPassword: true` → внятный отказ пользователю, а не 500.
- Комната неактивна (`isActive: false`) → отказ с объяснением.

**Проверки:** токен не утекает в ответ фронту; при отказе Taler ID запись не
остаётся в `dialing` (та же ловушка, что уже ловилась в своих комнатах).

## Задача 4. Выход сессии в чужую комнату

`voice-host/src/external-room-output.ts`

- `class ExternalRoomAudioOutput extends voice.AudioOutput`.
- Владеет `AudioSource` и `LocalAudioTrack`, публикует его в переданную комнату.
- `captureFrame(frame)` → `source.captureFrame(frame)`.
- Частота и число каналов — как у сессии; при расхождении не молчать, а
  логировать: немой ассистент диагностируется часами, о чём есть запись в спеке
  своих комнат.

**Проверки:** кадры доходят до источника; закрытие снимает публикацию.

## Задача 5. Воркер работает в чужой комнате

`voice-host/src/agent.ts`

- Метаданные с `provider: 'talerid'`, `externalUrl`, `externalToken` → подключить
  вторую `Room`.
- `session.input.audio = new MixedRoomAudioInput(externalRoom)` — класс уже
  принимает любую комнату, правок не требует.
- `session.output.audio = new ExternalRoomAudioOutput(externalRoom)`.
- **Оба — до `session.start()`.** Порядок уже стоил дня отладки на своих
  комнатах: `input.audio is already set, ignoring`.
- Имя участника в их списке — `<Ассистент> · ассистент <Владелец>`, как у нас.
- `occupancy` считает участников ИХ комнаты.
- Обрыв их комнаты = конец встречи: `complete` с транскриптом.

**Проверки:** без `provider` в метаданных поведение прежнее (свои комнаты и
звонки не задеты).

## Задача 6. Фронт

- Карточка `{{meeting_join}}` учитывает провайдера: показать, что встреча в
  Taler ID, и чья она (`creatorName`).
- Строки — через `t()`, семь локалей.

## Задача 7. Живая проверка

Во встрече Taler ID с владельцем: представился, молчит без обращения,
откликается по имени, режим слушателя, документ уходит нужному специалисту,
транскрипт и резюме на месте.

---

## Порядок

1 → 2 → 3 дают бэкенд, который умеет добыть токен. 4 → 5 дают воркера, который
умеет им воспользоваться. 6 — витрина. 7 — единственная проверка, которая
что-то доказывает.

Задачи 4 и 5 — риск: их можно проверить только живой встречей, юнит-тесты тут
доказывают мало. Поэтому они идут после того, как бэкенд научится отдавать
токен, и проверяются сразу, а не в конце.
