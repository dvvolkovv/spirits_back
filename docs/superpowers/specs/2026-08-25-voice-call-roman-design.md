# Голосовой звонок ассистенту (Роман) — дизайн

**Дата:** 2026-08-25
**Статус:** утверждён, готов к планированию реализации
**Источник:** встреча команды 24.08.2026 (Сергей, Дмитрий, Владимир), запись
`api.talerid.io/meeting/caa29d32-f925-43ae-9d73-98ef88ba1b5c`

## Задача

Дать пользователю возможность **позвонить ассистенту голосом** из интерфейса Linkeon и
разговаривать с ним в реальном времени. Ведущий разговора — существующий ассистент
**Роман** (`category: assistant`, «Помогаю делать всё, что не могут другие»). Роман
держит беседу сам, а профильные вопросы **асинхронно** переадресует специалистам
(Алексей — юрист, Анна — бухгалтер, Виталий — финдир, Андрей — бизнес, Александра —
маркетинг), продолжая говорить, пока те думают, и озвучивая ответ по готовности.

Формулировка из встречи: «быстрый и тупой дёргает умных» — так же устроен ассистент
Taler ID.

### Чего эта спека НЕ покрывает

Идея с встречи распадается на пять независимых подсистем. Здесь — только **A + B**:

| | Подсистема | Статус |
|---|---|---|
| **A** | Асинхронный мост «ведущий → специалисты» | **в этой спеке** |
| **B** | Звонок ассистенту из веб-интерфейса Linkeon | **в этой спеке** |
| C | Мост в чужие конференции (Zoom / Google Meet / Яндекс Телемост / Taler ID) | отдельная спека |
| D | Телефония, звонки на обычный номер | отдельная спека |
| E | Видео-аватары, липсинк, мимика | трек Сергея, отдельный сервис |

C и D переиспользуют всё, что строится здесь: те же комнаты LiveKit, тот же воркер, тот
же асинхронный мост. E независим.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Кому звонит пользователь | одному ведущему (Роман), специалисты за MCP | схема из встречи, один голос и один промпт, вся сложность в одном слое |
| Транспорт | LiveKit-комната, WebRTC | jitter buffer и потери; TCP-релей разваливается на мобильном интернете; прямая дорога к C и D |
| Мозг | OpenAI Realtime через `@livekit/agents-plugin-openai` | латентность 300–800 мс против 1.5–2.5 с у связки SpeechKit STT → Claude → SpeechKit TTS |
| Язык воркера | TypeScript (`@livekit/agents`) | тот же репозиторий, тот же `deploy.sh`, тот же pm2 |
| Где живёт воркер | прод `212.113.106.202`, рядом с API | Вена, OpenAI доступен; отдельный VPS не нужен |
| Тулы у Романа | свои function-тулы воркера, **не** remote MCP | remote-MCP исполняет OpenAI и синхронно ждёт HTTP-ответ — Opus туда не влезает |
| Связь звонка и чата | общая память, в ленту — карточка | сырой транскрипт не засоряет историю и не жрёт контекст следующих ходов |
| Аудитория v1 | только `isAdmin` | мерим латентность и цену минуты на живых разговорах до открытия |
| Биллинг v1 | считаем, не списываем | цена минуты неизвестна, тариф назначать не из чего |

### Почему не remote MCP, хотя Realtime это умеет

Realtime API принимает `server_url` в `session.update` и **исполняет MCP-тул на своей
стороне** — именно это на встрече названо основной фишкой. Но раз исполняет он, то он же
и ждёт HTTP-ответ. Окно ненастраиваемое, порядка минуты; Opus, думающий над вопросом
юриста 90 секунд, в него не помещается, и разговор просто повисает в тишине.

Поэтому `ask_specialist` — обычный function-тул, который исполняет **наш** воркер:
возвращает управление модели мгновенно, а ответ доставляется отдельным каналом. Ровно
то поведение, которое описал Владимир: «отправил Алексею, пока расскажу, что вижу сам».

## Архитектура

Пять компонентов, у каждого одна задача.

### 1. `linkeon-voice-host` — воркер

Отдельный процесс на `@livekit/agents` + `@livekit/agents-plugin-openai`, живёт в
`spirits_back` (каталог `voice-host/`), запускается pm2 как `linkeon-voice-host`.
`agent_name` — `linkeon-voice-host`, отдельный от `outbound-call-agent`.

Умеет ровно три вещи: получить инструкции из `metadata` диспатча, объявить function-тулы,
ходить в бэкенд по HTTP. Промпт Романа приезжает в metadata, а не зашит в код.

### 2. `VoiceCallModule` — владелец жизненного цикла

Новый NestJS-модуль, `src/voice-call/`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/webhook/voice-call/start` | проверяет `isAdmin`, создаёт запись, собирает preamble, выпускает токен, диспатчит воркера |
| POST | `/webhook/voice-call/:id/end` | завершение по кнопке |
| GET | `/webhook/voice-call/:id` | статус и карточка |
| POST | `/webhook/voice-call/internal/ask` | ← воркер: вопрос специалисту |
| POST | `/webhook/voice-call/internal/complete` | ← воркер: транскрипт и usage |
| POST | `/webhook/voice-call/internal/failed` | ← воркер: сессия не поднялась |

Все `internal/*` закрыты HMAC-подписью: заголовок `x-voice-signature` =
`HMAC-SHA256(VOICE_CALLBACK_SECRET, raw_request_body)` в hex, сравнение
constant-time. Проверка **обязательна**: если `VOICE_CALLBACK_SECRET` не задан в env,
модуль не поднимается — варианта «секрет пустой → пропускаем» нет.

**Гейт доступа.** `/start` проверяет `isAdmin` на сервере и возвращает `403` для всех
остальных. Скрытая кнопка на фронте — удобство, а не защита.

**Preamble.** Берём последние 20 сообщений из `custom_chat_history` для пары
(пользователь, Роман). Если суммарно больше 4000 символов — сжимаем через Haiku в один
абзац до 1500 символов. Если история пуста — preamble пустой, Роман здоровается как с
новым собеседником.

### 3. `SpecialistJobService` — асинхронный мост

Внутри `VoiceCallModule`. Ядро фичи.

- `/internal/ask` пишет строку в `voice_call_jobs`, кладёт задачу в очередь и
  **немедленно** отдаёт `202 {jobId}`. LLM в хендлере не вызывается ни при каких
  условиях — это инвариант, на него есть тест.
- В фоне вызывает `chat.service.streamUniversalAgent()` от лица специалиста с `userId`
  звонящего. Специалист видит профиль и историю пользователя, а не отвечает в вакууме.
- По готовности — `RoomService.sendData()` в ту же комнату.

Обратный канал через data-сообщения LiveKit, а не через отдельный WS к воркеру: комната
уже есть, авторизация уже есть, и **фронт слушает тот же канал** — плашку «Алексей
думает…» можно рисовать без второго транспорта.

### 4. Фронт

`VoiceCallModal` + хук `useVoiceCall` в `src/components/chat/` (репозиторий
`spirits_front`), зависимость `livekit-client`. Состояние соединения, индикатор
говорящего, плашки думающих специалистов, кнопка сброса. Кнопка «Позвонить» — в шапке
чата Романа, видна только при `isAdmin`.

### 5. Карточка звонка

Одна строка в `custom_chat_history` (`sender_type='ai'`, `agent` = id Романа,
`message_type='text'`), где `content` начинается с `{{voice_call: id=<uuid>}}`, дальше
резюме. Фронт добавляет regex рядом с `AUDIO_CLIP_REGEX` в
`src/utils/customMarkdown.tsx` — механизм отработан на аудиоклипах и SMM-сценариях.
Схема истории чата не меняется.

## Поток данных

```
1. «Позвонить» → POST /webhook/voice-call/start
2. бэк: строка в voice_calls (status=dialing)
        preamble = сжатая история чата с Романом
        AccessToken для браузера
        createDispatch(room, 'linkeon-voice-host', metadata)
3. браузер входит в комнату; воркер уже там → Роман здоровается
4. «спроси юриста, законно ли это»
   → модель зовёт ask_specialist(specialist='Алексей', question='…')
5. воркер → POST /internal/ask → 202 {jobId} за ~50 мс
   → модели возвращается {"status":"asked","specialist":"Алексей"}
   Роман: «Отправил Алексею. Пока расскажу, что вижу сам…»
6. бэк в фоне гоняет Claude
   → sendData(room, {v:1, type:'specialist_answer', jobId, specialist, text})
7. воркер: conversation.item.create + response.create
   Роман: «Алексей ответил: …»
8. трубка → POST /internal/complete {transcript, usage}
   → резюме через Haiku → карточка в custom_chat_history
```

Шаги 5–7 — то, чего нет в голом remote-MCP и ради чего строится свой воркер.

### Формат data-сообщений

Топик `linkeon`, JSON, поле `v` для версионирования (понадобится в C и D):

```jsonc
{"v":1,"type":"specialist_answer","jobId":"…","specialist":"Алексей","text":"…"}
{"v":1,"type":"specialist_failed","jobId":"…","specialist":"Алексей","reason":"timeout"}
{"v":1,"type":"specialist_pending","jobId":"…","specialist":"Алексей"}
```

`specialist_pending` бэкенд шлёт сразу после создания job — он нужен только фронту для
плашки «Алексей думает…»; воркер его игнорирует.

### Инжекция ждёт паузы

Если ответ пришёл, пока Роман говорит, воркер кладёт его в буфер до `response.done`.
Иначе Роман перебивает сам себя на полуслове — самый заметный глюк такой схемы.

### Тулы Романа — три, не десять

| Тул | Поведение |
|---|---|
| `ask_specialist(specialist, question)` | возвращает `{status, specialist}` мгновенно |
| `list_specialists()` | кеш `/webhook/agents`, собирается на старте звонка |

Ранняя редакция спеки закладывала третий тул `save_note(text)`. Он снят из v1 по
единственной причине: в голосовом разговоре он дублирует резюме звонка, а каждый
лишний тул — лишний повод модели уйти не туда.

Техническое препятствие, которое было в предыдущей редакции этой заметки
(«в notes-модуле нет ручки создания»), исчезло 25.08.2026: коммит `f8097a7`
добавил `POST /webhook/notes`. Так что вернуть тул теперь дёшево — вопрос только
в том, нужен ли он на самом деле.

Весь `CHAT_TOOLS` не отдаём: генерировать баннеры голосом в v1 незачем, а каждый лишний
тул — лишний повод модели уйти не туда. Список инструментов **не переносится между
сессиями** — каждая новая сессия заново тянет discovery, поэтому список держим коротким,
а отдачу быстрой (без похода в БД).

Параллельно висящих job — не больше трёх на звонок. Четвёртый `/internal/ask` получает
`200 {"status":"rejected","reason":"too_many_pending"}` (не ошибку — модель должна уметь
это озвучить: «сейчас уже три вопроса в работе, дождёмся ответов»).

## Данные

Две новые таблицы. Миграция — `src/voice-call/migrations/`.

```sql
CREATE TABLE voice_calls (
  id             UUID PRIMARY KEY,
  user_id        TEXT NOT NULL,           -- TEXT, не varchar(20): у email/OAuth это UUID
  agent_id       INTEGER NOT NULL,
  room_name      TEXT NOT NULL UNIQUE,
  status         TEXT NOT NULL,           -- dialing|active|completed|failed|interrupted
  started_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  ended_at       TIMESTAMPTZ,
  duration_sec   INTEGER,
  transcript     JSONB,                   -- [{role, text, ts}]
  summary        TEXT,
  recording_url  TEXT,                    -- задел под C/D; в v1 всегда NULL
  cost_usd       NUMERIC(10,4),
  model          TEXT
);

CREATE TABLE voice_call_jobs (
  id                   UUID PRIMARY KEY,
  call_id              UUID NOT NULL REFERENCES voice_calls(id) ON DELETE CASCADE,
  specialist_agent_id  INTEGER NOT NULL,
  question             TEXT NOT NULL,
  status               TEXT NOT NULL,     -- queued|running|done|failed
  answer               TEXT,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at          TIMESTAMPTZ,
  latency_ms           INTEGER
);
CREATE INDEX ON voice_call_jobs (call_id, status);
```

`user_id` — `TEXT`. У пользователей, зашедших через email/OAuth, идентификатор это
`gen_random_uuid()::text` длиной 36 символов, а не телефон; `varchar(20)` сломается.

**Прод-миграции накатывать через `psql` + ручной `INSERT` в `schema_migrations`** —
`npm run migrate` на проде застрял на `base/001` и после него ничего не докатывает.

## Ограничения OpenAI Realtime, которые видны уже в v1

Проверено 25.08.2026 по документации OpenAI:

- **Реконнект каждые 20 минут делает сам плагин.** В
  `@livekit/agents-plugin-openai@1.7.0` задан `DEFAULT_MAX_SESSION_DURATION = 20 * 60 * 1000`
  и есть механизм `reconnect()`, который переподнимает сокет и восстанавливает историю.
  Разговор не рвётся, переносить контекст руками не нужно.

  Прежняя редакция этого раздела утверждала «сессия обрывается на 60-й минуте,
  graceful-миграции контекста нет, перенос истории на нас». Для этого SDK неверно —
  проверено по исходникам плагина 25.08.2026 (`realtime_model.ts:143,1147`).

- **Но восстановленные после реконнекта элементы — только текстовые**
  (`realtime_model.ts:474`: «Items restored after reconnection are text-only»).
  Содержание разговора выживает, аудио-контекст — нет. На слух это может дать смену
  интонации или темпа каждые 20 минут. Проверяется только живым звонком длиннее
  20 минут — такой пункт есть в чек-листе задачи 14.

- **Часовой потолок звонка — наше продуктовое решение**, защита от расходов, а не
  обход ограничения API. За минуту до конца Роман подводит итог.
- **Вся история переотправляется модели на каждый Response** → расход токенов в минуту
  растёт по ходу разговора. TPM бьёт не по числу сессий, а по «сессии × длину».
- Лимита на число одновременных сессий в документации нет (цифру «100 для Tier 5» сняли
  03.02.2025, но её до сих пор цитируют).

**Наш тир — Tier 4**, проверено 25.08.2026 запросом с прода: заголовки
`x-ratelimit-limit-requests: 10000` и `x-ratelimit-limit-tokens: 10000000` на
`gpt-4o-mini` соответствуют строке Tier 4 (Tier 5 дал бы 30 000 / 150M). Для
realtime-моделей это **10 000 RPM / 4 000 000 TPM**. При поле в 1800 tok/мин на сессию
запас — порядка двух тысяч одновременных разговоров без учёта переотправки контекста и
сотни с учётом. Тир не является ограничением ни в v1, ни на рунге в 50 звонков;
предварительно пополнять счёт не нужно.

## Стоимость

Аудио тарифицируется фиксированно: вход 1 токен / 100 мс (600 tok/мин), выход
1 токен / 50 мс (1200 tok/мин). Ставки за 1M токенов: флагман — $32 in / $64 out,
mini — $10 / $20.

Пол при непрерывном микрофоне и агенте, говорящем примерно половину времени:
**~$3.5/час** на флагмане, **~$1.1/час** на mini. Без учёта текстового контекста, который
переотправляется каждый ход.

Транспорт на своём LiveKit — стоимость железа, то есть шум: **1–15% счёта**.

**В v1 считаем, но не списываем.** Воркер копит usage по `response.done`, на
`/internal/complete` пишем `voice_calls.cost_usd` и строку в `token_consumption_tasks`
с `tokens_to_consume = 0` и подробностями в `metadata`. Получаем реальную цену минуты до
того, как назначать тариф. Включение биллинга потом — один флаг, схема уже на месте.

|---|---|
| OpenAI 429 / недоступен | воркер → `/internal/failed`; фронт: «Роман сейчас не может говорить»; `cost_usd = 0` |
| job > 180 с | `specialist_failed` → «Алексей не отвечает, давайте я сам» |
| job упал с ошибкой | то же, но `reason: 'error'`; строка в `voice_call_jobs` со `status='failed'` |
| пользователь закрыл вкладку | LiveKit disconnect → воркер завершает через 30 с, звонок `completed` с записанным |
| воркер умер | фронт видит `ParticipantDisconnected` → `interrupted`, карточка с пометкой «оборвался» |
| сессия дожила до 60 мин | наш собственный потолок: Роман предупреждает за минуту и подводит итог |
| реконнект на 20-й минуте | делает плагин, история восстанавливается сама (текстом, без аудио-контекста) |
| **рестарт `linkeon-api`** | комната переживёт, но мост job'ов рвётся и ответ специалиста не придёт **молча** |

Последнее — та же грабля, что с чат-стримами: деплой посреди хода убивает ответ без
ошибки, без ретрая и без строки в истории. В `deploy.sh` нужна проверка активных звонков
перед рестартом, по аналогии с проверкой живых стримов.

## Инфраструктурная гигиена

Входит в объём работ — иначе фича встаёт на песок.

1. **`livekit.yaml` и определение контейнера — в git и в `deploy.sh`.** Сейчас конфиг
   существует в одном экземпляре на одной машине. Одна пересборка сервера — и SFU нет, а
   восстанавливать не по чему.
2. **Отдельные ключи LiveKit** для голосового чата, не переиспользовать
   `dozvon0987ebaed0ef3b8c`.
3. **UDP mux**: `rtc.udp_port: 7882-7892` вместо `port_range: 50000-60000`, диапазон не
   меньше числа vCPU (один сокет — точка сериализации). Снимает портовый потолок
   (~2500 комнат на ноду) до того, как мы в него упрёмся.
4. **`sort_by: cpuload` + `algorithm: twochoice`** уже сейчас, даже на одной ноде. Ноль
   стоимости, а когда появится вторая нода, не будет документированного «стадного»
   поведения, при котором все новые комнаты валятся на одну ноду.
5. **sysctl / ulimit** на хосте SFU: `ulimit -n 65535`, `net.core.rmem_max`,
   `net.core.wmem_max`, `somaxconn`.
6. **Починить `CLAUDE.md`**: раздел про shared-инфраструктуру Taler ID пометить как
   исторический, вписать реальность.

## Что измеряем с первого дня

Публичного бенчмарка для нашей формы нагрузки — много комнат по два участника,
audio-only — не существует. Все опубликованные замеры LiveKit про веер внутри одной
комнаты. Наша кривая с v1 будет единственным источником правды, поэтому снимаем сразу:

- peak RSS и CPU на job-процесс;
- тип ICE-кандидата (`host` / `srflx` / `relay`) — долю TURN под российских и мобильных
  операторов взять неоткуда;
- токены OpenAI на сессию в минуту;
- time-to-first-audio;
- распределение длины разговора.

## Предусловие: модуль `dozvon` выпиливается

**Решение владельца 25.08.2026: удалить модуль целиком.** Отдельная задача, выполняется
до или параллельно с этой работой; здесь фиксируется как предусловие, потому что снимает
дыру в безопасности и убирает мёртвую проводку к LiveKit, поверх которой иначе легко
начать строить.

При разборе инфраструктуры в нём нашлась дыра:

- `POST /webhook/dozvon/internal/recording-upload?callId=N`
  (`src/dozvon/dozvon-internal.controller.ts:20`) **не проверяет ничего**. Соседние два
  эндпоинта закрыты секретами, этот — нет. Тело целиком буферизуется в память без лимита
  и пишется в `public/dozvon/call_N.mp3`, отдаётся с нашего домена, обновляет
  `recording_url` в БД.
- `src/dozvon/recorder.service.ts:19` — `RECORDER_URL || 'http://167.172.181.34:3100'`.
  Переменной в проде нет, значит мы шлём на бокс постороннего человека JSON с адресом
  этого самого незащищённого эндпоинта. Оба вызова обёрнуты в `try/catch` с
  `warn`-логом — ни деплой, ни smoke этого не видят.

Path traversal нет (`callId` числовой, расширение из белого списка), это не RCE. Но
неаутентифицированная запись файла произвольного размера в публичную директорию — дыра.

Модуль нерабочий (ключей LiveKit в env нет), UI удалён в июне, кроны продолжают тикать.
Чинить авторизацию в мёртвом коде смысла нет — удаляется целиком.

**Объём удаления:** `src/dozvon/` (10 файлов), регистрация модуля в `app.module.ts`,
задачи планировщика в `dozvon-scheduler.service.ts`, эндпоинты `/webhook/dozvon/*`.
**Таблицы в БД (`dozvon_calls`, кампании) остаются** — там 53 исторических звонка, данные
не трогаем.

Что из удаляемого стоит прочитать до удаления, а не восстанавливать потом из git:
`voice-agent.service.ts` (`AgentDispatchClient.createDispatch` — та же механика нужна
в `VoiceCallModule`) и `sip.service.ts` (пригодится подсистеме D). Логику не копируем,
но образец вызовов SDK там рабочий.
