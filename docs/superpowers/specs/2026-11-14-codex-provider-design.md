# Codex — четвёртый провайдер ответов: GPT-6 Astra через локальный bridge

Дата: 2026-11-14. Продолжение `2026-10-29-qwen-fallback-design.md`,
`2026-10-30-llm-provider-switch-design.md` и `2026-10-31-kimi-provider-design.md`
(общий реестр запасных провайдеров). Макет-прототип выкачен и проверен на маке
владельца: `~/.linkeon/docs/2026-11-14-codex-bridge-design.md` (codex-bridge для
роутера моделей VS Code, 95/95 тестов, E2E с tool-use подтверждён владельцем).

## Зачем

1. У аварийной цепочки два звена (Qwen, Kimi), оба — платные планы со своими
   лимитами. При долгом сбое Claude + Qwen + Kimi отвечать некому.
2. Владелец хочет сравнивать GPT-6 Astra с остальными моделями на себе и на
   выбранных людях — так же, как Kimi и Qwen.

## Решения владельца (14.11)

- Аутентификация — **подписка ChatGPT Pro** (не API-ключ OpenAI): трафик идёт
  через бэкенд Codex `https://chatgpt.com/backend-api/codex/responses`.
- Аккаунт — **текущий личный аккаунт владельца** (тот же, что использует
  mac-bridge). Серость по ToS и смертность токенов приняты осознанно.
- Роль — **полный паритет с Kimi/Qwen**: четвёртое звено цепочки
  **Claude → Qwen → Kimi → Codex** (codex последним) + выбор в карточке
  пользователя + участие в глобальном рубильнике. Операционное правило:
  **глобальный рубильник на codex не ставить** (раздел «Мониторинг и правила»).
- Архитектура — **B: bridge + официальный codex CLI как освежитель**. Bridge
  (переводчик протокола) остаётся read-only, точно как на маке; свежесть токенов
  на каждом сервере поддерживает официальный codex CLI по cron. Своего
  refresh-кода нет вовсе. Вариант «codex CLI как второй движок вместо claude
  CLI» отвергнут: 3–5× объёма и ломает непрерывность бесед (`--resume`).

## Проверено до кода

- Anthropic-совместимого эндпоинта у OpenAI **нет**
  (`api.openai.com/v1/messages` → 404, проверено 14.11) — поэтому нужен
  переводчик протокола.
- Переводчик уже написан и проверен на маке: `codex-bridge.mjs` +
  `codex-translate.mjs` + `codex-sse.mjs` (тесты 10 + 12 + 17), live-smoke
  `end_turn`, полный E2E-цикл с tool_use в VS Code-сессии владельца (14.11).
- Геоблока нет: с обоих серверов (прод `212.113.106.202`, релей
  `5.101.115.184`; пробы 14.11) `chatgpt.com/backend-api/codex/responses` → 401
  (достигаем, нужен лишь токен), `api.openai.com/v1/models` → 401,
  `auth.openai.com` → 200.
- Node на серверах: бэкенд v20.20.2, релей v22.22.2 — bridge без зависимостей,
  подойдёт оба.
- `gpt-6-astra` — один и тот же slug и в кэше Codex-бэкенда, и в официальном API.
- Линии токенов независимы: каждый `codex login` заводит свою линию
  refresh-токенов; освежение одной линии не гасит access-токены других
  (access-токен — JWT со сроком ~10 дней, действует до истечения). Параллельные
  сессии трёх линий (мак, бэкенд, релей) официально не документированы —
  поэтому после каждого серверного логина делается smoke сосуществования
  (раздел «Выкат»).

## Устройство

### 1. codex-bridge (новый компонент, общий для бэкенда и релея)

Код mac-bridge переносится в `spirits_back/codex-bridge/` (корень репо, рядом с
`relay-agent/`): `bridge.mjs`, `translate.mjs`, `sse.mjs` + тесты
(`node --test`). Jest и tsc бэкенда каталог не трогают — как `relay-agent/`;
при переносе проверяется, что ничего не протекает в тулинг бэка.

Сетевой контракт — как на маке:

- слушает `127.0.0.1:8790` (env `BRIDGE_PORT`), только loopback; проверки
  Host/Origin/sec-fetch-site как в роутере;
- `POST /v1/messages` (SSE и non-streaming), `POST /v1/messages/count_tokens`
  (грубая оценка байты/4), `GET /healthz`, `HEAD /api/hello`;
- журнал: файл 0600 (каталог 0700), только поля
  `{time,id,type,route,model,status,error}` — тела, токены и текст сообщений не
  логируются никогда;
- перевод запроса: Anthropic Messages → Responses API (`instructions`,
  `input[]`, `function_call`/`function_call_output`, `reasoning.effort`
  (env `CODEX_BRIDGE_REASONING_EFFORT`, по умолчанию `medium`),
  `max_output_tokens = max(max_tokens, 1024)`, `stream: true`, `store: false`);
  thinking-блоки из запроса удаляются (прецедент Kimi);
- перевод ответа: Responses SSE → Anthropic SSE (`message_start`,
  `content_block_*` для текста и tool_use, `message_delta` со stop_reason
  (completed→`end_turn`, function_call→`tool_use`, incomplete→`max_tokens`) и
  usage, `message_stop`); reasoning-события пропускаются; HTTP-статусы upstream
  (включая 429 лимитов подписки) → Anthropic error-envelope с тем же статусом;
- обрыв клиента уничтожает upstream-запрос (не жжёт квоту) и логируется 499
  `client_disconnect`.

Отличия серверной версии от mac (все три — с тестами):

1. **Входящая `model` уважается**: mac-bridge подставлял константу; серверный
   берёт `model` из запроса (fallback-окружение само задаёт
   `ANTHROPIC_DEFAULT_*_MODEL=gpt-6-astra`, так что CLI шлёт именно его).
2. **401 от upstream → перечитать `auth.json` и повторить запрос один раз**
   (страховка от гонки: cron-освежитель мог ротировать файл между чтением и
   ответом upstream). Второй 401 — ошибка CLI как на маке
   («Codex token rejected…»), в журнале `upstream_status`.
3. **User-Agent**: env `CODEX_BRIDGE_UA`, по умолчанию
   `codex_cli_rs/<версия установленного CLI> (Linux; x86_64)`; версия — из
   `package.json` установленного на сервере `@openai/codex` (тот же приём, что
   на маке, где `codex --version` был сломан).

Аутентификация: `~/.codex/auth.json` пользователя, под которым работает bridge
(env-переопределение `CODEX_AUTH_PATH`), читается **на каждый запрос** и никогда
не пишется. Заголовки на upstream — как на маке: `Authorization: Bearer
<access_token>`, `chatgpt-account-id`, `openai-beta: responses=experimental`,
`originator: codex_cli_rs`, UA, `session_id` (новый UUID на запрос).

Запуск: pm2-процесс `codex-bridge` под пользователем API на каждой машине
(бэкенд — `dvolkov@212.113.106.202`, релей — `dv@5.101.115.184`), из чекаута
соответствующего репо. `deploy.sh` его не перезапускает: обновление кода моста —
ручной `pm2 restart codex-bridge` (с OK владельца; рестарт рвёт только идущие
через codex запросы).

### 2. Логин и свежесть токенов (на каждом сервере)

- Разово: `npm i -g @openai/codex@<закреплённая версия>` (пин фиксируется в
  раннбуке); `codex login` слушает `localhost:1455` — с мака пробрасывается
  туннель `ssh -L 1455:localhost:1455 <сервер>`, **вход в браузере подтверждает
  владелец сам** (пароль и 2FA Claude не касаются). Результат — независимая
  линия токенов в `~/.codex/auth.json` серверного пользователя.
- Поддержание свежести: cron на каждом сервере **раз в 3 дня** выполняет
  `codex exec` с тривиальным промптом («ответь ok»), модель `gpt-5.6-luna`, в
  scratch-каталоге, песочница read-only. Официальный CLI сам освежает истекающий
  токен и персистит `auth.json` своей линии. Расход квоты — пренебрежимый.
  Запас: срок токена ~10 дней, т.е. ≥3 попытки освежения до истечения.
- Вывод cron — в лог-файл (без секретов). Алертов у cron в v1 нет: мёртвая
  линия проявится как стойкие 401 из bridge → окно «не отвечает» у codex →
  существующий алерт запасных. Раннбук: повторить `codex login` на этом
  сервере, затем smoke сосуществования с маком.
- Если exec-песочница не заработает на серверном ядре (урок seccomp/LibreOffice
  на релее) — keep-alive-скрипт переключается на режим без песочницы для
  тривиального промпто без инструментов; проверяется первым прогоном.

### 3. Реестры (бэкенд и релей)

По одной записи в каждом файле; порядок цепочки:
`FALLBACK_ORDER = ['qwen', 'kimi', 'codex']`.

| | Codex |
|---|---|
| Адрес по умолчанию | `http://127.0.0.1:8790` (локальный bridge) |
| Модели opus / sonnet / haiku | `gpt-6-astra` для всех трёх |
| Ключ на бэкенде | `CODEX_FALLBACK_API_KEY` — **фиктивное значение** `local-bridge`: CLI требует непустой `ANTHROPIC_AUTH_TOKEN`, bridge его игнорирует. Наличие ключа = провайдер включён (общее правило) |
| Переопределения на бэкенде | `CODEX_FALLBACK_BASE_URL`, `CODEX_FALLBACK_MODEL_*` (из общей универсальности) |
| Ключ на релее | `/home/dv/file-agent/secrets/codex.key` (0600) — то же фиктивное значение; нет файла → codex выключен, переименование файла выключает без рестарта |

Окружение спавна — общий `fallbackSpawnEnv`, без изменений. Окна, план попыток
и правила переходов (`isFallbackWorthy`, `mayAdvance`) достаются codex
автоматически. 401/«Codex token rejected» от bridge классифицируется как сбой
доступа (вид `auth`) — мёртвая линия открывает окно «не отвечает», цепочка
идёт дальше; проверяется тестом.

Код:

- бэкенд — `src/common/services/llm-fallback.ts`: запись `PROVIDER_DEFAULTS`
  (`envPrefix: 'CODEX'`), `codex: null` в `NO_FALLBACK_CONFIGS`,
  `readFallbackConfigs` возвращает `{ qwen, kimi, codex }`;
- релей — `relay-agent/llm-fallback.mjs`: запись с `keyFile`;
- `fallbackStats()` / `stats()` / `/health.fallback.providers` /
  `claude_cli_call.provider` / `done.provider` / `chat_quality.props` получают
  codex из универсальности — отдельного кода не требуют.

### 4. Переключатели

- **По пользователю** (`ai_profiles_consolidated.llm_provider`): значение
  `'codex'` становится валидным автоматически (`LlmProvider = AnswerProvider`,
  `LLM_CHOICES` выводится из `ANSWER_PROVIDERS`). Незнакомое/выключенное
  значение по-прежнему читается как Claude — откат деградирует мягко.
- **Глобальный рубильник**: валидация `isAnswerProvider` пропускает codex
  автоматически; ручная правка одна — `admin-global-llm.controller.ts`
  `configured()` → `{ qwen, kimi, codex }` (+ его spec). Правило 409 `no_key`
  сохраняется: без ключа на сервере рубильник на codex не переключить.
- **Фронт** (`spirits_front`): `src/components/admin/globalLlm.ts` — локальная
  копия юниона (`AnswerProvider`, `PROVIDERS`, `PROVIDER_LABELS`, парсер,
  `configured`) расширяется codex; лейбл — **«Codex (GPT-6 Astra)»**;
  `GlobalLlmProviderControl.tsx`, `UserLlmProviderControl.tsx` (+ их тесты),
  `GlobalLlmBanner.test.tsx`, `UserActivityDrawer` — по образцу Kimi; тексты —
  в локалях, где уже есть лейблы провайдеров (ru, en, pt). У варианта codex в
  рубильнике — пометка «только аварийно» (правило из раздела 5).

### 5. Мониторинг и операционные правила

- Существующая универсальность покрывает codex без нового кода: строка алерта
  «Запасные за 15 мин: … Codex — ответов N, ошибок M» (или «не настроен»),
  монитор релея читает `providers.codex`, суточное напоминание
  `GlobalLlmReminderService` срабатывает на любого провайдера рубильника кроме
  Claude (включая codex).
- **Правило: глобальный рубильник на codex не ставится.** Причина: квота одной
  личной подписки общая с работой владельца, а длительный сбой Claude с полным
  продуктовым трафиком выберет её и уронит codex в окно «не отвечает» у всех
  сразу. Codex — последнее звено аварийной цепочки и личный выбор отдельных
  пользователей. Правило фиксируется в этом спеке и в пометке в админке
  (раздел 4).

### Соответствие концепции

Концепция — `linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`.

- **§4.2.2 «обработка облачной моделью: открытый текст проходит, используется и
  не сохраняется»** — codex обрабатывает ходы через личный аккаунт ChatGPT Pro
  владельца (бэкенд Codex), т.е. по потребительским условиям OpenAI, а не по
  enterprise/API-условиям с гарантией «не используется для обучения».
  Использование личной подписки как бэкенда продукта — серая зона ToS;
  **владелец предупреждён и принял риск решением от 14.11** — тот же прецедент,
  что у Qwen Token Plan и ключа Kimi Code (см. «Риски» kimi-спека). Аварийная
  цепочка уводит туда беседы пользователей без их ведома — для codex это
  принято так же, как ранее для Qwen.
- **§2.5 и §4.2.2 — выбор человека на каждое использование** — фича добавляет
  провайдера, а не новый вид данных, уходящих с устройства; выбор в карточке
  работает как у Kimi/Qwen.

### Риски

- **ToS/аккаунт**: OpenAI строже Alibaba/Moonshot смотрит на использование
  подписки вне официальных клиентов; худший случай — блокировка аккаунта,
  которая заденет и личный ChatGPT Pro владельца, и mac-bridge. Принято
  владельцем (14.11). Смягчение: codex — последнее звено цепочки (минимальный
  трафик), рубильник на него не ставится.
- **Общая квота Pro**: работа владельца в Codex/ChatGPT + аварийный трафик
  продукта — один план; при 429 codex уходит в окно «не отвечает», цепочка
  продолжает работать без него.
- **Линии токенов**: три независимые линии одного аккаунта; терпимость к
  параллельным сессиям не документирована — проверяется smoke после каждого
  логина. Смерть линии — раннбук повторного `codex login`.
- **Бэкенд Codex может измениться без предупреждения** (это не публичный API):
  bridge сломается, codex выпадет из цепочки через окно «не отвечает»; Claude,
  Qwen и Kimi это не затронет.
- `total_cost_usd` считает ответы codex по прайсу Opus — существующий артефакт
  всех запасных провайдеров (зафиксирован в kimi-спеке), без изменений.

## Тесты

- Бэкенд (jest, на ноде): реестр codex (умолчания, переопределения, нет ключа);
  окружение; план с цепочкой из четырёх; классификация 401/«Codex token
  rejected» как сбоя доступа; `configured()` с codex; `answer-provider`;
  админ-ручки (валидация, 409); рубильник; строка алерта запасных.
- `codex-bridge/` (`node --test`): перенесённые mac-наборы (translate 10,
  sse 12, bridge 17) + новые: passthrough входящей `model`; 401 → перечитал
  auth → ровно один повтор; linux-UA по умолчанию. Проверка, что jest/tsc бэка
  каталог не подхватывают.
- Релей (`node --test`): `llm-fallback.mjs` с codex — план, `mayAdvance`,
  `stats()`; прежние тесты релея зелёные.
- Фронт (vitest): опция codex в обоих контролах, пометки «нет ключа», баннер,
  ключи локалей.
- Живые проверки — только на Linux, каждая ровно один раз, с OK владельца
  (тратят квоту Pro):
  - бэкенд: скрипт по образцу `qwen-fallback-check.js` на собранном `dist` в
    изолированном окружении (пустой `CLAUDE_CONFIG_DIR`, ключей qwen/kimi нет) →
    цепочка отвечает через codex;
  - bridge: `curl /v1/messages` «ответь OK» → `end_turn` — на обоих серверах;
  - CLI: `claude -p --model gpt-6-astra` с fallback-окружением →
    `is_error=false`;
  - сосуществование: после каждого серверного логина `gpt-6-astra` на маке
    продолжает отвечать через роутер 8788;
  - keep-alive: первый прогон cron — exec успешен; после истечения токена —
    `auth.json` обновлён (mtime);
  - E2E: владелец переключает свою карточку на Codex, пишет ассистенту, в
    `claude_cli_call` — `provider: 'codex'`, затем возвращает выбор обратно.

## Выкат

Каждый шаг — с OK владельца; рестарты — при отсутствии живых стримов.

1. **Код**: bridge в `spirits_back/codex-bridge/`, реестры бэка и релея,
   `configured()`, фронт, тесты зелёные. Бэкенд и фронт — `deploy.sh`
   (двухфазный); релей — вручную по рецепту (файлы рядом → `node --check` →
   `node --test` → git-коммит в живой ветке part-b → `pm2 restart file-agent`
   при нуле ходов). Ключей нигде нет — codex выключен везде, выкат ничего не
   меняет в поведении.
2. **Бэкенд-сервер**: установка codex CLI (пин), `codex login` через туннель
   :1455 (браузер — владелец), smoke сосуществования с маком, pm2
   `codex-bridge`, curl-smoke моста, ключ в `.env` через stdin, перезапуск API
   выкатом `deploy.sh` (`BACK_ONLY=1`), cron keep-alive, скриптовый smoke
   цепочки.
3. **Релей**: то же — логин (владелец), smoke сосуществования, pm2 bridge,
   файл ключа 0600 (рестарт `file-agent` не нужен), cron, curl-smoke.
4. **E2E владельца** — из раздела «Тесты».

## Откат

- Выключить: релей — переименовать `codex.key` в `.disabled` (без рестарта);
  бэкенд — убрать `CODEX_FALLBACK_API_KEY` из `.env` и перезапустить API
  выкатом. Сохранённые выборы `llm_provider='codex'` деградируют до Claude
  (предупреждение в лог — существующее поведение для ненастроенного
  провайдера).
- Полный съём: `pm2 delete codex-bridge` + удаление cron на обоих серверах;
  серверные линии входа владелец может отозвать в настройках аккаунта ChatGPT
  (сессии). Записи реестра можно оставить: без ключа провайдер выключен.
