# Kimi — третий провайдер ответов: выбор в карточке и второе звено запасного пути

Дата: 2026-10-31. Продолжение `2026-10-29-qwen-fallback-design.md` (запасной путь
`ClaudeCliService` на Qwen) и `2026-10-30-llm-provider-switch-design.md`
(переключатель модели по аккаунту и запасной Qwen на релее).

## Зачем

1. У запасного пути одно звено. У Qwen Token Plan свои лимиты (кредиты на 5 часов
   и на неделю); кончились они во время сбоя Claude — отвечать некому.
2. Владелец хочет сравнить Kimi K3 с Claude и Qwen на себе и на выбранных людях.

## Решения владельца (30–31.10)

- Kimi — и вариант выбора в карточке пользователя (как Qwen), и второе звено
  аварийной цепочки: **Claude → Qwen → Kimi**.
- Ключ — постоянный API-ключ из кабинета Kimi Code. Вход подписки по OAuth не
  годится: токен живёт 15 минут, а обновлять его с сервера значит выбивать вход
  на маке владельца.
- Выбранный провайдер не ответил — ответ даёт обычный путь: Claude, а при его
  сбое — цепочка без упавшего.
- Подход — общий реестр запасных провайдеров, а не копия кода Qwen: правила
  цепочки остаются в одном месте, следующий провайдер — одна запись и ключ.

## Проверено до кода

- Kimi Code принимает Anthropic Messages по `https://api.kimi.ai/coding/v1/messages`,
  то есть для Claude Code `ANTHROPIC_BASE_URL=https://api.kimi.ai/coding`; ключ —
  в `ANTHROPIC_AUTH_TOKEN`, как у Qwen. Адрес за Cloudflare, запросы с UA CLI
  проходят.
- Модели: `k3`, `k3-256k`, `k3.1-pro`, `k3.1-pro-highspeed` (двойной расход).
  `k3.1-pro` ответил за ~6 с, `k3` — за ~17 с (мак, 30.10).
- Linux без bubblewrap (релей), `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0`: `k3.1-pro`
  отвечает, exit 0 (30.10).
- `--resume` в обе стороны (31.10, мак, CLI 2.1.280): беседа Opus → Kimi → Opus →
  Kimi сохраняет контекст. Блоки thinking у Kimi приходят со своей подписью, и
  Claude их принимает.
- Стоимость: для `k3.1-pro` CLI считает `total_cost_usd` по прайсу Opus, как для
  Qwen. Первый ход после смены провайдера платит за весь контекст без кэша — кэш
  у каждого провайдера свой; дальше Kimi отдаёт `cache_read`. С `--resume` CLI
  отдаёт `total_cost_usd` нарастающим итогом за беседу — релей уже считает
  стоимость хода сам (`turn-cost.mjs`), бэкенд `--resume` не использует.

## Устройство

### 1. Реестр запасных провайдеров

Основной провайдер — Claude. Запасные — в порядке цепочки: Qwen, затем Kimi.

| | Qwen | Kimi |
|---|---|---|
| Адрес по умолчанию | `https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic` | `https://api.kimi.ai/coding` |
| Модели opus / sonnet / haiku | `qwen3.8-max` / `qwen3.8-flash` / `qwen3.6-flash` | `k3.1-pro` для всех трёх |
| Ключ на бэкенде | `QWEN_FALLBACK_API_KEY` | `KIMI_FALLBACK_API_KEY` |
| Переопределения на бэкенде | `QWEN_FALLBACK_BASE_URL`, `QWEN_FALLBACK_MODEL_*` | `KIMI_FALLBACK_BASE_URL`, `KIMI_FALLBACK_MODEL_*` |
| Ключ на релее | `secrets/qwen.key` или путь в `QWEN_KEY_FILE` | `secrets/kimi.key` или путь в `KIMI_KEY_FILE` |

Провайдер включён, если есть его ключ. Длина окон (раздел 2) — одна на всех:
`LLM_FALLBACK_BREAKER_MS`, по умолчанию 5 минут; прежнее `QWEN_FALLBACK_BREAKER_MS`
читается, если нового нет.

Окружение процесса у всех запасных одно (нынешний `qwenSpawnEnv`, обобщённый):
снять `ANTHROPIC_*` и `CLAUDE_CODE_OAUTH_TOKEN`; задать `ANTHROPIC_BASE_URL`,
`ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL`,
`CLAUDE_CODE_SUBAGENT_MODEL` (модель класса opus), `CLAUDE_CODE_MAX_RETRIES=1`,
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `API_TIMEOUT_MS=300000`,
`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0`. Модель в `--model` — по классу запрошенной
модели Claude, как сейчас у Qwen (незнакомое — класс opus).

Код:
- бэкенд — `src/common/services/llm-fallback.ts` вместо `qwen-fallback.ts`:
  реестр, чтение конфигов, модели, окружение, план попыток и состояние окон
  (небольшой объект без зависимостей — проверяется тестами отдельно от запуска
  CLI);
- релей — `relay-agent/llm-fallback.mjs` вместо `qwen-provider.mjs`, с тем же
  содержимым.

Правила «сбой доступа» (`src/common/llm-error.ts`, `isAccessFailure` релея) не
меняются и одинаковы для всех провайдеров. Старые модули удаляются, импорты
переводятся на новые, прослоек для старых имён нет.

### 2. Окна

Состояние — на процесс: в бэкенде — в `ClaudeCliService`, на релее — в процессе
`server.mjs`.

- **Окно Claude** (нынешний предохранитель). Открывается при сбое доступа к
  Claude (вход, лимит, перегрузка), если включён хоть один запасной. Пока оно
  открыто, вызовы идут сразу к запасным, без попытки Claude. Закрывается:
  успехом Claude, начатым после открытия окна; по истечении; когда вызов,
  дошедший до запасных, закончился ошибкой (никто из них не ответил — Claude мог
  уже ожить, следующий вызов снова попробует его). Сбой доступа к Claude
  открывает окно и тогда, когда сам вызов повторять нельзя, — как сейчас.
- **Окно «не отвечает» у каждого запасного.** Открывается его сбоем доступа в
  любом вызове — аварийном или по выбору пользователя. Пока оно открыто,
  аварийная цепочка его пропускает. Закрывается его успехом или по истечении.
- Окно Claude открыто, а все включённые запасные «не отвечают» — вызов идёт на
  Claude, как при закрытом окне: переключаться не на кого.

Счётчики «ответил / упал» за 15 минут ведутся по каждому запасному и только для
аварийных вызовов: вызовы по выбору пользователя — не авария.

### 3. Порядок попыток (одинаково в бэкенде и на релее)

План вызова — упорядоченный список провайдеров, его считает чистая функция от
выбора пользователя, включённых провайдеров и окон на момент начала вызова:

- **Проба мониторинга или проба без входа** (`noFallback`) — только Claude: ни
  выбора, ни цепочки.
- **Обычный путь.** Окно Claude закрыто — Claude, затем включённые запасные,
  которые не «не отвечают», в порядке цепочки. Окно открыто — только эти
  запасные (если их нет — как при закрытом окне).
- **Выбран Qwen или Kimi**, и его ключ есть — сначала выбранный, затем обычный
  путь без него. Выбранный пробуется и тогда, когда его окно «не отвечает»
  открыто: выбор — явная проверка, его сбой должен быть виден. Ключа нет —
  предупреждение в лог и обычный путь.

План считается в начале вызова. При переходе запасной, который за это время
стал «не отвечает» (его уронил параллельный вызов), пропускается. Claude после
запасных в том же вызове не пробуется: план, начатый с запасных, кончается на них.

Переход к следующему в плане разрешён, только если:
1. попытка упала по подходящей причине:
   - Claude или запасной в аварийной цепочке — сбой доступа (`isFallbackWorthy`:
     вход, лимит, перегрузка, а также 403 / Access denied / Arrearage — так
     Alibaba отвечает при неоплаченном плане или долге; не таймаут и не длина
     контекста);
   - выбранный провайдер — любой сбой (решение владельца);
2. повторить безопасно — правила те же, что сейчас: модель не вызывала
   инструментов с последствиями; человек ещё не видел ни куска ответа (вызов с
   `onTextDelta` не переигрывается вовсе, на релее — пока не ушёл первый текст);
   ход не прерван новым сообщением и клиент не ушёл (релей).

Отказ CLI, пришедший обычным ответом (`looksLikeCliRefusal`), — сбой того
провайдера, который его дал, а не только Claude.

Время: каждая следующая попытка получает остаток бюджета вызова, но не меньше
минуты (`fallbackTimeoutMs`, как сейчас). Худший случай — бюджет плюс две минуты.

Переход запрещён или план кончился — вызывающий получает ошибку, человек — то же
вежливое уведомление, что сейчас, токены не списываются. Ошибка перечисляет
попытки по порядку: первой — причина первой попытки (у выбранного —
`<провайдер> (выбран): …`; если Claude пропущен из-за окна —
`claude CLI пропущен (окно запасного пути)`), дальше `| <провайдер> fallback: …`.
Логи — по образцу нынешних: `claude CLI → запасной Kimi k3.1-pro (<вид>)`,
`claude CLI cost (kimi)`.

### 4. Бэкенд: `ClaudeCliService`

- `ClaudeCliOptions.provider?: 'qwen' | 'kimi'`.
- `runRaw` проходит план из раздела 3; один запуск — `runOnce` с конфигом
  провайдера или без него (Claude).
- **Вызовы с MCP всегда идут в stream-json.** В stream-json видно, вызывала ли
  модель инструмент, а от этого зависит, можно ли повторить вызов у другого
  провайдера (инструмент с последствиями сработал бы дважды). Маша и TG-боты и
  так идут в stream-json — они передают `onProgress`; правило — страховка для
  любого будущего вызова с MCP без `onProgress`, который в json-режиме не
  повторялся бы никогда.
- Событие `claude_cli_call`: `provider` — кто ответил (`claude` / `qwen` /
  `kimi`), `fallback` — ответ дал аварийный путь, `selected` — выбор
  пользователя, если он не Claude. Пишутся, как и сейчас, только успешные
  вызовы; «выбранный подвёл» видно по `selected` ≠ `provider`.
- `fallbackStats()` сохраняет нынешние поля: `enabled` — включён хоть один
  запасной; `ok` / `failed` — суммы по запасным; `breakerOpenUntil` — окно Claude,
  его читает проба без входа; `windowMs`. Добавляется
  `providers: { qwen: { enabled, ok, failed, downUntil }, kimi: { … } }`.
- Меняется прежнее поведение: сбой выбранного Qwen раньше давал ошибку
  `claude CLI не вызывался (выбран Qwen) | qwen: …`, теперь — ответ обычным
  путём.

### 5. Выбор в карточке

- Колонка `ai_profiles_consolidated.llm_provider`: `NULL` (Claude), `'qwen'` или
  `'kimi'`. Колонка текстовая, миграция не нужна; незнакомое значение читается
  как Claude.
- `GET/POST /webhook/admin/users/:userId/llm-provider`: `provider` —
  `'claude' | 'qwen' | 'kimi'`. Ответ получает `configured: { qwen, kimi }`;
  прежнее `qwenConfigured` остаётся для старого фронта на время выката. 400 —
  чужое значение, 404 — нет пользователя, запись в лог «кто кого переключил» —
  как сейчас.
- Фронт, блок «Модель ответов» в карточке пользователя:
  - три варианта: «Claude (по умолчанию)», «Qwen», «Kimi»;
  - у варианта без ключа на сервере — пометка «нет ключа»; если без ключа именно
    выбранный — прежнее предупреждение «Ключ … на сервере не настроен — ответы
    пойдут через Claude»;
  - подсказка: «Если выбранная модель не ответит, ответит Claude»;
  - без поля `configured` в ответе (старый бэкенд) Kimi считается
    ненастроенным, Qwen — по `qwenConfigured`;
  - тексты — в локалях, где блок уже есть (ru, en, pt).
- Где выбор действует — как сейчас: веб-чаты через релей, Маша, TG-боты, у
  которых человек — владелец (основной ход, не привратник). Пробы мониторинга,
  проба без входа и фоновые задачи выбору не следуют.

### 6. Релей

- Запрос: поле `provider` — `qwen` или `kimi` (прочие значения игнорируются —
  Claude); `noFallback=1` — как сейчас.
- Ключи — файлами, читаются на каждом ходе: нет файла — провайдер выключен,
  сменить ключ можно без рестарта.
- Модуль `llm-fallback.mjs`: реестр, конфиги, модели, окружение, распознавание
  сбоя доступа (прежние правила), план попыток, состояние окон и счётчики.
- Ход: провайдер — первый в плане. При сбое — следующий в плане, если переход
  разрешён (раздел 3), с тем же `--resume`. У выбранного провайдера переход
  разрешает не только сбой доступа, но и любая ошибка в `result` — в том числе
  после штатного повтора при временной ошибке. Условия те же: первый текст ещё не
  ушёл, инструментов с последствиями не было. Сбой доступа, который релей штатно не
  повторяет (например, `400 Arrearage`), переводит ход к следующему сразу — иначе
  человеку ушёл бы сырой текст ошибки. Упали все — прежние уведомления
  (`cli_fatal` / `transient`), ход `failed`, токены не списываются.
- `done`: `provider` — `claude` / `qwen` / `kimi`; `fallback` — ответ дал
  аварийный путь.
- `/health`: новое поле
  `fallback: { windowMs, breakerOpenUntil, lastOpenedAt, lastClaudeOkAt,
  providers: { qwen: { enabled, ok, failed, downUntil }, kimi: { … } } }`.
  Прежнее поле `qwen` остаётся с прежним смыслом (окно Claude и счётчики Qwen):
  его читает монитор, пока не выкачен новый бэкенд.
- Врезка — скриптом `relay-agent/llm-fallback-patch.py` поверх уже стоящей
  врезки Qwen (`qwen-patch.py`). Якоря — текст врезки Qwen, он одинаков в живом
  релее и в копии `relay-agent/` в main. Каждый якорь — ровно один раз, проверки
  до записи. `qwen-provider.mjs` и его тест удаляются тем же коммитом.

### 7. Бэкенд ↔ релей

- `relayProviderFields(probe, provider)`: выбор `qwen` / `kimi` → поле
  `provider`; проба → `noFallback=1`.
- `readDoneProvider` понимает `kimi`.
- `chat_quality.props`: `provider`, `fallback` и `selected` — выбор
  пользователя, если он не Claude (бэкенд знает его сам).
- Старый релей `provider=kimi` не знает и отвечает через Claude — поэтому релей
  выкатывается первым.

### 8. Мониторинг

- Алерт «Локальный Claude CLI недоступен» — строка по каждому запасному:
  «Запасные за 15 мин: Qwen — ответов N, ошибок M; Kimi — не настроен».
- Монитор релея (`RelayQwenMonitorService`) читает `/health.fallback`, а если его
  нет — прежнее `qwen`. Переменная `RELAY_QWEN_MONITOR` и компонент
  `relay_qwen_fallback` в `monitor_alert_state` сохраняют имена: настройка test и
  состояние антиповтора переживают выкат. Признак «аварийный режим» — прежний
  (окно Claude, `lastOpenedAt` / `lastClaudeOkAt`), счётчики суммируются по
  запасным. Тексты:
  - 🟠 «Релей: Claude недоступен — ассистенты отвечают через запасные» и та же
    строка, что в алерте CLI (`fallbackAlertLine`): «Запасные за 15 мин: Qwen —
    ответов N, ошибок M; Kimi — не настроен»;
  - 🔴 «Релей: Claude недоступен, запасные тоже не отвечают» — ответов ноль,
    ошибки есть;
  - 🟠 «Релей: Claude не отвечал с момента сбоя — запасные за 15 мин не
    понадобились»;
  - 🟢 «Релей: Claude снова отвечает» — как сейчас.
- Пробы мониторинга — `noFallback`, меряют только Claude.

## Соответствие концепции

Концепция — `linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`.

- **§4.2.2 «обработка облачной моделью: открытый текст проходит, используется и
  не сохраняется»** — держится договором с провайдером («модель без состояния»).
  Запасной провайдер получает ход ассистента целиком, то есть беседу человека,
  поэтому условия провайдера — часть решения:
  - **Qwen (Alibaba Model Studio):** по официальной документации данные бесед не
    используются для обучения; срок хранения не указан. Запасной путь на Qwen на
    проде с 30.10; его спеки этого раздела не содержали — фиксируется здесь.
  - **Kimi Code (Moonshot):** по соглашению Kimi контент пользователей по
    умолчанию идёт в обучение и улучшение моделей; отказ — только письмом
    (адрес в соглашении — support@moonshot.cn). Это прямо расходится с §4.2.2:
    в аварийной цепочке туда без ведома людей ушли бы беседы всех пользователей,
    включая психолога и юриста.
  - **Решение владельца (31.10):** Kimi входит и в выбор, и в цепочку, но ключ
    Kimi на прод и на релей кладётся только после письменного подтверждения
    отказа от обучения. До этого Kimi на проде выключен — ключа нет, в карточке
    он помечен «нет ключа».
- **§2.5 и §4.2.2 — выбор человека на каждое использование.** Для веб-кабинета
  фича этого не меняет: беседы с ассистентами и раньше обрабатывала облачная
  модель. Фича добавляет провайдера, а не новый вид данных, уходящих с
  устройства.

## Риски

- Kimi Code — подписка для программирования; её условия могут не допускать
  использование ключа бэкендом продукта (как и у Token Plan), а присланный
  контент по умолчанию идёт в обучение (см. «Соответствие концепции»). Если
  ключ отзовут, Kimi выпадет из цепочки через окно «не отвечает»; Claude и Qwen
  это не затронет.
- Квота Kimi общая с личной работой владельца в Kimi Code: долгий сбой Claude и
  Qwen может её выбрать.
- Каждая смена провайдера в беседе — один ход без кэша, по цене Opus. Это
  центы; списание с людей — как обычно, по стоимости хода от CLI.
- Хранение ключа Kimi на релее — такое же, как у ключа Qwen; общая защита
  секретов релея — отдельная задача.

## Тесты

- Бэкенд (jest, на ноде):
  - реестр: умолчания Kimi, переопределения, нет ключа;
  - окружение Kimi;
  - план: все ветки раздела 3;
  - переходы: сбой доступа против прочих сбоев, «выбранный — любой сбой»,
    запреты по инструментам и `onTextDelta`;
  - вызовы с MCP идут в stream-json;
  - окна: Claude, «не отвечает», все запасные «не отвечают» → Claude;
  - `fallbackStats()`: прежние поля и `providers`;
  - события: `provider`, `fallback`, `selected`;
  - админ-ручки: `kimi`, `configured`;
  - `answer-provider`;
  - TG-роутер: выбор владельца `kimi`;
  - монитор релея: новое и старое поле `/health`, тексты;
  - строка алерта CLI.
- Релей (`node --test`): `llm-fallback.mjs` целиком; врезка ложится на копию в
  main и на копию живого `server.mjs`; прежние тесты релея зелёные.
- Фронт (vitest): три варианта, пометки «нет ключа», сохранение, старый ответ без
  `configured`.
- Живые проверки — только на Linux (урок SCRUB):
  - бэкенд — скрипт по образцу `scripts/qwen-fallback-check.js` на собранном
    `dist`: Claude сломан пустым `CLAUDE_CONFIG_DIR`, Qwen без ключа → отвечает
    Kimi; выбран Kimi → отвечает Kimi; выбран Kimi с битым ключом → попытка
    Claude;
  - релей — стенд на ноде, слушает только `127.0.0.1`, пустой
    `CLAUDE_CONFIG_DIR`, ключи во временных файлах. Сценарии: сбой Claude без
    ключа Qwen → Kimi; сбой Claude, битый ключ Qwen → Kimi; `provider=kimi` →
    Kimi; `provider=kimi` с битым ключом → попытка Claude, затем Qwen;
    `noFallback=1` → прежнее уведомление. Стенд снимается сразу после проверки.

## Выкат

Каждый шаг — с OK владельца.

1. Релей — вручную по рецепту: файлы рядом → врезка в копию `server.mjs` →
   `node --check` → `node --test` → замена и коммит в git релея →
   `pm2 restart file-agent`, когда нет живых ходов → `/health`. Ключа Kimi ещё нет — Kimi выключен; Qwen работает как прежде, кроме
   одного: сбой выбранного Qwen теперь переигрывается на Claude.
2. Бэкенд и фронт — `deploy.sh`. Ключа Kimi нет — Kimi выключен.
3. **Только после письменного подтверждения отказа Kimi от обучения** (см.
   «Соответствие концепции»): ключ Kimi — в `.env` прода (через stdin) и
   перезапуск API выкатом `deploy.sh` (`BACK_ONLY=1`). Если подтверждение
   пришло раньше шага 2 — ключ кладётся до него, и отдельный перезапуск не
   нужен. Ключ на релей — файлом (600), без рестарта.
4. Живые проверки из раздела «Тесты». Владелец выбирает Kimi в своей карточке и
   пишет Роману, Маше и своему TG-боту; в событиях — `provider: 'kimi'`.

## Вне охвата

- Фоновые задачи по выбору пользователя — по-прежнему обычный путь с аварийной
  цепочкой.
- Запасные для пробы без входа — нет, как сейчас.
- Отдельные ключи или квоты под выбор и под аварию — ключ у провайдера один.
- Чтение MCP-инструментов без последствий (справка, поиск файлов) как
  «безопасных» для повтора — возможно позже, если понадобится.
- Pay-as-you-go Moonshot (`https://api.moonshot.ai/anthropic`) вместо ключа
  Kimi Code — замена одной записью реестра, если ключ отзовут.
