# Ассистент ведёт продукт целиком: от создания до удаления

Дата: 25.10.2026. Решение владельца: «нужно давать ассистенту полностью
управлять продуктами от создания до удаления». Задача в бэклоге —
«Ассистент управляет продуктами полностью: от создания до удаления»; в неё
входят «Продукты: удаление» и «Продукты: смена и добавление ключей после
создания».

## Зачем

Первый живой бот-продукт клиента (25.10.2026) прошёл весь путь и упёрся в три
стены:

- ключи бота задаются только при создании — назвал их не так, как ждал код,
  исправить нечем, пришлось заводить второго бота заново;
- удалить ненужный продукт нечем ни пользователю, ни администратору
  (`products.archived_at` не пишет ни один код); погашенный администратором
  продукт продолжает занимать место в пределе аккаунта;
- создать продукт ассистент не может: только кнопкой в Студии.

Попутно человек вставил ключи сторонних API прямо в текст правки — это прямое
следствие того, что другого пути передать ключ из разговора нет.

## Решения владельца (25.10.2026)

| Вопрос | Решение |
|---|---|
| Как ключи попадают в продукт | Защищённая карточка: значения уходят прямо на сервер, мимо модели и истории чата |
| Что значит «удалить» | Мягко: продукт гаснет сразу, освобождает место и аренду; 30 дней на возврат, потом стирается насовсем |
| Подтверждение | Удаление — только кнопкой; создание — словом, с названной ценой |
| Каналы первой версии | Веб (и React-приложение) и Telegram; во Flutter — ссылка на то же действие в кабинете |
| Как карточка попадает в чат | Её прикрепляет сервер, а не модель |
| Откат правки | Входит |

## Что есть сейчас

- `manage_product` (`src/products/product-tool.service.ts`): `list`, `edit`,
  `status`, `domain`. Отдаётся только с `/webhook/mcp/products`; владелец — из
  подписанного токена сессии (`product-tool.token.ts`: `userId`, `channel`),
  аргумента `userId` нет. Есть у всех ассистентов релея, у Маши и в Telegram
  (владельцу, без посторонних в чате).
- Создание — `POST /webhook/products` (форма Студии): имя, слаг, вид, секреты
  (`BOT_TOKEN` и «Дополнительные ключи»). Предел — 2 продукта на аккаунт
  (`limits.service.ts`, считаются все, кроме архивных). Аренда — 50 000
  токенов в месяц (`RENT_TOKENS`), первый месяц бесплатно.
- Задания агента машины (`JobKind`): `provision`, `sleep`, `wake`, `domain`.
  `sleep` — заглушка на домене и `docker stop`; `wake` — обратно и
  `docker start`. Контейнер и каталог `/srv/products/<слаг>` при этом целы.
- Откат правки — `TurnsService.revert` (кнопка в кабинете).
- Гашение администратором — `POST /webhook/products/block`.
- Резервные копии — голые репозитории на проде
  `~/product-repos/<слаг>.git`, есть не у всех продуктов.

## Действия инструмента

Тот же `manage_product`, новые значения `action`. Действия, которые
меняют деньги или ключи или необратимы, сами ничего не делают: заводят
**ожидающее действие** (см. ниже), а сделать его может только человек.

| action | Подтверждение | Что делает |
|---|---|---|
| `create` `{kind:'site', name, prompt?}` | словом в разговоре | Создаёт сайт сразу. До вызова ассистент называет условия: первый месяц бесплатно, дальше 50 000 токенов в месяц, не больше двух продуктов |
| `create` `{kind:'bot', name, prompt?}` | карточка ключей | Заводит ожидающее действие `create_bot`; бот создаётся, когда человек отправит карточку с `BOT_TOKEN` и ключами |
| `keys` `{product}` | карточка ключей | Заводит `keys`: в карточке имена текущих ключей (значения — никогда), можно заменить, убрать, добавить |
| `delete` `{product}` | кнопка | Заводит `delete`; удаление — по нажатию |
| `restore` `{product}` | словом | Возвращает удалённый в течение 30 дней |
| `revert` `{product, turnId?}` | словом | Откат правки; без `turnId` — последней применённой |

`prompt` у `create` — описание первой правки: сервер ставит её, как только
заведение завершилось. «Создай бота, который каждое утро присылает отчёт» —
одна просьба, а не три.

Слаг для `create` выбирает сервер — по тому же правилу, что форма Студии
(основа из имени и случайный хвост); модель слагов не придумывает.

`list` показывает и удалённые, ещё не стёртые продукты — отдельным списком с
датой, до которой их можно вернуть.

`status` принимает и идентификатор ожидающего действия: ассистент узнаёт, чем
кончилась карточка.

## Ожидающее действие и карточка

### Журнал `product_actions`

Одна таблица на два дела: ожидающие действия и журнал всех действий
жизненного цикла (концепция, §12.3: аудит).

| Поле | Смысл |
|---|---|
| `id` uuid | |
| `user_id` text | владелец (TEXT: у входа по почте — UUID) |
| `product_id` uuid null | null у `create_bot` до создания |
| `kind` | `create_site`, `create_bot`, `keys`, `delete`, `restore`, `revert`, `purge` |
| `status` | `pending`, `done`, `failed`, `expired`, `cancelled` |
| `channel` | где действие заведено: `web`, `telegram`; `system` — суточное стирание |
| `confirmed_via` text null | где подтверждено: `chat`, `telegram`, `tma`, `cabinet` |
| `turn_nonce` text null | метка хода, в котором действие заведено |
| `payload` jsonb | имя, вид, `prompt`, ИМЕНА ключей, `turnId` — значений ключей нет никогда |
| `secrets_box` bytea null | новые ключи, зашифрованные тем же `SecretsService`; живут до конца задания и стираются |
| `result` jsonb | итог для карточки и ассистента, без значений ключей |
| `attached_at`, `tg_chat_id`, `tg_message_id` | куда прикреплена карточка (чтобы поправить сообщение в Telegram) |
| `created_at`, `expires_at`, `resolved_at` | |

Действия без карточки (`create_site`, `restore`, `revert`, `purge`)
пишутся сразу строкой `done`/`failed` — это журнал.

Карточка живёт 30 минут (`expires_at`). Отправка — один оператор
`UPDATE … SET status = … WHERE id = $1 AND user_id = $2 AND status = 'pending'
AND expires_at > now() RETURNING …`: двойное нажатие получает «уже сделано»,
опоздавшее — «срок вышел, попросите ассистента ещё раз».

### Как карточка попадает в чат

Карточку прикрепляет сервер; модель её не пишет и подделать не может.

1. **Метка хода.** Токен инструмента получает поле `turn` — случайная метка,
   выпускаемая на каждый ход: `productsRelayFields(userId, turn)` для релея,
   `signProductToolToken(userId, channel, turn)` для локального CLI. Точка
   `/webhook/mcp/products` передаёт метку в `execute`, действие ложится с
   `turn_nonce`.
2. **В конце хода** чат-сервис забирает ожидающие действия этого хода: по
   метке, а если её нет (релей принёс токен прошлого хода) — действия этого
   пользователя, заведённые за время хода и ещё не прикреплённые
   (`attached_at IS NULL`).
3. **Канал:**
   - веб и React-приложение — клиент объявляет `ui.cards` (рядом с
     `activity`/`ask` в `chat/client-ui.ts`). В поток уходит событие
     `{type:'product_action', id, kind}` — без текстовых полей, как у
     `activity`. В сохранённое сообщение дописывается блок
     ` ```product-action {"id":"…"} ``` `: после перезагрузки карточка
     рисуется в своём текущем состоянии;
   - Telegram — бот присылает отдельное сообщение. У `delete` — кнопки
     «Удалить» и «Отмена» (`pa:ok:<id>`, `pa:no:<id>`, разбор в
     `TgBotService.handleCallbackQuery` раньше проверки привязки, как у кнопок
     блога и «Затыков недели»; нажатие засчитывается, только если `from.id` —
     привязанный Telegram владельца действия). У ключей — кнопка, открывающая
     форму в мини-приложении (`/tma/`), вход там по `initData` → обычный токен
     доступа;
   - клиенты без `ui.cards` (Flutter) — к ответу дописывается строка со
     ссылкой `https://my.linkeon.io/studio?tab=products&action=<id>`.
4. **Кабинет.** Вкладка «Продукты» показывает ожидающие действия пометкой
   «ждёт подтверждения» и открывает карточку по `?action=<id>` — запасной путь
   на случай, когда карточка не прикрепилась (две вкладки, обрыв хода), и
   цель ссылки для Flutter.

### Ручки карточки

`JwtGuard`, владелец — из токена, чужое действие — 404 (не 403: не
выдавать существование).

- `GET /webhook/products/actions?status=pending` — для пометки в кабинете;
- `GET /webhook/products/actions/:id` — вид, продукт, ИМЕНА ключей,
  состояние, срок, итог;
- `POST /webhook/products/actions/:id`:
  - `delete` — `{confirm: true}`;
  - `keys` — `{set: {ИМЯ: значение}, remove: [ИМЯ]}`;
  - `create_bot` — `{set: {BOT_TOKEN: …, …}}`;
- `POST /webhook/products/actions/:id/cancel`.

Значения ключей проверяются теми же правилами, что при создании (имя
переменной, занятые платформой имена — три копии одной проверки, длина,
число), шифруются и дальше живут только в `secrets_box` и
`products.secrets_encrypted`. Ни в ответ, ни в журнал, ни в лог, ни в историю
чата они не попадают.

Поля ввода карточки — под классом скрытия от Вебвизора, с тестом, как у
остальных экранов с личным.

### Как ассистент узнаёт итог

Нажатие модель не видит. Итог показывает сама карточка («ключи обновлены, бот
перезапущен»; в Telegram бот правит сообщение с кнопками), а ассистент может
спросить `status` с идентификатором действия.

## Машина продуктов

- **Удаление** — существующее задание `sleep`. Предусловие выдачи сейчас не
  пускает архивные продукты (`p.archived_at IS NULL`, а `sleep` — только для
  `sleeping`/`blocked`): его надо расширить на удалённые. Если идёт правка,
  задание ждёт её тишины (`TURN_SILENCE_SQL`), как сон за неуплату.
- **Возврат** — существующее `wake`; погашенный администратором (`block_reason`
  не пуст) возвращается погашенным и не будится.
- **Ключи** — новое задание `rekey`: пересоздать контейнер с тем же образом
  (идентификатор образа живого контейнера), портами и каталогом; меняются
  только переменные ключей владельца. Старые имена уходят из окружения, новые
  приходят из задания (расшифровываются при выдаче, как у `provision`). После
  пересоздания — `/health` с `"ok":true`; не прошло — контейнер пересоздаётся
  со старым окружением, действие `failed`, ключи в базе прежние. Пока задание
  в очереди или идёт, новые правки не ставятся. Ключи спящему и погашенному
  продукту не меняются.
- **Стирание** — новое задание `purge`: `docker rm -f`, удаление каталога
  `/srv/products/<слаг>` (слаг сверяется со строгим шаблоном до любого `rm`),
  снятие настроек домена через `product-vhost`.

Код агента входит в образ продуктов (хеш содержимого `product-runner`), так
что выкат `rekey`/`purge` пересоздаёт все контейнеры продуктов — секунды на
каждый, живые правки не трогаются. Катить в тихое время, одним выкатом.

## Данные и деньги

- **Удаление:** `archived_at = now()`, `purge_after = now() + 30 дней`, статус
  `archived`. Место в пределе и аренда освобождаются сразу — их уже считают по
  `archived_at IS NULL`. Карточка (`pa_delete_prompt`) говорит прямо и
  безусловно: оплаченный период не возвращается — это общее правило удаления,
  а не утверждение про остаток у конкретного продукта. Ассистент (описание
  инструмента + свой `say()`) называет этот остаток иначе — см. правку ниже
  после производственной проверки.
- **Возврат:** только при свободном месте в пределе (та же проверка, что у
  создания, с тем же текстом отказа) и до `purge_after`. Снимаются
  `archived_at`/`purge_after`. Оплаченный период ещё идёт — `wake` сразу;
  кончился — как при неуплате: аренда списывается, а не хватает токенов —
  продукт спит до пополнения.
- **Стирание:** раз в сутки сервер ставит `purge` продуктам с
  `purge_after <= now()`. После задания: `secrets_encrypted = NULL`,
  `purged_at = now()`, строки своего домена удаляются, резервная копия
  `~/product-repos/<слаг>.git` (если есть) стирается сервером. Запись продукта
  с именем остаётся для журнала; слаг не переиспользуется.
- **Токен бота у двух продуктов.** При создании бота и при смене `BOT_TOKEN`
  сервер проверяет токен в Telegram (`getMe`) и записывает идентификатор бота
  (`products.tg_bot_id`, не секрет). Тот же бот у другого живого продукта —
  отказ: два продукта на одном токене отнимают друг у друга обновления.
- **Владелец бота.** Если Telegram пользователя привязан
  (`tg_user_identities`), бот при заведении получает `OWNER_TG_ID` в
  окружение — платформенная переменная рядом с `RUNNER_TOKEN`, в списке
  занятых имён. Каркас (`skeleton.ts`) говорит ассистенту правок: владелец —
  `OWNER_TG_ID`. Без привязки — нынешнее правило, но первая сборка обязана
  отвечать на `/start` chat_id и подсказкой, что с ним делать.

## Тексты ассистенту

Описание `manage_product` и `NO_PRODUCTS_SAY` переписываются: убрать «завести,
погасить, передать ключи — не можешь», добавить новые действия и правила:

- до `create` назвать цену и предел и получить согласие;
- ключи в разговоре не просить никогда; прислал ключ в чат — никуда его не
  передавать, предложить карточку `keys`;
- удаление — только карточкой; «удалил» не говорить, пока действие не `done`;
- о карточке говорить «под ответом карточка» (в Telegram — «ниже сообщение с
  кнопкой»), не выдумывая её содержимое;
- после удаления называть дату, до которой можно вернуть.

Тексты, где сказано, что ассистент продукты не создаёт и не удаляет —
`chat/platform-guide.ts`, справка кабинета, статьи `linkeon_help`, — сверить
грепом и поправить в той же очереди.

Тексты карточек — на всех языках кабинета, мини-приложения и бота.

## Ошибки и краевые случаи

- Предел занят — тот же отказ, что у кнопки в Студии («предел — 2 продукта…
  напишите нам»); нет места на машине — существующий отказ.
- `getMe` не прошёл — ошибка на месте в карточке, ничего не создано.
- Удаление во время правки — архив ставится сразу (новые правки уже не
  принимаются), гашение контейнера ждёт конца хода.
- Действие над чужим или стёртым продуктом — тот же ответ, что «нет такого».
- Возврат после стирания — «продукт уже стёрт».
- Текст на сайте, в файле или в пересланном сообщении не может ничего
  удалить и ничего не узнает о ключах: удаление — только кнопкой владельца,
  ключи — только из формы.

## Тесты

- Сервис действий: переходы состояний, двойная отправка, срок, чужой
  пользователь, отмена.
- Новые действия инструмента; прикрепление карточки по метке и запасным путём;
  строка-ссылка для клиента без `ui.cards`.
- Кнопки Telegram: только владелец, только `pending`.
- Значения ключей не попадают в историю чата, журнал, лог и ответы — отдельный
  тест с нарочно узнаваемым значением.
- Предусловия выдачи `sleep`/`wake`/`purge` для удалённых.
- Агент: `rekey` и `purge` на поддельном Docker, как уже тестируется агент;
  откат `rekey` при упавшем `/health`; `purge` не трогает путь вне
  `/srv/products/<слаг>`.
- Test-стенд вживую: сайт создан ассистентом, удалён, возвращён; бот создан
  через карточку, ключи сменены. Затем прод тестовым аккаунтом.

## Очереди выката

1. **Без изменений агента машины** (контейнеры не пересоздаются): журнал и
   карточки во всех каналах, `create` (сайт и бот), `revert`, `delete` и
   `restore` на `sleep`/`wake`, кабинет (`?action=`, пометка), тексты.
2. **С агентом машины, одним выкатом:** `rekey` и действие `keys`, `purge` и
   суточный обход, `OWNER_TG_ID` и текст каркаса. До второй очереди
   удалённые продукты просто ждут стирания — обход подберёт их задним
   числом.

## Соответствие концепции

- **§12.3, полномочия агентов.** Ассистент действует только в границах
  продуктов владельца токена. Деньги называются до действия; необратимое
  делается только кнопкой человека; каждое действие — строка журнала
  `product_actions`; удаление 30 дней обратимо.
- **§1 и §4.2.2, облако — исполнитель без состояния, сервер — слепое реле.**
  Ключи не проходят через облачную модель вовсе: карточка отправляет их
  прямо на сервер, хранятся они только зашифрованными, модель видит одни
  имена.
- **Честные формулировки.** «Удалён, можно вернуть до …», а не «удалён
  навсегда», пока продукт не стёрт; «ключи обновлены» — только после
  успешного `rekey`.

## Вне рамок

- Свои кнопки «Ключи» и «Удалить» в карточке продукта в кабинете: кабинет
  только показывает и подтверждает действия, заведённые ассистентом.
- Пауза продукта по желанию владельца (сон бывает только за неуплату и по
  блокировке).
- Переименование, смена вида, перенос на другую машину.
- Карточки во Flutter-приложении (там ссылка на кабинет).
- Возврат денег за оставшийся период при удалении.
- Поднятие предела продуктов — по-прежнему через поддержку.

## Отступления очереди 1 (по ходу исполнения, 25–26.10.2026)

Спека выше — как задумано; здесь — что сделано иначе и почему. Код — источник правды.

**Карточка и ручки**
- Ручки — `/webhook/product-actions` (список ожидающих, без `?status`), `GET|POST /webhook/product-actions/:id`, `POST …/:id/cancel`: свой префикс, чтобы не спорить с маршрутами `products/:id/…`. Чужое — 404.
- Состояние `working` между `pending` и исходом: «двойное нажатие — один раз» держит один UPDATE с условием на `pending`. Зависшие `working` (процесс умер между захватом и исходом) через 10 минут после срока уходят в `failed` — сборщик раз в минуту.
- Поправимые ошибки (Telegram не принял токен, не ответил, бот уже в другом продукте, неверное имя ключа) возвращают карточку в `pending` с `result.error`, а не в `failed`: человек правит в той же карточке.
- POST по записи журнала (`create_site`, `restore`, `revert`, `purge`) — 409 «это не карточка»; `keys` — 501 (очередь 2).
- Отправок карточки — не больше 20 за 10 минут на человека: каждая отправка бота зовёт `getMe` Telegram с нашего адреса.
- Удаление продукта, который ещё заводится, — отказ; возврат, пока у продукта идёт задание, — отказ.

**Как карточка доходит до ответа**
- Отдельного события потока нет: сервер дописывает блок ```product-action``` к ответу обычным куском текста, он же ложится в историю. Карточка прикрепляется и когда поток релея оборвался после вызова инструмента.
- Блоки, написанные моделью, сервер вырезает до того, как допишет свои (терпимо к небрежной форме), фронт узнаёт только точную форму сервера и не показывает один id дважды.
- Метка хода едет в подписи токена инструмента полем `turn` рядом с полями справки (`lang`, `client`, `scope`, `agent`).
- Ход загрузки файла получает инструмент без метки: карточка такого хода есть только в кабинете, и ответ инструмента говорит модели именно это.

**Бот и Telegram**
- Один бот — в одном живом продукте: частичный уникальный индекс `products_tg_bot_live`, `tg_bot_id` пишется в той же вставке, что заводит продукт. Возврат удалённого, чей бот тем временем работает в другом продукте, — отказ.
- Кнопка мини-приложения ведёт на `/tma/?pa=<id>` (строка запроса; фрагмент `#pa=` тоже понимается): Telegram дописывает во фрагмент свои параметры.
- Итог нажатия — на языке профиля владельца, причины отказа — своими текстами на семи языках; повторное нажатие показывает фактический исход; карточка уходит и тогда, когда ход упал.

**Прочее**
- Сон удалённых раз в минуту ещё и доснимает застрявшие в очереди задания архивного продукта (иначе они вечно загораживают сон).
- Справка ассистентов (статья «Продукты») и промпт продуктов CLI (Маша, TG-бот) знают создание, удаление, возврат и откат; числа — из констант.

**Решения и правки после итогового ревью (26.10.2026)**
- Бесплатный первый месяц — только первым двум продуктам человека за всё время, удалённые тоже считаются (решение владельца 26.10: иначе «удалить → завести заново» давало бесплатные месяцы без конца). Не считаются продукты, заведение которых сорвалось (задание `provision` провалено); заводящийся продукт уже считается — иначе пока он заводится, выдавались бы лишние месяцы. Срок оплаты считается в той же вставке, что заводит продукт; инструмент говорит модели, сколько бесплатных месяцев осталось, и итог создания — достался ли месяц. Платный с первого дня продукт списывается ТЕМ ЖЕ тактом, что переводит его в running (`promoteReady` → `RentService.chargeOnStart`), а не следующим суточным оборотом аренды — см. правки ниже после производственной проверки.
- Продукт, остановленный администратором, ассистент не удаляет — только поддержка: иначе удаление освобождало бы место в пределе и обходило блокировку. Блокировка, наложенная пока карточка ждёт нажатия, тоже останавливает удаление.
- Студия тоже проверяет токен бота в Telegram при заведении: отвергнутый — отказ, занятый другим живым продуктом — отказ; Telegram недоступен — заводится без отметки бота. Отметка бота у уже живущих ботов досчитывается раз в 10 минут (колонка `tg_bot_checked_at`); два живых продукта с одним ботом — предупреждение в лог, без токена.
- Сон удалённого продукта после трёх неудач не ставится заново. Удаление снимает и стоящие в очереди правки продукта. Возврат — одной транзакцией с замком на строке продукта, задания продукта — без ожидания (`NOWAIT`: занято — «попробуйте через минуту», иначе обратный порядок замков с отчётом агента); продукт, удалённый в состоянии «не завёлся», возвращается в него же, без аренды. Отказы возврата и отката пишутся в журнал.
- Карточка бота не открывается, если предел продуктов уже исчерпан.
- После подтверждения в кабинете список продуктов перечитывается.

**Три правки после производственной проверки (26.10.2026, одобрено владельцем)**
- Первая аренда списывается СРАЗУ при переходе продукта в running (заведение или пробуждение), а не ждёт следующего суточного `RentService.tick()`: без неё платный с первого дня продукт работал бесплатно до тика, а «создать → удалить до тика» было бесплатным хостингом навсегда. Зовёт списание `promoteReady` через новый `RentService.chargeOnStart` — это единственное место, где продукт переходит в `running` С начислением аренды; второй переход туда же — из `degraded` в `touchRunner` (`turns.service.ts:357`), heartbeat после пропущенных отметок, — chargeOnStart не зовёт: продукт всё это время оставался `running`/`degraded` для `tick()` и аренду с него и так берёт суточный оборот, а не старт. `chargeOnStart` безопасен звать и для бесплатного месяца, и для уже оплаченного периода: его собственные предусловия (те же, что у `tick()`) просто не находят, что списывать. На старте якорь даты — ВСЕГДА `now()` (`anchorRentNow`/`chargeRent(id, true)`), а не «от занятого срока», как у суточного тика: иначе продукт, проспавший меньше месяца, платил бы за остаток старого месяца, а не за полный новый (ревью, 26.10).
- Честный возврат: если у удалённого продукта оплаченный период истёк, но баланс владельца покрывает аренду, `restore()` сам ставит пробуждение, не дожидаясь подметальщика, и не пишет причину сна «не хватило токенов» — она была бы неправдой; если старая причина сна («Не хватило токенов») лежала с прошлого раза, баланс, которого теперь хватает, её снимает (ревью, M1). Текст инструмента называет ТРИ случая, не два: оплаченный период ещё идёт — «просыпается, срок до <дата> продолжается» (аренда уже оплачена, списывать нечего); период истёк, но денег хватает — «просыпается, аренда спишется при запуске»; денег не хватает — «спит, на аренду нужно N, на балансе M» (ревью, I1/M7).
- Перед открытием карточки ассистент упоминает невозвратный остаток оплаченного срока, только если он реально есть (`paid_until` ещё в будущем — бесплатный месяц или уже оплаченный период); у продукта, которому и так уже пора платить аренду, ассистент эту фразу не произносит. Сама карточка (`pa_delete_prompt`) остаётся безусловной — см. правку базового абзаца выше.

**Открыто на очередь 2**
- Стирание (`purge`) обязано только помечать `purged_at`, не удаляя строку `products`: задания удаляются каскадом, и счёт бесплатных месяцев сбросился бы.
- Удалённый продукт, у которого сон трижды не прошёл, может работать до стирания (бот — отвечать); сигнал — строка ошибки в логе.
- Тексты инструмента о деньгах уходят и в сборку из магазина приложений: инструмент не различает `client=store`.
- Flutter, открыв историю веб-хода, покажет блок карточки кодом: ручке истории нужно превращать блок в ссылку на кабинет для клиентов без карточек.
- Фронт не заменяет текст ответа на `end.content`: блок, скопированный моделью с чужим или старым id, виден до перезагрузки (тот же id не задвоится).
- Тексты поправимых ошибок (`result.error`) — по-русски на всех языках.
- В Telegram-группе карточка бота ведёт ссылкой в кабинет — тупик для аккаунтов только из Telegram; подумать о прямой ссылке на мини-приложение.
- Самолечение пустого потока теоретически может открыть вторую карточку.
