# Озвучка ответов ассистентов — Фаза 3 (Flutter) — дизайн

**Дата:** 2026-08-07
**Статус:** утверждён, готов к планированию
**Родительский дизайн:** `2026-08-06-assistant-tts-design.md`
**Репозиторий реализации:** `~/Downloads/linkeon_mobile` (отдельный git, релиз через сторы)

## Задача

Показать в мобильном приложении аудио, которое ассистент создаёт инструментом
`generate_speech`. Бэкенд и веб (Фаза 1) уже в проде и работают; мобилке нужно
только проиграть готовый клип.

Фаза 2 (Telegram) сознательно пропускается — её ценность под вопросом.

## Что уже готово на бэкенде

Ничего дописывать не нужно, контракт закрыт Фазой 1:

- ассистент вызывает `generate_speech`, клип пишется в `speech_clips`, токены списываются;
- после стрима бэкенд сам дописывает в текст ответа маркер `{{audio:id=<uuid>}}` —
  структурных событий об инструментах в этом пути нет, поэтому маркер приходит
  обычным текстом и одинаково доступен всем клиентам;
- маркер попадает в сохранённую историю, то есть виден и при повторном открытии чата;
- `GET /webhook/speech/:id` отдаёт `{ id, url, durationSec, chars, voice, provider, lang, createdAt }`,
  фильтруя по владельцу; чужой клип получить нельзя.

Выбор голоса в мобилке не делаем: он хранится в общем `profile_data.assistant_voices`,
назначается в вебе и применяется на бэкенде. Мобильному клиенту достаточно проиграть
то, что пришло.

## Решения

| Решение | Выбор | Причина |
|---|---|---|
| Пакет воспроизведения | `just_audio` | профильный пакет: стриминг по URL, буферизация, перемотка и длительность из коробки |
| Где рисуем | карточка под сообщением | тем же способом, что уже рисуются карточки SMM-роликов и сценариев |
| Объём | только плеер | голос назначается в вебе, профиль общий |

Отклонённые варианты: `audioplayers` (проще API, но состояние загрузки и прогресс
пришлось бы собирать руками); переиспользование `video_player`, который уже в
`pubspec` (ноль новых зависимостей, но это видео-плеер — нет аудио-сессии, на iOS
такое обычно оборачивается молчанием в бесшумном режиме).

## Архитектура

Четыре файла, каждый с одной задачей:

| Файл | Ответственность |
|---|---|
| `lib/models/speech.dart` | чистая `extractAudioClipIds(text)` — разбор маркера |
| `lib/services/speech_service.dart` | `fetchClip(id)` → `GET /webhook/speech/:id` |
| `lib/widgets/audio_clip_card.dart` | карточка плеера: play/pause, прогресс, время, ошибки |
| `lib/widgets/chat_markdown.dart` | вызов извлечения и отрисовка карточек (правка) |

Поток данных:

```
текст ответа с {{audio:id=<uuid>}}
  → extractAudioClipIds(СЫРОЙ текст) отдаёт список id
  → stripCustomTags() убирает маркер из текста, который пойдёт в разметку
  → под сообщением рисуется AudioClipCard на каждый id
  → карточка запрашивает GET /webhook/speech/:id
  → just_audio играет url
```

**Порядок обязателен: извлекаем из сырого текста, до `stripCustomTags`.** Если
извлекать из уже очищенного, список всегда будет пустым, и симптом окажется точно
таким же, как если бы извлечения не было вовсе, — то есть никаким. Существующая
`extractSmmRefs` вызывается именно так (`chat_markdown.dart:41`, до очистки), новый
вызов ставится рядом с ней.

`extractAudioClipIds` зеркалит уже существующую `extractSmmRefs`
(`lib/models/smm.dart:196-214`): та же форма, тот же стиль регулярки
`\{\{audio:id=([a-f0-9-]{36})\}\}`, порядок появления сохраняется, дубликаты не
отсеиваются.

## Три ловушки, заложенные в дизайн явно

**1. Зачистка маркеров съедает наш тег молча.**
`ChatMarkdown.stripCustomTags` (`lib/widgets/chat_markdown.dart:121`) заканчивается
строкой `out.replaceAll(RegExp(r'\{\{[^}]*\}\}'), '')` — вырезает любые фигурные
теги, которые мобилка не умеет рисовать. Это правильное поведение по умолчанию, но
для нас означает: забудем извлечение — маркер исчезнет без ошибки, без пустого места
и без единого следа в логах. Пользователь увидит текст ответа и никогда не узнает,
что к нему прилагалось аудио, за которое он заплатил.

Отсюда требование к тесту: проверять не «регулярка совпала», а «из текста с маркером
получилась карточка». Тест, удостоверяющий только регулярку, эту ловушку пропустит.

**2. `AppLocalizations.of(context)` в `initState` роняет прод.**
Карточка грузит метаданные клипа при инициализации, и соблазн взять там же подписи
велик. Нельзя: вызов локализации из методов, дёргаемых в `initState`, падает, и на
это в репозитории уже стоит сторож `tool/check_initstate_l10n.mjs`. Все тексты
берутся только в `build`.

**3. Забытый перевод ломает сборку, а не «переведём потом».**
В `l10n.yaml` задан `untranslated-messages-file`, источник правды — `app_ru.arb`.
Новые ключи добавляются сразу во все шесть локалей (`ru`, `en`, `es`, `de`, `fr`, `zh`),
осмысленными переводами, а не копиями русского. Второй сторож — `tool/check_arb.mjs`
(покрытие, подстановки, ICU-формы).

## Состояния карточки

| Состояние | Что показываем |
|---|---|
| загрузка метаданных | скелетон, без текста |
| готово | кнопка play/pause, прогресс, `текущее / общее` время |
| воспроизведение | та же карточка, кнопка в состоянии pause, прогресс идёт |
| клип не найден (404) или сеть | короткое локализованное сообщение вместо плеера |
| ошибка самого аудио | то же сообщение — битый файл не должен оставлять мёртвую кнопку |

Длительность берём из `just_audio` по факту загрузки; `durationSec` из API — только
предварительная оценка (бэкенд считает её по числу символов, провайдеры точную
длительность не возвращают).

Скачивание файла в мобилке не делаем: на телефоне это не тот жест, что в вебе, и
тянет за собой разрешения на запись.

## Тестирование

Юнит-тесты на `extractAudioClipIds`:

- валидный маркер в тексте, в начале и в конце строки;
- несколько маркеров подряд — порядок сохраняется;
- мусорный id (короткий, верхний регистр, нелатиница) не распознаётся;
- соседние маркеры `{{smm_video:…}}` и `{{smm_scenario:…}}` не захватываются.

Виджет-тест: сообщение с маркером рождает `AudioClipCard`; сообщение без маркера —
не рождает. Это и есть защита от ловушки №1.

**Каждый тест проверяется в обе стороны.** Сузить маску id — тесты обязаны покраснеть.
Убрать вызов извлечения в `chat_markdown.dart` — виджет-тест обязан покраснеть.
Зелёный прогон сам по себе ничего не доказывает: в этом проекте уже были и
ложно-зелёные тесты, и тест, который пережил полное отключение проверяемой логики.

## Что в фазу не входит

- выбор голоса в мобилке — профиль общий, голос назначается в вебе;
- кнопка «озвучить» у произвольного сообщения — сейчас озвучка возможна только как
  вызов инструмента ассистентом, отдельного эндпоинта для этого нет;
- фоновое воспроизведение, экран блокировки, очередь клипов;
- Telegram (Фаза 2).

## Релиз

Мобилка едет через сторы, отдельно от `deploy.sh`. Бэкенд её не ждёт: маркеры уже
приходят в ответах, просто до выхода сборки мобильные пользователи их не увидят —
`stripCustomTags` их вырезает, то есть деградация тихая и безопасная.
