# Говорящий аватар ассистента в звонках и встречах

Дата: 07.09.2026. Статус: задание на реализацию.

Часть I написана так, чтобы её можно было переслать стороннему разработчику
целиком, без доступа к нашим репозиториям: она самодостаточна. Части II и III —
наша сторона работы, подрядчику они нужны только как контекст.

## Зачем

Ассистент (Роман и другие) уже входит в голосовую комнату полноценным
участником и говорит. Но он входит **без видео**, поэтому в интерфейсе
собеседников выглядит как пустая плитка с именем. У этого две беды:

1. Никто не понимает, что происходит. Молчащий ассистент неотличим от
   сломавшегося, а пауза, пока он уточняет ответ у коллеги-специалиста,
   доходит до минуты.
2. На встрече с людьми он визуально отсутствует — участники забывают, что он
   вообще здесь, и не обращаются к нему.

Лечится тем, что ассистент публикует видеодорожку: портрет с индикатором
состояния. Оба клиента, где это в первую очередь нужно (веб-комната и мобильное
приложение), уже умеют показывать видео участников, поэтому картинка появится
у них **без правок на их стороне и без релиза мобильного приложения**.

Фотореалистичный липсинк в этой работе не делается — см. «За рамками».

# Часть I. Пакет `linkeon-avatar-video`

Это то, что делает подрядчик. Отдельный репозиторий, отдельные тесты, своя
версия. В наш код голосовой сессии заходить не нужно и не следует.

## 1. Что это

Библиотека на TypeScript для Node.js, которая рисует кадры «говорящего
аватара»: круглый портрет, индикаторное кольцо вокруг него и подпись.

Библиотека **ничего не знает** о том, куда эти кадры пойдут. Она не открывает
сокетов, не ходит в сеть, не заводит таймеров и не читает системное время. Ей
говорят: «состояние — говорит, громкость — 0.7, момент времени — 1234 мс», она
возвращает массив пикселей. Всё остальное — забота вызывающей стороны.

Это ограничение не стилистическое. Сегодня кадры публикует наш голосовой
воркер; позже тот же рендерер должен переехать в отдельный сервис рядом с
липсинком, и переезд обязан быть заменой десятка строк вызывающего кода, а не
переписыванием пакета.

## 2. Публичный интерфейс

```ts
export type AvatarState =
  | 'listening'   // молчит, готов ответить
  | 'speaking'    // говорит
  | 'thinking'    // думает или ждёт ответа коллеги
  | 'muted';      // режим слушателя: попросили молчать

export interface AvatarIdentity {
  /** Имя в кадре: «Роман». Обязательно. */
  name: string;
  /** Роль под именем: «бизнес-ассистент». Может отсутствовать. */
  role?: string;
  /** Портрет: PNG, JPEG или WebP, любого размера и пропорций. Может отсутствовать. */
  portrait?: Buffer;
  /** Акцентный цвет колец и плашки, '#RRGGBB'. По умолчанию — фирменный. */
  accent?: string;
}

export interface AvatarRendererOptions {
  /** Ширина кадра, по умолчанию 640. */
  width?: number;
  /** Высота кадра, по умолчанию 360. */
  height?: number;
}

export class AvatarRenderer {
  /** Асинхронно: декодирует портрет и готовит шрифты. */
  static create(
    identity: AvatarIdentity,
    options?: AvatarRendererOptions,
  ): Promise<AvatarRenderer>;

  readonly width: number;
  readonly height: number;

  /** Сменить состояние. `detail` — уточнение под ролью, например «уточняю у Анны». */
  setState(state: AvatarState, detail?: string): void;

  /** Текущая громкость речи, 0..1. Значения вне диапазона зажимаются. */
  setLevel(level: number): void;

  /**
   * Отрисовать кадр на момент `nowMs` (миллисекунды, монотонные, задаёт
   * вызывающая сторона). Возвращает RGBA, длина width * height * 4.
   * Буфер можно переиспользовать между вызовами — вызывающий обязан
   * скопировать данные, если ему нужно их сохранить.
   */
  render(nowMs: number): Uint8Array;
}
```

Ничего сверх этого наружу не требуется. Внутреннее устройство — на усмотрение
разработчика.

## 3. Что должно быть в кадре

Кадр 640×360 (16:9) — пропорция, в которой плитку участника показывает
большинство интерфейсов. Фон непрозрачный, тёмный.

**Безопасная зона.** Клиенты кропают плитку по-разному: квадратом в сетке
участников, вертикально на телефоне. Поэтому всё значимое — портрет, имя, роль,
подпись состояния — обязано умещаться **в центральный квадрат 360×360**. За его
пределами допустим только фон. Проверяется тестом: кроп кадра до квадрата и до
4:3 не срезает ни портрета, ни текста.

Композиция внутри безопасной зоны:

- круглый портрет, диаметр примерно 0.5 стороны квадрата, центр чуть выше
  геометрического центра;
- индикаторное кольцо вокруг портрета с небольшим зазором;
- под портретом имя — крупно, полужирным;
- под именем роль — мельче, приглушённо;
- при наличии `detail` — третья строка ещё мельче.

Текст, который не влезает по ширине, обрезается многоточием. Кегль имени
задаётся долей от стороны кадра, а не в абсолютных пикселях: плитка на телефоне
в сетке из пяти участников бывает шириной 160 логических точек, и подпись обязана
остаться читаемой.

Портрет любых пропорций вписывается в круг кропом «по заполнению», без
искажения лица.

**Нет портрета, портрет не декодировался или пришёл битый буфер** — рисуются
инициалы на плашке акцентного цвета. Падать нельзя: отсутствие картинки не
должно ломать звонок.

## 4. Состояния

| Состояние | Как выглядит | Зачем |
|---|---|---|
| `speaking` | кольцо пульсирует по громкости, акцентный цвет | видно, что говорит именно он, а не сосед |
| `listening` | ровное тонкое кольцо | «здесь, слушает» |
| `thinking` | бегущая по кольцу дуга, третья строка с `detail` | пауза до минуты перестаёт выглядеть зависанием |
| `muted` | кольцо погашено, приглушённый портрет, подпись «слушает молча» | его попросили не вмешиваться — участники должны это видеть |

Реакция кольца на громкость сглаживается внутри пакета: быстрый подъём
(порядка 30 мс), медленный спад (порядка 200 мс). Без сглаживания кольцо
дёргается покадрово и выглядит как помеха, а не как речь.

Анимация — функция от переданного `nowMs`. Собственного времени пакет не
читает.

## 5. Жёсткие ограничения

Это условия приёмки, а не пожелания.

- **Зависимости.** Разрешён `@napi-rs/canvas` (нативный, с готовыми бинарями
  под linux-x64, без системных библиотек). Запрещены: любые пакеты
  `@livekit/*`, клиенты LLM, `canvas` (тянет cairo, ставится через apt —
  на наших серверах это неприемлемо).
- **Никакой сети и файловой системы** в рантайме. Портрет приходит буфером.
  Шрифт лежит внутри пакета и регистрируется из его же каталога.
- **Никаких таймеров.** Ни `setInterval`, ни `setTimeout`. Частоту кадров
  задаёт вызывающая сторона.
- **Никакого системного времени и случайности.** Ни `Date.now()`, ни
  `Math.random()`. Последовательность вызовов `render()` с одними и теми же
  аргументами обязана давать побайтово одинаковые кадры — на этом держатся
  тесты.
- **Шрифт с кириллицей внутри пакета** (например Noto Sans под OFL).
  Полагаться на системные шрифты нельзя: на сервере их может не быть вовсе, и
  «Роман · бизнес-ассистент» превратится в прямоугольники. Лицензию шрифта
  положить в репозиторий.
- **Node 20+, ESM, TypeScript.**

## 6. Производительность

Бюджет — **не более 3 мс на кадр** при 640×360 на одном ядре x86-64. При 15
кадрах в секунду это меньше 5% ядра; в комнате может идти несколько встреч
одновременно на одной машине.

Замер оформить тестом: отрисовать 200 кадров подряд, проверить медиану.

## 7. Тесты

Тесты на `node:test` (`node --test` / `tsx --test`), без браузера и без
внешних сервисов. Обязательный минимум:

1. Детерминизм: две одинаковые последовательности вызовов дают одинаковые
   байты.
2. Размер и формат буфера: `width * height * 4`, RGBA.
3. Безопасная зона: при кропе до квадрата и до 4:3 портрет и обе строки текста
   целиком внутри.
4. Состояния различимы: кадры `speaking` при уровне 0.9 и `listening`
   отличаются в области кольца; `muted` отличается от обоих.
5. Громкость влияет на кольцо: уровень 0.1 и 0.9 дают разную толщину/яркость.
6. Сглаживание: после резкого падения уровня с 1.0 до 0 кольцо гаснет не
   мгновенно, а за несколько кадров.
7. Нет портрета → инициалы, не исключение.
8. Битый буфер портрета → инициалы, не исключение.
9. Длинные имя и роль обрезаются многоточием и не вылезают за безопасную зону.
10. Кириллица рисуется: кадр с именем «Роман» отличается от кадра с именем
    «Пётр» (то есть текст реально отрисован, а не съеден отсутствующим
    шрифтом).
11. Бюджет времени из пункта 6.

## 8. Что сдаётся

- Репозиторий с исходниками, тестами и README, где описан интерфейс и приведён

- Набор эталонных PNG: по одному кадру на каждое из четырёх состояний, плюс

  согласовать вид.
- Тег версии.

# Часть II. Интеграция в голосовой воркер

Делаем мы, подрядчику не передаётся. Здесь — чтобы был виден контекст и объём.

Воркер (`spirits_back/voice-host`) добавляет тонкий адаптер, порядка сорока
строк:

- создаёт `AvatarRenderer` при старте сессии, портрет скачивает по ссылке из
  задания на запуск;
- тикает `render()` и отдаёт кадры в `VideoSource.captureFrame(new VideoFrame(rgba, w, h, VideoBufferType.RGBA))`,
  публикуя дорожку через `LocalVideoTrack.createVideoTrack` с
  `TrackSource.SOURCE_CAMERA` в `stage = foreign ?? ctx.room`
  (`voice-host/src/agent.ts:598`). API проверен в установленном
  `@livekit/rtc-node`;
- частота: 15 кадров в секунду во время речи, 5 в покое;
- публикация ленивая и ровно одна — зеркалит защиту, уже стоящую в
  `voice-host/src/external-room-output.ts`;
- любая ошибка внутри тика гасится и логируется: сломанный рендер не имеет
  права уронить голосовую сессию.

Состояния берутся из того, что уже есть:

| Что | Откуда |
|---|---|
| `speaking` / `listening` / `thinking` | событие `AgentStateChanged`, уже слушается в `agent.ts` |
| `muted` | флаг режима слушателя в `voice-host/src/name-gate.ts` |
| `detail` («уточняю у Анны») | `voice-host/src/pending.ts` — имя специалиста лежит там |
| громкость | RMS по кадрам аудиовыхода |

Про RMS: в `voice-host/src/mixer.ts` уже есть отлаженный расчёт огибающей по
входящему звуку участников — для исходящего звука ассистента берём тот же
подход, а не пишем третий.

**Открытый пункт, решается при реализации.** В чужих комнатах кадры исходящего
звука проходят через наш `ExternalRoomAudioOutput`, и громкость там доступна
даром. В наших собственных комнатах звук уходит штатным выводом SDK, и доступа
к кадрам нет. Либо обёртка-декоратор над стандартным выводом, либо на время
`speaking` кольцо анимируется синтетической огибающей. Разница для глаза
невелика, выбирать по факту.

Бэкенд (`src/meeting/meeting.service.ts:186` и то же место для звонков)
добавляет в задание на запуск два поля: ссылку на портрет — существующий
`GET /webhook/0cdacf32-…/agent/avatar/:agentId` — и роль ассистента для подписи.

## Выбор «с аватаром или без»

Два независимых рубильника:

1. Поле в задании на запуск воркера — решает бэкенд для каждого звонка или
   встречи отдельно.
2. Переменная окружения воркера — отключает аватар на всём стенде без релиза.

Выключено — поведение ровно сегодняшнее: аудио без видео. Это обязательное
требование, а не удобство: мы публикуем дорожку в чужой продукт, и способ
выключить её за минуту должен существовать.

## За рамками

- Липсинк и фотореалистичная говорящая голова. Для них рендерер переезжает в
  отдельный сервис-участник, который публикует и звук, и видео — иначе
  синхронизации не добиться. Интерфейс пакета из части I этот переезд
  переживает без изменений, но сам переезд в объём не входит.
- Zoom, Google Meet, Телемост. Мост туда через безголовый браузер — отдельная
  работа, описанная в `docs/meeting-bot.md`. Рендерер там переиспользуется.
- Аватары для других продуктов. Пакет к этому готов, но интеграция — их
  сторона.

## Открытые вопросы

1. **Вид кадра согласовать по эталонным PNG** до того, как он поедет в чужие
   комнаты: цвет фона и акцента, шрифт, формулировка подписи в режиме
   слушателя.
2. **Громкость в наших комнатах** — см. открытый пункт в части II.
3. **Портреты специалистов.** Эндпоинт отдаёт аватар по id ассистента, но
   пригодность каждой картинки для круглого кропа 180×180 никто не проверял.
   Посмотреть глазами до запуска; где плохо — перерисовать.
