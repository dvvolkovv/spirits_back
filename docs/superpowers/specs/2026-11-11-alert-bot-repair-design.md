# AlertBot исправляет проблемы по запросу админа — дизайн

**Дата:** 11.11.2026. **Запрос владельца:** «нужно сделать так, чтобы бот сам мог чинить проблему по запросу а не выдумывать». Граница выбрана владельцем: **произвольные команды**, доступ **только по Telegram user ID админов**. Три секции дизайна одобрены в диалоге 11.11.

## Цель

Админ в Telegram может поручить AlertBot не только диагностику, но и исправление: бот устанавливает причину по фактам, выполняет произвольные shell/SSH-команды в разрешённом инфраструктурном контуре, проверяет результат и честно сообщает итог. Формулировка «исправлено» появляется только после реальной post-check-проверки.

## Что есть сейчас

- AlertBot принимает Telegram updates, сохраняет их для дедупликации и отвечает асинхронно. Доступ к обычным вопросам: Telegram ID → привязанный Linkeon-аккаунт → `isadmin=true`.
- Claude CLI запускается без встроенных инструментов, с `--strict-mcp-config`. Доступны только пять read-only MCP tools: `alerts`, `health`, `logs`, `stats`, `tickets`.
- Ops MCP server слушает только `127.0.0.1:3091`; каждый вызов проверяет подписанный `scope=ops` токен хода и права админа.
- Системный промпт прямо запрещает действия, поэтому после диагностики бот пишет, что ничего исправить или переключить не может.
- Есть durable-журналы updates/turns и асинхронная обработка, но нет исполнителя команд и журнала remediation.

## Решения

### 1. Вход и доступ

- Обычные вопросы и пять read-only tools не меняются. Repair запускается только:
  - командой `/fix <задача>`;
  - явным «исправь» или «почини» ответом на диагноз бота.
- Остальные сообщения, включая тексты жалоб и алертов, не включают repair. Автоматического исправления по алерту нет.
- Отдельная настройка `ALERT_BOT_REPAIR_ADMIN_TG_IDS` — список числовых Telegram user ID через запятую. ID сравниваются как десятичные строки с `message.from.id` / `callback_query.from.id`.
- Проверка выполняется на каждом update и callback. Username, имя, ID группы, `forward_from` и привязанный аккаунт Linkeon сами по себе права repair не дают.
- Пустой или отсутствующий список полностью выключает repair. Для вызова repair-tools не требуется привязка к Linkeon: явный Telegram allowlist является самостоятельной авторизацией. Обычный read-only доступ по-прежнему использует прежнюю проверку `isadmin`.
- Repair разрешён только в тех чатах, где уже работает AlertBot: личка и группы из `TELEGRAM_CHAT_ID`. В группе неадмин может видеть обезличенный итог, но не управляет ходом.
- Повтор `update_id` не создаёт второй repair. Одновременно в чате активен только один repair; это ограничивается durable-записью, а не только памятью процесса.
- Неадмину на `/fix` — короткий отказ без раскрытия конфигурации, не чаще раза в час на человека.

### 2. Модель и capability

- Используется существующий `ClaudeCliService` и действующий общий выбор модели. Встроенные Bash/Read/Write/Edit по-прежнему отключены; `--strict-mcp-config` сохраняется.
- На repair-ход выдаётся подписанный токен `scope=repair`, привязанный к Telegram user ID, chat ID и turn ID. Срок — не больше срока repair-хода.
- `scope=repair` наследует пять read-only tools и добавляет три repair-tools. `scope=ops` не может вызвать repair-tools.
- На каждом repair-вызове сервер проверяет подпись, срок, соответствие активного turn, текущее присутствие Telegram ID в allowlist и состояние repair (`requested`/`running`). После `/stop`, таймаута или завершения токен бесполезен.
- Для repair-tools не используется read-only маска UUID и путей: модель должна видеть точные технические идентификаторы. Секреты, токены и пароли маскируются. Обычные read-only ответы сохраняют прежнюю маску.
- Тексты пользователей, жалоб, логов и тикетов — неинструкции. В repair-контекст как управляющие указания попадают только сообщения админа из allowlist.

### 3. Произвольные команды через журналируемый executor

Добавляются три MCP tools:

| Инструмент | Вход | Результат |
|---|---|---|
| `repair_exec` | `host`, `command`, `timeout_ms?`, `interruptible?`, `mutates?` | асинхронный `job_id`; команда поставлена в исполнение |
| `repair_job` | `job_id`, `wait_seconds?` до 30 | состояние, exit code, bounded stdout/stderr; при необходимости ждёт завершение |
| `repair_verify` | `host`, `command`, `timeout_ms?`, `interruptible?` | асинхронная проверка с типом `verify`; exit 0 означает успешную проверку |

- Список `host` ограничен известными инфраструктурными псевдонимами `prod`, `relay`, `test`. Произвольный `user@host` входом не принимается. Внутри выбранного хоста команда произвольная: allowlist команд и runbook-only ограничения нет.
- `prod` исполняется локальным `bash -lc`; для `relay` и `test` используется `ssh -T -o BatchMode=yes` на серверный псевдоним, скрипт передаётся через stdin. Псевдоним и параметры SSH задаёт сервер, не модель.
- Executor асинхронный: длительная команда не держит Telegram webhook и не ограничена трёхминутным таймаутом обычного ответа.
- Команды одного repair выполняются последовательно. Максимальная длительность repair — 60 минут, команды по умолчанию — 20 минут; `timeout_ms` может уменьшить срок, но не увеличить его сверх 30 минут.
- Права не расширяются: доступно только то, что уже разрешено сервисному пользователю API и его существующим SSH-ключам. Новый root-доступ или отдельный privileged-демон не создаётся.
- Вывод каждого потока ограничен 64 КБ в журнале; MCP возвращает не больше 8 КБ с маркером обрезки. Команда, stdout и stderr проходят маскирование секретов перед сохранением и возвратом.
- `mutates` по умолчанию `true`: любой `repair_exec` консервативно считается возможным изменением. Для диагностической read-only команды модель может явно передать `mutates:false`.
- Общие правила репозитория обязательны для repair-промпта: сначала root cause, никаких случайных исправлений; удаление данных, force-push, деньги и новые внешние отправки требуют отдельного явного OK; код выкатывается только штатными скриптами. Подтверждения каждой команды нет.
- Осознанное следствие выбора владельца: технического allowlist произвольных shell-команд нет. Ограничение риска обеспечивается Telegram-ID capability, отсутствием повышения прав, инструкциями, последовательным исполнением и полным аудитом; детерминированно классифицировать любой shell как безопасный невозможно.

### 4. Durable lifecycle

Добавляются таблицы:

- `alert_bot_repairs`: `id`, связанный `turn_id`, `chat_id`, `admin_tg_id`, исходная инструкция, статус, время создания/завершения, причина завершения, счётчики изменений и проверок.
- `alert_bot_repair_jobs`: `id`, `repair_id`, `host`, `command_redacted`, `kind` (`exec`/`verify`), `mutates`, `interruptible`, `status`, `requested_timeout_ms`, `started_at`, `finished_at`, `exit_code`, `stdout_redacted`, `stderr_redacted`, `failure_kind`.

Статусы repair: `requested`, `running`, `cancel_requested`, `verified`, `unverified`, `failed`, `timeout`, `cancelled`, `interrupted`.

- Активность одного repair на чат и одной исполняемой команды на repair обеспечивается ограничениями/атомарными переходами в PostgreSQL, чтобы выдержать повторы updates и рестарт.
- Миграция `002_alert_bot_repair.sql` следует принятому шаблону: один `DO`, advisory transaction lock, `lock_timeout`, проверка `to_regclass` перед созданием индексов. Никакого верхнеуровнего `CREATE INDEX IF NOT EXISTS` на каждом старте.
- Журналы хранятся 90 дней и очищаются существующим суточным циклом. В pm2 логируются только ID, статусы и виды сбоев, без команд и вывода.
- При рестарте API новые команды не запускаются до восстановления состояния. Незавершённые repair переходят в `interrupted`; running jobs без подтверждённого завершения получают неизвестный исход. Автоматического повторного выполнения нет: удалённый процесс мог продолжить работу.
- `/stop` переводит repair в `cancel_requested`, запрещает новые команды и прерывает модель. Для `interruptible:true` завершается процессная группа текущей команды; непрерываемая операция завершается сама. Выполненное не откатывается автоматически.

### 5. Проверка и честный ответ

- До первого `mutates:true` при исправлении инцидента модель обязана установить первопричину по данным инструментов. Если причина не подтверждена, repair завершается без изменений со статусом `failed` и объяснением, каких данных не хватает. Для явного self-test приёмки проверяемой причиной является работоспособность самого repair-контура.
- После последнего возможного изменения модель обязана вызвать `repair_verify` с проверкой именно исправленного поведения, а не безусловно успешной командой.
- Итог вычисляет backend по журналу, текст модели не может его переопределить:
  - есть успешный `verify` позже последнего `mutates:true`, и более поздних изменений нет → `verified`;
  - команды завершены, но такой проверки нет → `unverified`;
  - модель/команда завершились ошибкой и успешной последующей проверки нет → `failed`;
  - истёк общий срок → `timeout`; остановка админом → `cancelled`; рестарт/неизвестный исход → `interrupted`.
- Более поздний `mutates:true` делает прежнюю проверку устаревшей. Ошибка промежуточной команды не мешает честному `verified`, если после восстановления есть успешная финальная проверка.
- В Telegram backend добавляет служебный статус независимо от объяснения модели:
  - `verified` с изменениями → **«Исправлено и проверено»**;
  - `verified` без изменений → **«Проверено: исправление не потребовалось»**;
  - причина не установлена → `failed` и **«Не исправлено: причина не подтверждена»**;
  - `unverified` → **«Выполнено, результат не подтверждён»**;
  - остальные → **«Не исправлено» / «Исход неизвестен»** с последним подтверждённым состоянием.
- Если модель оборвалась после успешной финальной проверки, backend может отправить `verified` по журналу с коротким служебным объяснением. Если обрыв произошёл до проверки, успех не объявляется.
- В Telegram выводится краткая обезличенная сводка, без сырых секретов и пользовательских идентификаторов. Точные команды и технические пути остаются в защищённом журнале.

### 6. Соответствие концепции

Прочитаны §2.5 и §4.2.2 `linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`: облачная модель видит открытый текст при обработке, поэтому наружу передаётся минимум под текущий запрос; для чувствительных данных нужен запросно-ограниченный срез и явное решение человека.

- Обычный AlertBot сохраняет существующую маску и read-only поведение.
- Точные operational ID и пути передаются модели только после явного repair-запроса админа и только внутри этого хода. Это запросно-ограниченный служебный срез, а не постоянная выгрузка базы.
- Секреты маскируются; Telegram получает обезличенный итог; записи имеют срок хранения.
- Действующее решение владельца об общем model switch не меняется и не описывается как Claude-only.

## Проверка

### Jest на тестовой ноде

- Allowlist: разрешённый ID, неадмин в той же группе, другой username, forwarded-сообщение, чужой callback, пустой список, отсутствие привязки Linkeon при разрешённом repair ID.
- Триггеры: `/fix`, «исправь/почини» реплаем, обычный вопрос, повтор update, второй активный repair в чате.
- Capability: `scope=ops` не вызывает repair; чужой/истёкший `scope=repair`, другой admin/chat/turn, снятый из allowlist ID, завершённый и остановленный repair → отказ без spawn.
- Executor: произвольная безобидная shell-команда, stdout/stderr, ненулевой exit, Unicode, большой вывод, таймаут, SSH-сбой, неизвестный host, последовательность команд, `interruptible` и `/stop`.
- Журнал: секреты не сохраняются и не попадают в pm2/Telegram; технические UUID/пути доступны только repair-контуру.
- Итог: отсутствие verify → `unverified`; verify до последнего изменения → `unverified`; verify после него → `verified`; более позднее изменение устаревает проверку; промежуточная ошибка с финальным verify → `verified`; обрыв до/после verify; отсутствие изменений.
- Существующие 25 alert-bot suites и пять read-only tools остаются зелёными.

### Настоящий PostgreSQL

- Повторная и одновременная миграция, открытая пишущая транзакция, атомарный захват активного repair и активной команды.
- Дедупликация updates, terminal transitions, recovery после рестарта, очистка по сроку.

### Гейты и ревью

- `tsc -p tsconfig.build.json`, связанные Jest и `*.pg.spec.ts` на ноде, `npm run build`; полный `jest src` — дельтой к базовому `origin/main`.
- Два независимых ревью: соответствие спецификации и качество/безопасность. Отдельно проверить отсутствие реальных Telegram ID и секретов в публичном репозитории.

## Выкат

1. Работа в `feat/alertbot-repair` от свежего `origin/main`, в изолированном worktree. Локальный `main` с чужими незапушенными коммитами не трогать.
2. Код выключен по умолчанию: без `ALERT_BOT_REPAIR_ADMIN_TG_IDS` repair не создаётся и tools не исполняются.
3. Реальные ID задаются только в серверной конфигурации после подтверждения владельца. В git не попадают; `sync-api-keys-to-test.sh` не синхронизирует repair-настройки.
4. После отдельного OK владельца — только штатный `scripts/deploy.sh`, без ручных правок и ручного рестарта на сервере.
5. Живая приёмка:
   - неадмин не может запустить `/fix`;
   - админ выполняет запись и чтение уникального безобидного файла в `/tmp`, затем `repair_verify`; статус должен быть «Исправлено и проверено»;
   - специально завершившаяся ошибкой команда без успешной проверки даёт «Не исправлено»;
   - read-only вопрос и существующие тикеты работают как раньше.
6. Реальный DOCX-инцидент запускается только новой явной командой админа в Telegram; при выкате никакого автоматического repair не выполняется.
7. Откат: очистить `ALERT_BOT_REPAIR_ADMIN_TG_IDS` и штатно перезапустить. Ops server отклоняет даже ранее выданные repair-токены. Незавершённые команды получают неизвестный исход, а не ложный успех.

## Не входит

Автоматическое исправление без запроса админа; произвольный SSH destination; новый root-доступ; включение встроенных инструментов CLI; автоматический retry команд после рестарта; автоматический откат; ответы пользователю без существующего человеческого подтверждения; изменения фронтенда; ограничение команд заранее записанными runbook’ами.
