# Подавление алерта о Claude при работающем общем провайдере

Дата: 2026-11-11
Статус: дизайн подтверждён владельцем

## Контекст

`ClaudeHealthService` каждые 15 минут проверяет локальный Claude CLI с `noFallback: true`. Это нужно, чтобы знать состояние самого Claude для личного выбора и запасного пути, а не получать зелёный результат за счёт Kimi/Qwen.

При глобальном Kimi рабочие вызовы уже идут через Kimi, но красный алерт «Локальный Claude CLI недоступен» всё равно приходит. Он выглядит как отказ текущего пути ответов, хотя затронуты только проба, личный Claude и резерв.

## Решение

Не отправлять Telegram-алерт о недоступности Claude и его отбой, когда одновременно верно:

1. Общий рубильник стоит на Kimi или Qwen.
2. У выбранного провайдера есть ключ и он не находится в окне «не отвечает» — существующее условие `switchCarriesCliPath`.
3. Ни у одного профиля нет явного личного выбора `llm_provider = 'claude'`.

Проба Claude, `llmStatus`, `llmError`, журнал и данные для админки продолжают обновляться без изменений. Подавляется только доставка Telegram-уведомления.

Красный алерт и обычный отбой сохраняются, если:

- рубильник на Claude;
- у модели рубильника нет ключа или она «не отвечает»;
- есть хотя бы один профиль с личным Claude;
- не удалось проверить наличие личного Claude.

Ошибка проверки личных настроек обрабатывается fail-open: считаем, что личный Claude может быть, и не подавляем алерт.

## Состояние инцидента

Если ранее алерт уже был отправлен, а затем условия подавления стали истинными, инцидент очищается молча:

- `monitor_alert_state.alerted` для `claude_cli` переводится в `false`;
- `lastOutageAlertAt` сбрасывается в `null`;
- сообщение о восстановлении не отправляется, потому что Claude мог остаться недоступным.

Если после этого вернуть рубильник на Claude или назначить личный Claude во время продолжающегося простоя, алерт отправится заново по существующему порогу подряд-провалов. Без ранее открытого инцидента подавление не пишет в `monitor_alert_state`.

## Реализация

Изменение концентрируется в `ClaudeHealthService.maybeAlertOutage()`:

- вычислить состояние рубильника через существующий `switchState()`;
- переиспользовать условие `switchCarriesCliPath`, экспортировав его из `global-llm-messages.ts` без изменения семантики;
- при потенциальном алерте или отбое в reserve-only режиме проверить личный Claude через существующий `PgService` запросом `SELECT EXISTS (...)` по `ai_profiles_consolidated.llm_provider`;
- перед отправкой применить подавление и описанную очистку состояния.

Новая зависимость от `UserLlmProviderService` и изменения маршрутизации моделей не нужны. SQL-выполнение происходит только при reserve-only режиме и наличии потенциального уведомления, а не на каждой пробе.

Тексты существующих красных алертов и отбоев для неподавленных случаев не меняются.

## Тесты

В `claude-health.outage-alert.spec.ts` покрыть:

1. Живой глобальный Kimi, личного Claude нет, Claude down — Telegram-вызова нет.
2. Тот же случай для Qwen — подавление не привязано к одному провайдеру.
3. Живой глобальный Kimi и личный Claude есть — красный алерт сохраняется.
4. Kimi без ключа или в окне «не отвечает» — алерт сохраняется независимо от наличия личного Claude.
5. Ошибка запроса личных настроек — алерт сохраняется.
6. Ранее открытый инцидент и наступившее подавление при Claude down — сообщения нет, состояние очищено.
7. Ранее открытый инцидент и наступившее подавление при Claude ok — отбой не отправляется, состояние очищено.
8. Личный Claude есть при Claude ok — обычный отбой сохраняется.

Существующие сценарии матрицы рубильника должны явно задавать наличие личного Claude там, где ожидают отправку в reserve-only режиме. Остальные тесты здоровья CLI и текстов сообщений не меняются по поведению.

## Границы

- Не менять `noFallback: true` у пробы.
- Не менять общий рубильник, личные настройки и аварийную цепочку.
- Не добавлять новую пробу Kimi/Qwen: «работающий» здесь означает текущее состояние `switchCarriesCliPath`, а не новое активное измерение.
- Не менять отдельный synthetic-мониторинг `r.linkeon.io`.

## Проверка и выкат

Сначала красный тест на подавление, затем минимальная реализация и зелёный focused jest. После этого — typecheck бэкенда и проверки на тестовой ноде по правилам репозитория. Выкат только через `scripts/deploy.sh`, отдельно и с подтверждением владельца; эта спецификация не разрешает автоматический прод-деплой.
