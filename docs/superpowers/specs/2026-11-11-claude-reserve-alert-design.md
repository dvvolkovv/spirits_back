# Подавление алерта о Claude при работающем общем провайдере

Дата: 2026-11-11
Статус: ревизия 2 по решениям владельца + технические гарантии после code review

## Контекст

`ClaudeHealthService` каждые 15 минут проверяет локальный Claude CLI с `noFallback: true`. Это нужно, чтобы знать состояние самого Claude для личного выбора и запасного пути, а не получать зелёный результат за счёт Kimi/Qwen.

При глобальном Kimi рабочие вызовы обычно идут через Kimi, но красный алерт «Локальный Claude CLI недоступен» всё равно приходит. Первая версия дизайна подавляла его по наличию ключа и отсутствию breaker-окна. Code review выявил два пробела:

1. AlertBot жёстко вызывал Claude с `noFallback: true`, поэтому подавление скрывало реальную деградацию admin-facing функции.
2. `enabled && !down` не доказывает доступность Kimi/Qwen: таймауты не всегда открывают breaker, а окно не персистится.

Владелец выбрал перевести AlertBot на общий рубильник и подтверждать доступность выбранного провайдера активной пробой.

## Решение

Не отправлять Telegram-алерт о недоступности Claude и его отбой, когда одновременно верно:

1. Общий рубильник стоит на Kimi или Qwen, у провайдера есть ключ и он не находится в текущем breaker-окне — существующее условие `switchCarriesCliPath` используется как предварительный gate.
2. Активная проба выбранного провайдера только что завершилась успешно.
3. Ни у одного активного аккаунта нет явного личного выбора `llm_provider = 'claude'`.
4. AlertBot использует общий рубильник и не остаётся отдельным Claude-only потребителем.

Проба Claude, `llmStatus`, `llmError`, журнал и данные для админки продолжают обновляться без изменений. Подавляется только доставка Telegram-уведомления.

Красный алерт и обычный отбой сохраняются, если:

- рубильник на Claude;
- у модели рубильника нет ключа или уже открыто breaker-окно;
- активная проба выбранного провайдера упала, вернула пустой ответ или отказ;
- есть хотя бы один активный аккаунт с личным Claude;
- не удалось проверить наличие личного Claude.

Ошибки активной пробы и проверки личных настроек обрабатываются fail-open: алерт не подавляется.

## Активная проба общего провайдера

Проба выполняется внутри оценки уведомления только при предварительном `switchCarriesCliPath` и наличии потенциального алерта, открытого инцидента или отбоя. Новый outage ниже порога подряд-провалов и без открытого инцидента возвращается до неё.

Параметры:

- тот же короткий prompt `Reply with exactly: ok`, без пользовательских или операционных данных;
- явный `provider` текущего рубильника и `providerChoice: 'global'`;
- `noFallback: true`, чтобы ответ другого провайдера не маскировал сбой выбранного;
- `model: 'claude-haiku-4-5'`, который существующий mapping переводит в haiku-класс Kimi/Qwen;
- таймаут 30 секунд;
- `isolatedCwd: true`, чтобы CLI не читал инструкции и hooks из общего `/tmp`;
- `noSessionPersistence: true`, чтобы синтетические пробы не оставляли транскрипты.

Проба использует новый отдельный `ClaudeCliService` без `PgService`. Его `FallbackState` не shared с рабочим сервисом, поэтому `markUp`, другие внутренние переходы и события пробы не могут изменить рабочий breaker или производственную статистику ответов рубильника. Исходный injected `ClaudeCliService` продолжает использоваться только для основной пробы Claude и чтения рабочего состояния.

После активной пробы выполняется один строгий SQL-запрос, который в одном statement snapshot возвращает и текущий global provider из `llm_settings`, и наличие активного личного Claude. Он не использует 15-секундный кэш `GlobalLlmProviderService.get()` и не полагается на его fallback к старому значению. Ошибка этого запроса — fail-open без suppression. После запроса остаются только синхронные `fallbackStats(Date.now())`, построение `CliSwitchState` и решение: ни breaker, ни рубильник, ни личный Claude не читаются через последующий `await`. Это закрывает гонки во время пробы, SQL и финального чтения. Подавление разрешено только если текущий провайдер совпадает с пробованным, предварительный gate всё ещё проходит и в том же snapshot нет активного личного Claude. При смене рубильника во время любого ожидания действует fail-open; новый провайдер в том же тике второй пробой не вызывается. Для нового non-Claude провайдера, который сам проходит `switchCarriesCliPath`, сообщение получает `providerUnverified`; отсутствие ключа и реальный `down` сохраняют приоритет своих существующих текстов. Строка fallback-статистики использует синхронный снимок после атомарного запроса.

Успех — непустой ответ, не распознанный существующим `looksLikeCliRefusal` как отказ. Ошибка логируется только с безопасным видом/статусом, без сырого текста CLI.

При неуспехе для текста текущего алерта используется отдельный признак `probeFailed`, а не подмена реального breaker-флага `down`. Текст называет подтверждённое влияние Claude outage (пробы мониторинга, личный Claude и запасной путь), сообщает о failed control probe и неподтверждённой доступности рабочего пути через выбранную модель; breaker/маршрутизация не изменялись. Ложного утверждения о затронутом OAuth-пути всех рабочих вызовов или уже выполненном fallback нет. Если за время ожидания реальный breaker тоже открылся, приоритет имеет существующий текст реального `down`.

## AlertBot

`AlertBotAi.answer()` больше не задаёт `noFallback: true`. Его вызов `ClaudeCliService` использует общий рубильник и существующую аварийную цепочку так же, как другие рабочие вызовы. Вопросы админов и данные ops-инструментов поэтому идут выбранной модели; это явно подтверждено владельцем.

Состав ops-инструментов, маскирование, модельный класс, таймауты и обработка ошибок AlertBot не меняются.

## Личный Claude

Проверка использует существующий `PgService` и `SELECT EXISTS` с join:

```sql
SELECT
  (
    SELECT value->>'provider'
    FROM llm_settings
    WHERE key = 'global_provider'
  ) AS global_provider,
  EXISTS (
    SELECT 1
    FROM ai_profiles_consolidated p
    JOIN user_id u ON u.internal_id = p.user_id
    WHERE p.llm_provider = 'claude'
      AND u.state = 'active'
  ) AS personal_claude
```

Удалённые и слитые аккаунты не удерживают алерт включённым. Неизвестное значение provider трактуется как Claude, как в существующем контракте. Ошибка запроса возвращает `null` и запрещает suppression (fail-open). Запрос выполняется только после успешной активной пробы общего провайдера, а не на каждом тике. Отдельного `hasPersonalClaude()` и повторного `GlobalLlmProviderService.get()` после него нет: единый statement возвращает согласованную пару значений.

## Состояние инцидента

Подтверждённое ранее поведение сохраняется. Если ранее алерт уже был отправлен, а затем все условия подавления стали истинными, инцидент очищается молча:

- `monitor_alert_state.alerted` для `claude_cli` переводится в `false`;
- `lastOutageAlertAt` сбрасывается в `null`;
- сообщение о восстановлении не отправляется.

Для очистки при `status = 'ok'` также требуется успешная активная проба общего провайдера и отсутствие активного личного Claude. Это сознательно сохраняет выбранное владельцем подавление отбоя, а не вводит новый lifecycle уведомлений.

Если после очистки вернуть рубильник на Claude, назначить личный Claude или активная проба общего провайдера начнёт падать во время продолжающегося простоя Claude, алерт отправится заново по существующему порогу. Без ранее открытого инцидента подавление не пишет в `monitor_alert_state`.

## Реализация

- `claude-health.service.ts`: активная проба общего провайдера через отдельный observation-only CLI-экземпляр, единый атомарный SQL-snapshot рубильника и личного Claude, синхронная финальная breaker-gate, gate доставки и молчаливая очистка.
- `global-llm-messages.ts`: экспортированный `switchCarriesCliPath` без изменения семантики и отдельный `probeFailed`-текст без выдуманного routing fallback.
- `alert-bot.ai.ts`: удаление Claude-only `noFallback` без других изменений.
- Соответствующие focused specs обновляются сначала красными тестами.

Новая зависимость от `UserLlmProviderService` не нужна. Общий рубильник, личные настройки, breaker и аварийная цепочка маршрутизации не меняются. Тексты существующих красных алертов и отбоев для неподавленных случаев не меняются.

## Тесты

### AlertBot

1. Опции вызова не содержат `noFallback: true`, поэтому применяется общий рубильник.
2. Ops-инструменты, модель, маскирование и остальные опции сохраняются.
3. Существующие тесты `ClaudeCliService` продолжают подтверждать выбор общего рубильника при отсутствии явного provider и `noFallback`.

### Активная проба и gate

1. Успешная Kimi-проба, нет активного личного Claude — подавление; опции пробы содержат явный `provider: 'kimi'`, `providerChoice: 'global'`, `noFallback: true` и haiku-класс.
2. Тот же успех для Qwen — подавление не привязано к одному провайдеру.
3. Ошибка, пустой ответ или текстовый отказ Kimi — красный алерт с `probeFailed`-текстом, без выдуманного fallback.
4. Нет ключа или открыто breaker-окно — активная проба не вызывается, алерт сохраняется.
5. Новый outage ниже порога без открытого инцидента — активной пробы нет.
6. Открытый инцидент ниже порога — проба выполняется для возможной молчаливой очистки, преждевременного realert нет.
7. Ошибка SQL личных настроек после успешной пробы — алерт сохраняется.
8. SQL содержит join к `user_id` и условие `u.state = 'active'`.
9. Молчаливые очистка и подавление отбоя требуют успешной активной пробы.
10. После очистки возврат на Claude или сбой активной пробы во время простоя даёт новый алерт.
11. Личный Claude при восстановлении — обычный отбой сохраняется.
12. Проба требует `isolatedCwd` и `noSessionPersistence`; фабрика возвращает новый CLI без PG, отдельный от рабочего и от предыдущей пробы.
13. Переключение рубильника во время deferred-пробы — fail-open, подавления нет, второй пробы нового провайдера нет.
14. Ошибка пробы при новом инциденте создаёт красный алерт и пишет `alerted=true`; при recovery сохраняется правдивый отбой с `probeFailed`-текстом.
15. `probeFailed`-тексты не утверждают, что breaker сработал или рабочие вызовы перешли на другого провайдера.
16. Переключение рубильника во время deferred-SQL — fail-open без suppression; финальное чтение происходит после SQL.
17. Kimi→Qwen во время пробы — outage и recovery содержат `providerUnverified`, а не healthy-текст Qwen; второй пробы нет.
18. `fallbackAlertLine` использует финальные счётчики после ожидания, а не предпробный снимок.
19. Kimi→Qwen без ключа — `providerUnverified` не перекрывает no-key текст ни в outage, ни в recovery.
20. Кэшированный `get()` продолжает возвращать Kimi, но атомарный SQL видит Claude — suppression запрещено.
21. Ошибка атомарного запроса — fail-open красный алерт, без fallback к cached healthy provider.
22. Атомарный snapshot содержит `personal_claude=true` — suppression запрещено даже если прежний mock личного запроса был false.
23. Открытие breaker во время атомарного запроса видно в синхронном `fallbackStats` после него — suppression запрещено.

Существующие матрицы сообщений и безопасных причин ошибок остаются зелёными.

## Границы

- Не менять `noFallback: true` у исходной пробы Claude и у новой пробы выбранного провайдера.
- Не менять общий рубильник, личные настройки, breaker и маршрутизацию остальных реальных вызовов вручную.
- Не добавлять активную пробу на каждый тик без потенциального уведомления.
- Не менять отдельный synthetic-мониторинг `r.linkeon.io`.
- Не исправлять в этой задаче старые дефекты Telegram delivery/cooldown и не перестраивать lifecycle уже отправленных уведомлений за пределами подтверждённой молчаливой очистки.

## Соответствие концепции

Перед реализацией прочитаны §2.5 и §4.2.2 концепции: `~/Downloads/linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`.

Активная проба содержит только синтетический `Reply with exactly: ok`: биография, профиль, пользовательские разговоры и операционные данные в неё не попадают. Поэтому для неё не возникает новый поток персональных данных в облако. `noSessionPersistence` запрещает CLI сохранять транскрипт с нашей стороны; о политике хранения самого внешнего провайдера это не утверждает ничего.

AlertBot работает с админскими вопросами и ops-данными, а не с биографией пользователя. Перевод этих данных на общий рубильник — отдельное явное решение владельца, зафиксированное выше, а не молчаливое расширение потока. Остальные маршруты и согласия пользователей задача не меняет.

## Проверка и выкат

Каждое изменение — через красный тест, минимальную реализацию и зелёный focused jest. Финальная проверка включает monitoring, global messages, safe errors, AlertBot и production build на тестовой ноде. Выкат только через `scripts/deploy.sh`, отдельно и с подтверждением владельца; эта спецификация не разрешает автоматический прод-деплой.
