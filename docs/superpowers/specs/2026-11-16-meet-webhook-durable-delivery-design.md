# Durable Attendee webhook для Google Meet — дизайн

**Дата:** 2026-11-16
**Статус:** утверждено владельцем 2026-11-16
**Связанные:** `src/meeting/meet-webhook.controller.ts`, `src/meeting/migrations/`,
`src/voice-call/migrations/001_voice_calls.sql`, концепт лаунчера §2.5

## Цель

Событие Attendee, необходимое Роману для работы в Google Meet, не должно теряться из-за
временной ошибки PostgreSQL или LiveKit. Подтверждение `200 {ok:true}` должно означать, что
событие либо уже надёжно сохранено, либо является повтором сохранённого, либо заведомо не
требует доставки.

Первый релиз меняет только серверный путь Attendee webhook → PostgreSQL → LiveKit. Формат
LiveKit-сообщений и поведение голосового воркера остаются прежними.

## Что сломано сейчас

`MeetWebhookController` после проверки подписи:

1. заносит `callId:idempotency_key` в процессный `Set` ограниченного размера;
2. загружает звонок, превращая любую ошибку загрузки в «звонок не найден»;
3. отправляет сообщение в LiveKit;
4. ошибку отправки только логирует и всё равно отвечает `{ok:true}`.

В результате временный сбой необратимо теряет событие, а повтор Attendee с тем же ключом может
быть подавлен записью в `Set`. После рестарта или вытеснения ключа, наоборот, возможен повтор.

## Решения и инварианты

- **PostgreSQL inbox, не Redis и не синхронный hotfix.** Используем уже существующую инфраструктуру;
  запись переживает рестарт API и обща для нескольких API-процессов.
- **At-least-once, не «ровно один раз»**. Обычные повторы Attendee с ключом подавляются уникальным
  индексом. Редкий повтор после падения между успешным LiveKit send и записью `delivered`
  допустим: транзакционно связать внешнюю отправку и локальную БД невозможно.
- **Сохранение предшествует подтверждению.** Если запись не удалась, ручка отвечает `503`,
  чтобы ретрай Attendee был полезен. Ошибки LiveKit после сохранения не меняют ответ webhook.
- **Семантика фильтров не меняется.** Плохая подпись, отсутствие конфигурации, события без
  `callId`, неизвестные триггеры, пустой чат и неактивный звонок обрабатываются так же, как сейчас.
- **Без нового требования строгого порядка.** Due-строки выбираются по `next_retry_at, created_at, id`;
  одновременные HTTP-запросы уже сейчас не дают строгого per-call FIFO. Первый релиз не вводит
  блокировку всех событий встречи из-за одного ожидающего ретрая.
- **Без изменения сообщений воркеру.** `meet_participant`, `meet_speaking`, `meet_chat` и
  `meet_bot_state` сериализуются в LiveKit ровно в существующем виде.

## Архитектура

### `MeetWebhookController`

Оставляет аутентификацию и преобразование Attendee payload, но больше не хранит `seen`, не зовёт
LiveKit напрямую и не подавляет ошибки БД.

Поток принятия события:

1. Прочитать `ATTENDEE_WEBHOOK_SECRET`; при отсутствии оставить `503`.
2. Проверить HMAC по канонизированному JSON; при несовпадении оставить `401`.
3. Получить `callId`; без него вернуть `{ok:true}`.
4. Построить нормализованное LiveKit-сообщение; для неизвестного триггера или пустого чата вернуть
   `{ok:true}` без записи.
5. Загрузить звонок. Успешно загруженный отсутствующий/неактивный звонок → `{ok:true}` без записи;
   ошибка загрузки → `503`, а не отсутствие звонка.
6. Выполнить идемпотентный `INSERT`. Подтверждённый конфликт уникального ключа означает повтор и
   тоже даёт `{ok:true}`.
7. Если звонок удалили между загрузкой и вставкой, PostgreSQL `23503` трактовать как закрытый звонок
   и вернуть `{ok:true}`. Любая другая ошибка вставки → `503`.
8. После успешной вставки или подтверждённого повтора запустить немедленный неблокирующий pump
   доставщика и вернуть `{ok:true}`.

Загрузка звонка перед вставкой сохраняет существующее поведение для чужих/закрытых звонков и
позволяет поставить FK с каскадным удалением. Ошибка этой загрузки больше не приравнивается к
отсутствию звонка.

### `MeetingWebhookInboxStore`

Единственная граница SQL:

- идемпотентная вставка через `INSERT ... ON CONFLICT ... DO NOTHING RETURNING id`;
- выбор due-событий и восстановление просроченных `processing`;
- атомарный захват события;
- переходы `delivered`, `pending`, `discarded`, `dead`;
- очистка завершённых записей по retention.

Store не знает LiveKit и правила преобразования Attendee payload.

### `MeetingWebhookDeliveryService`

Зависит от Store, `VoiceCallService` и `LiveKitClient`:

- немедленный `kick()` после enqueue;
- fallback poll каждую секунду;
- reentrancy guard внутри процесса и безопасные DB claims между процессами;
- выборка партии до 20 событий, не более пяти одновременных попыток доставки;
- ограничение одной попытки LiveKit send десятью секундами;
- backoff, terminal failure и логирование переходов;
- hourly retention cleanup.

Ошибка фонового pump логируется и не создаёт unhandled rejection; следующий poll остаётся
страховкой.

## Хранение

Новая миграция `src/meeting/migrations/006_meeting_webhook_events.sql`:

```sql
CREATE TABLE IF NOT EXISTS meeting_webhook_events (
  id               BIGSERIAL PRIMARY KEY,
  call_id          UUID NOT NULL REFERENCES voice_calls(id) ON DELETE CASCADE,
  idempotency_key  TEXT,
  trigger          TEXT NOT NULL,
  message          JSONB NOT NULL,
  status           TEXT NOT NULL DEFAULT 'pending'
                   CHECK (status IN ('pending', 'processing', 'delivered', 'discarded', 'dead')),
  attempts         INTEGER NOT NULL DEFAULT 0,
  next_retry_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_error       TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  delivered_at     TIMESTAMPTZ
);
```

Индексы:

- уникальный `(call_id, idempotency_key) WHERE idempotency_key IS NOT NULL`;
- non-partial `(call_id)` для эффективного FK cascade, включая строки с NULL key;
- due-выборка `(next_retry_at, created_at, id) WHERE status = 'pending'`;
- stale-восстановление `(updated_at) WHERE status = 'processing'`;
- retention `(updated_at) WHERE status IN ('delivered', 'discarded', 'dead')`.

`ON CONFLICT` использует тот же частичный уникальный индекс. Несколько событий с `NULL` вместо
ключа не сливаются: Attendee в таком случае не дал основания считать их одинаковыми.

В `message` сохраняется только нормализованное сообщение, необходимое для доставки. Полный исходный
webhook отдельно не копируем: для повторной отправки он не нужен, а лишнего хранения имен участников,
текста чата и служебных полей не должно быть.

### Как миграция доезжает

Файл остаётся совместимым с `scripts/migrate.ts` и регистрируется как
`meeting/006_meeting_webhook_events.sql`. Но текущий `deploy.sh` не вызывает общий runner, а
комментарии действующих модулей фиксируют, что глобальный `npm run migrate` на проде застревает на
ранних миграциях. Поэтому только ручной общий runner считать достаточным нельзя.

`MeetingWebhookInboxStore` при старте API применяет неприменённый файл по образцу `SpeechService`:

- путь из `dist` и fallback к `src`, поскольку Nest не копирует `.sql` в сборку;
- `CREATE TABLE IF NOT EXISTS schema_migrations` перед проверкой;
- отдельная транзакция для SQL файла и записи в общую `schema_migrations`;
- `pg_advisory_xact_lock(8675309)` внутри транзакции сериализует модульный запуск с общим runner
  и другими API-процессами; после ожидания признак применённой миграции проверяется заново;
- `lock_timeout = '3s'`;
- уже записанная миграция повторно не выполняется;
- ошибка логируется и старт API не роняется; webhook при этом будет честно возвращать `503`, пока
  таблица недоступна.

Это не второй журнал миграций: используется та же таблица и то же имя файла, что у общего runner.

## Доставка и состояния

```text
pending ──claim──> processing ──success──> delivered
                      │
                      ├──call missing/inactive──> discarded
                      │
                      ├──retryable failure, attempts < 10──> pending
                      │
                      └──retryable failure, attempts = 10──> dead

processing старше lease 60 с ──новый claim──> processing (attempts + 1)
```

- Перед claim stale `processing` с `attempts >= 10` атомарно становится `dead` с технической
  причиной lease expiry; попытка 11 не выдаётся. Это закрывает и повторные падения после финальной
  попытки, когда `markFailed` уже не выполняется.
- Claim — атомарный conditional `UPDATE ... RETURNING`: захватывает только due `pending` либо
  `processing` с `attempts < 10`, чей `updated_at` старше 60 секунд; увеличивает `attempts`, ставит
  `processing` и новый `updated_at`. Два доставщика не могут успешно захватить одну попытку.
- Каждое завершение ограждено генерацией claim: условия включают `id`, `status='processing'` и
  `attempts=claimAttempts`. Старый worker после recovery получает `false`/`null` и не может
  перезаписать состояние нового worker; успешные `delivered`/`discarded` возвращают `true`, а
  `markFailed` возвращает фактический `pending`/`dead` либо `null` при отсутствии перехода.
- Перед отправкой звонок загружается заново. Ошибка загрузки — retryable; успешно полученные
  `null`/неактивный статус — `discarded`.
- Успешный `LiveKitClient.send` → `delivered`, `delivered_at = now()`, `last_error = NULL`.
- Задержки после неудачных попыток: 1 с, 2 с, 5 с, 15 с, затем 60 с. После десятой неудачи —
  `dead`; автоматического воскрешения по повторному webhook нет.
- `last_error` обрезается до 500 знаков и содержит техническую причину без полного payload.
- Просроченный lease повторяет отправку. Если первый процесс успел отправить и умер до отметки
  `delivered`, воркер может получить повтор — это обязательный сценарий at-least-once, а не сбой
  уникального индекса.
- Таймаут send также может оставить неопределённый внешний исход; он обрабатывается как retryable
  failure и подчиняется той же at-least-once семантике.

## Ошибки webhook

| Ситуация | Ответ | Сохранение/ретрай |
| --- | --- | --- |
| нет `ATTENDEE_WEBHOOK_SECRET` | `503` | конфигурационная ошибка, как сейчас |
| плохая подпись | `401` | payload не сохраняется |
| нет `callId`, неизвестный trigger, пустой чат | `200 {ok:true}` | записи нет |
| звонок успешно загружен, но отсутствует/неактивен | `200 {ok:true}` | записи нет |
| ошибка загрузки звонка | `503` | Attendee может повторить |
| вставка или проверка duplicate успешна | `200 {ok:true}` | событие durable, LiveKit доставит асинхронно |
| звонок удалён в гонке перед вставкой (`23503`) | `200 {ok:true}` | доставлять некуда |
| другая ошибка INSERT | `503` | Attendee может повторить |
| LiveKit временно недоступен после durable INSERT | `200 {ok:true}` исходному webhook | ретраит dispatcher |

## Хранение результатов и приватность

- `delivered` и `discarded` удаляются через 24 часа после `updated_at`.
- `dead` хранится 7 суток для разбора, затем удаляется.
- `pending` и `processing` retention не удаляет.
- `ON DELETE CASCADE` удаляет inbox-записи вместе с соответствующим `voice_calls`, включая сценарий
  удаления аккаунта. Этот каскад проверяется реальным PostgreSQL-тестом, а не только чтением SQL.
- Логи содержат `eventId`, `callId`, trigger, attempts и техническую ошибку; имена участников и текст
  чата в новые логи не добавляются.

## Наблюдаемость первого релиза

Логируются: первичная вставка/duplicate на уровне debug, каждый terminal `dead`, восстановление
stale `processing`, сбой миграции и итоговая ошибка pump. Обычная временная ошибка включает номер
попытки и следующую задержку.

Telegram-алерты деградации встречи, dashboard и отдельная метрическая система в этот релиз не
входят: это следующий независимый этап общего плана.

## Проверка

### Юнит-тесты

- Все существующие тесты подписи и преобразования participant/speech/chat/bot-state сохраняются.
- Дубликат с тем же `(callId, key)` подтверждается без второй вставки.
- Два события без ключа не подавляют друг друга.
- Ошибка `calls.load` до сохранения даёт `503`; отсутствующий/неактивный звонок — `{ok:true}`.
- Ошибка INSERT даёт `503`; `23503` после успешной предварительной загрузки даёт `{ok:true}`.
- LiveKit success → `delivered`; временная ошибка → запланированный retry; десятая ошибка → `dead`.
- Ошибка загрузки звонка в dispatcher → retry; неактивный звонок → `discarded`.
- Зависший `processing` снова доставляется после lease; stale попытка 10 становится `dead`, а не 11.
- Старый worker после recovery не может завершить или провалить claim нового worker: fencing по
  `attempts` возвращает `false`/`null`, состояние новой генерации остаётся неизменным.
- Таймаут send не оставляет строку навсегда в `processing`.
- Смодированное падение после send, но до отметки `delivered`, приводит к повторной отправке и не
  нарушает состояние очереди.
- Новый migration файл реально присутствует в списке/директории модульного запуска; повторный старт
  не выполняет уже записанную миграцию.

Каждое новое правило сначала проверяется красным тестом на старой реализации или с мутацией новой.

### Реальный PostgreSQL на тестовой ноде

Новый `src/meeting/meet-webhook-inbox.pg.spec.ts` запускается с `PROVISIONING_PG_URL` против
одноразовой базы:

1. конкурентные вставки одного ключа создают ровно одну строку;
2. два `NULL`-ключа создают две строки;
3. конкурентные claim не возвращают одну попытку двум доставщикам;
4. stale `processing` восстанавливается, свежий — нет; старая генерация claim ограждена от новой,
   а истёкшая попытка 10 переходит в `dead` без выдачи попытки 11;
5. backoff, `delivered`, `discarded`, `dead` и retention меняют строки по описанным правилам;
6. удаление `voice_calls` каскадно удаляет связанные inbox-записи;
7. повторный и параллельный запуски миграции не дублируют запись и не выполняют повторный DDL уже
   записанного файла.

Существующий account-deletion PostgreSQL suite дополняется новой миграцией и проверкой каскада.
Моки `pg` не засчитываются как проверка SQL.

Все прогоны — в свежем CI-клоне на конкретном SHA: `npm ci`, затем
`npx jest src/meeting src/voice-call --maxWorkers=2` с выделенной одноразовой БД; перед релизом —
полный backend suite и build на тестовой ноде. Локальные тяжёлые Jest/build на Windows не запускать.

## Деплой и откат

1. Реализация начинается от свежего зафиксированного `origin/main`, поскольку удалённая ветка активно
   движется.
2. На test проверяются зелёные тесты, запись `meeting/006_meeting_webhook_events.sql` в
   `schema_migrations` и отсутствие ошибки миграции в логах API.
3. Test/prod выкатываются только стандартным `bash ~/Downloads/spirits_back/scripts/deploy.sh`;
   прод не трогается при красном test.
4. После выката проверяются smoke и отсутствие новых `dead`/migration errors на спокойном контуре.
   Живая встреча в проде обязательным тестовым шагом не является.

Откат выполняется кодом через тот же deploy pipeline. Таблицу и её данные не удаляем: старый код её
игнорирует, а накопленные строки сохраняются для последующего возврата исправления. Отдельного
destructive down migration нет.

## Соответствие концепции

Решение спроектировано в границах §2.5, описанной в проектных инструкциях как «что и как уходит в
облако; два тира и выбор пользователя на каждое использование»:

- нового внешнего канала нет: используются уже существующие Attendee → backend → LiveKit;
- новый внутренний PostgreSQL inbox не передаёт данные новому внешнему сервису и не создаёт нового
  платного integration;
- сохраняется минимальный нормализованный payload, а не полный webhook;
- выбор пользователя начать/завершить встречу и текущие режимы ассистента не меняются;
- сроки хранения ограничены, а удаление звонка/аккаунта удаляет и временные inbox-записи.

**Решение владельца:** исходный документ концепции недоступен ни на одной известной машине.
16.11.2026 владелец явно подтвердил продолжение без него. Основанием служат требования
`CLAUDE.md` к §2.5 и перечисленные выше проверяемые ограничения; утверждения, что исходный §2.5
был прочитан, нет. Если документ позже найдётся, соответствие пересматривается отдельно, а
обнаруженное расхождение не игнорируется.

## Что НЕ делаем в первом релизе

- Redis Stream или новая инфраструктура очередей.
- Изменение LiveKit SDK, voice-host, Realtime reconnect и SDK patches.
- Изменение формата LiveKit-сообщений и добавление нового downstream dedupe protocol.
- Строгий per-call FIFO с head-of-line blocking.
- Telegram degradation alerts и fault-injection soak tests.
- Participant UUID/roster rework и фронтовая локаль времени.
- Ретрай навсегда, автоматический requeue `dead`, destructive rollback миграции.
