# Ошибки Claude CLI без сырого текста — дизайн

Дата: 02.11.2026. Решение владельца: «ОК» на предложение «ошибка CLI несёт только безопасный текст: вид сбоя, код ответа API, служебная диагностика; сырой — внутри, только для классификации».

## Зачем

Текст ошибки `ClaudeCliService` сейчас собирается из сырых кусков: `result` (в json-режиме это начало ответа модели), `stdout` (NDJSON хода или итоговый JSON), `stderr`, сообщение `SyntaxError` от `JSON.parse` (цитирует начало stdout), текст отказа, пришедший обычным ответом. Дальше он уходит:

- в журналы pm2 — сам сервис (`claude CLI exit N: stderr=… stdout=…`, переходы на запасных, «запасные тоже не ответили») и 14 из 16 мест вызова (`e.message`);
- в базу — `tg_bot_messages` (системная строка «ход упал: …», её видит владелец бота через `GET /webhook/tg-bot/configs/:id/messages`), `insights_runs.error`, `vmm_runs`/`vpm_runs.error_message`;
- в Telegram-алерт мониторинга (`claude-health`: «Причина: …» — для вида `other` это сырой текст) и сводку «затыков недели»;
- в ответы админ-API (vmm/vpm `generate`, `list_runs`, мониторинг).

Это фрагменты разговоров пользователей. На релее с 31.10 в журнал перехода идёт только безопасная деталь (`safeErrorDetail`: статус и строка `[ede_diagnostic]`); бэкенд выравниваем.

## Решение

1. **Классификация — по сырому тексту внутри сервиса, до создания ошибки.** Наружу уходит `ClaudeCliCallError` с безопасным `message` и признаками:
   - `kind: LlmOutageKind` — `classifyLlmError(сырой).kind`;
   - `access: boolean` — `isFallbackWorthy(сырой)` (403/Arrearage дают `access` при виде `other`; переполнение контекста — нет доступа при виде `weekly_limit`: признаки независимы, нести оба);
   - `status?: number` — `api_error_status` (целое 100–599), если CLI его дал;
   - `refusal?: boolean` — отказ CLI, пришедший обычным ответом.

   Безопасный текст задаётся сразу в `super(...)`: `e.stack` (его пишут `tg-bot.service` и Nest ExceptionsHandler) начинается с `message`.

2. **Безопасный текст — фиксированный словарь и коды**, формат `claude CLI <что>: <вид>[, status N][, exit N][, <деталь>]`:
   - что — «отказ», «ошибка», «код выхода N», «неверный JSON (stdout N байт)», «не запустился (<код spawn, например ENOENT>)»; таймаут остаётся прежним `claude CLI timeout after Nms` (на слове timeout держится вид `timeout`);
   - деталь — только (а) строка `[ede_diagnostic] …` из `errors[]` по строгой регулярке (та же, что у релея: ключи `[a-z_]+`, значения `[A-Za-z0-9_.:-]*`, до 160 знаков) и (б) текст отказа CLI (`looksLikeCliRefusal`) — одной строкой до 160 знаков: его пишет CLI, а не модель, и в нём время сброса лимита;
   - никогда: `result`, `stdout`, `stderr`, `j.error`, `streamErrorDetail`, сообщение `JSON.parse`.

3. **Склейка попыток** (`parts` в `runRaw`) — из безопасных текстов. Итоговая ошибка после цепочки — `ClaudeCliCallError` (сейчас обычный `Error`) со сводным `kind` (приоритет как у `classifyLlmError`: `weekly_limit` → `rate_limit` → `auth` → `overloaded` → `timeout` → `other`) и `access` — хоть одна попытка со сбоем доступа. Формат склейки прежний: `<первая> | <p> fallback: …`, `(выбран)`, `(для всех)`.

4. **`runRaw`**: `access = err.access ?? isFallbackWorthy(message)`, `kind = err.kind ?? classifyLlmError(message).kind` — признаки, если они есть; текст — только для обычных `Error` (таймаут, spawn), где он и так безопасен.

5. **Журналы сервиса** — только безопасный текст; вместо содержимого stdout/stderr — их размер в байтах.

6. **Потребители, которые решают по тексту ошибки:**
   - `insights.service` (`isLimit(e.message)` → отложить на 6 ч) — по `e.kind`, если он есть; по тексту — только для ошибок без признаков;
   - `claude-health` (проба живости, `classifyLlmError(e.message)` → вид и «Причина» в алерте/админке) — вид из `e.kind`, причина — фиксированная фраза вида; для `other` — безопасный `message`.

   Остальные 14 мест только пишут или хранят `e.message` — станут безопасными без правок.

## Что меняется в поведении

- `неверный JSON`: вид всегда `other`, без перехода на запасных. Раньше кусок stdout в сообщении `SyntaxError` мог случайно дать `rate_limit`/`auth` и переключение.
- Алерт мониторинга для вида `other` — без сырой причины (фраза + безопасный текст).
- Владелец TG-бота в журнале сообщений видит безопасную причину сбоя хода.
- Отладка сбоя по журналу: видны вид, статус, код выхода, диагностика CLI и размеры вывода; самой фразы ошибки нет.

## Не трогаем

- Тексты, которые видит человек (заглушки), и тексты отказов, которые Маша/TG/гость показывают сами, — без изменений.
- «Сырые головы» ответов модели в журналах при разборе JSON в vmm/vpm/neo4j/backlog/custom-agents — не ошибки CLI, отдельная задача.
- `classifyLlmError(...).human` для `other` (сырой текст) — сама функция не меняется; `claude-health` перестаёт брать из неё причину.
- Релей (`relay-agent/`) — там это уже сделано.

## Соответствие концепции

§4.2.2 концепции лаунчера — обработка без сохранения: журналы, база и алерты больше не хранят фрагменты разговоров из ошибок CLI.

## Тесты

- Модульные (чистые функции): строгая диагностика, сводный вид, безопасный текст.
- Сервис: маркер из `result`/`stdout`/`stderr`/`errors[]` не попадает ни в `message`, ни в `stack`, ни в один вызов `logger`, ни в склейку; признаки верны для 401 (`auth`, доступ), 529 (`overloaded`, доступ), отказа «hit your limit» текстом (`weekly_limit`, доступ, `refusal`), 403/Arrearage (`other`, доступ), переполнения контекста (без доступа), таймаута (`timeout`), неверного JSON (`other`, без доступа).
- Регрессия цепочки: Claude 401 → Qwen → Kimi и выбор провайдера работают при сырых текстах с маркером; маркер не выходит наружу.
- `insights`: лимит из `e.kind` откладывает прогон; `claude-health`: вид из `e.kind`, в алерте нет маркера.
- Ожидания трёх спеков (`claude-cli.fallback`, `claude-cli.chain`, `claude-cli.global-switch`), проверявших сырой текст, — на признаки и безопасный текст.
- Живая проверка на ноде — `scripts/llm-fallback-check.js` (разбор склейки — под новый формат).
