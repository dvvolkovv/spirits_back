# Родительный падеж имени владельца в подписи ассистента

**Дата:** 2026-11-17
**Статус:** дизайн утверждён владельцем
**Область:** `spirits_back`, встречи через LiveKit/Taler ID и Attendee (Meet, Zoom, Teams, Telemost)

## 1. Контекст и подтверждённая причина

Ассистент должен быть подписан как «Роман · ассистент Владимира», а не «Роман · ассистент Владимир». Имя владельца хранится и передаётся в именительном падеже, поэтому перед подстановкой в шаблон «ассистент …» оно должно быть преобразовано в родительный.

В коде уже есть центральный модуль `src/meeting/assistant-signature.ts`:

- `ownerGenitive()` преобразует одиночные русские имена;
- `assistantSignature()` собирает готовую подпись;
- `MeetingService.join()` использует её для LiveKit/Taler ID и передаёт воркеру как `assistantDisplayName`.

Это исправление было добавлено коммитом `57abeef9` 2026-09-14, но охватило не все пути:

1. `MeetingService.attachBot()` повторно собирает `botName` из исходного `ownerName` и отправляет его в Attendee. Поэтому видимое имя бота на Meet/Zoom/Teams/Telemost остаётся в именительном падеже.
2. `voice-host/src/agent.ts` отдельно собирает `selfName` из исходного `meta.ownerName`. Это значение используют `Presence` и `Roster` для исключения собственного бота из состава встречи.
3. Существующий тест `attachBot` закрепляет ошибочное поведение: ожидает «Андрей · ассистент Дмитрий».

Фронтенд эту подпись не формирует.

## 2. Цель и критерии приёма

Для всех вновь создаваемых встреч видимая подпись ассистента должна формироваться через один и тот же `assistantSignature()`:

- `Владимир` → «Роман · ассистент Владимира»;
- `Дмитрий` → «Роман · ассистент Дмитрия»;
- пустое или отсутствующее имя → «Роман · ассистент пользователя».

Одна и та же строка должна использоваться:

- при создании Attendee-бота;
- как `displayName` воркера;
- как `selfName` для `Presence` и `Roster`.

Это одновременно исправляет грамматику и исключает рассинхронизацию имени, по которому воркер узнаёт собственного бота.

## 3. Утверждённый дизайн

### 3.1 Backend / Attendee

`MeetingService.attachBot()` должен вызывать:

```ts
const botName = assistantSignature(
  agentRes.rows[0]?.display_name || 'Ассистент',
  ownerName,
);
```

Самостоятельный шаблон с исходным `ownerName` удаляется. Порядок загрузки владельца, создания бота, обработки ошибок и записи `external_bot_id` не меняется.

`MeetingService.join()` уже реализует требуемое поведение и не меняется.

### 3.2 Voice-host

Воркер уже получает `assistantDisplayName` и вычисляет:

```ts
const displayName =
  meta.assistantDisplayName || `${agentName} · ассистент ${meta.ownerName || 'пользователя'}`;
```

Для исключения собственного бота используется та же строка:

```ts
const selfName = displayName;
```

Новый модуль склонения в voice-host и импорт из backend в отдельный процесс воркера не добавляются. Fallback для заданий старого backend остаётся прежним; при этом `displayName` и `selfName` совпадают как для старых, так и для новых заданий.

### 3.3 Правила склонения и ограничения

Текущая эвристика `ownerGenitive()` сохраняется без расширения:

- одиночные кириллические имена склоняются по существующим правилам;
- латиница, другие алфавиты и составные имена возвращаются без изменений;
- заглушка «пользователя» повторно не склоняется.

Полная морфология, склонение ФИО, определение рода и обработка новых исключений в этот релиз не входят. Подключение внешней библиотеки и вызов LLM не требуются.

### 3.4 Что не меняется

- Хранимое имя владельца и содержимое профиля.
- Голосовой сценарий и текст `meetingInstructions()`: задача ограничена видимой подписью и связанной идентификацией бота.
- Формат API, схема PostgreSQL и метаданные задания.
- Frontend.
- Уже начатые встречи: новая подпись применяется к вновь создаваемым ботам и заданиям, ретроактивного переименования нет.

## 4. Ошибки и совместимость

Новых сетевых вызовов и дополнительных точек отказа нет. Ошибки Attendee обрабатываются существующим кодом `attachBot()`.

При отсутствии `assistantDisplayName` в задании старого backend сохраняется прежний fallback. Поскольку `selfName` берётся из того же `displayName`, старая и новая схемы не расходятся внутри одного воркера.

Откат выполняется обратным коммитом и штатным деплоем. Миграции и очистка данных не нужны.

## 5. Тестирование

Разработка ведётся через red/green:

1. Сначала изменить регрессионный тест `attachBot`: ожидать «Андрей · ассистент Дмитрия». На исходном коде тест должен упасть, поскольку фактически отправляется «Дмитрий».
2. Добавить проверку с владельцем `Владимир`: в `AttendeeClient.createBot()` должен уйти `botName: 'Андрей · ассистент Владимира'`.
3. После реализации повторно прогнать `assistant-signature.spec.ts` и `meeting.service.spec.ts`.
4. Проверить по diff, что `selfName` ссылается непосредственно на `displayName`; прогнать тесты и сборку voice-host для проверки отсутствия регрессий и ошибок типов.
5. Прогнать backend build и целевые meeting-тесты на CI-ноде с `--maxWorkers=2`.

Тяжёлые Jest/build локально не запускаются. Используется CI-клон, зафиксированный на конкретном SHA.

## 6. Выкат и проверка

Выкат только штатной командой:

```bash
bash ~/Downloads/spirits_back/scripts/deploy.sh
```

После зелёных test/prod smoke проверить на test новую Attendee-встречу тестового аккаунта: в списке участников должно быть «Роман · ассистент <имя в родительном>». Платные или публичные внешние действия для проверки не добавляются.

## 7. Соответствие концепции

Изменение не затрагивает модель ассистанса, состав профиля, приватность или правила отправки данных с устройства. Используется имя, которое уже передаётся в существующий канал Attendee/LiveKit; меняется только его грамматическая форма в видимой подписи.

Новые персональные данные не собираются, новые внешние каналы публикации не создаются, сроки хранения и права доступа не меняются.
