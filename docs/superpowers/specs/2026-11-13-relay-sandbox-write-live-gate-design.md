# Живой гейт записи relay sandbox после обновления CLI

**Дата:** 2026-11-13  
**Статус:** подход одобрен владельцем

## Контекст и подтверждённая причина

После обновления relay sandbox runtime с Claude Code CLI `2.1.280` на `2.1.322` у пользователя веб-чата перестали сохраняться созданные документы. Исходный DOCX читался, но запись и в scratch, и в output завершалась `OSError: [Errno 30] Read-only file system`.

Один и тот же изолированный прогон с одинаковыми `buildSandboxSettings`, `buildCliEnv` и каталогами показал:

- CLI `2.1.322`: `EROFS` при записи `/tmp/agent-scratch/<fs_key>/claude-1002/probe.txt`; запись в `/tmp/agent-output/<fs_key>/probe.txt` у пользователя также завершалась `EROFS`;
- CLI `2.1.280`: обе записи и чтение результата успешны.

Следовательно, unit-проверка содержимого sandbox-настроек не может поймать эту регрессию: сами настройки корректны, различие возникает в исполнении выбранной версии CLI.

По разрешению владельца только `/opt/linkeon-agent/bin/claude-runtime` откачен на сохранённый `2.1.280` под lock/drain. Системный CLI и пользовательский launcher остались `2.1.322`. После отката прямой probe подтвердил `SCRATCH_OK=true OUTPUT_OK=true`; настоящий `/chat` завершился с `done.failed=false`, одним `outputFiles`, а `/files` вернул HTTP 200 с ожидаемым содержимым.

## Границы регрессии

Доказан сбой native CLI в relay sandbox. Нельзя автоматически распространять его на остальные runtime:

- три production-вызова backend Agent SDK либо разрешают только `Read`, либо задают `tools: []`; они не используют relay `sandbox.filesystem.allowWrite` и не дают этому пути `Bash`;
- `product-runner/src/claude.ts` вызывает CLI с `--permission-mode bypassPermissions`; границей изоляции там является Docker-контейнер продукта, а не sandbox-настройки relay.

Поэтому отдельные изменения Agent SDK и product images этим дизайном не откатываются и не блокируются. Повторный relay sandbox upgrade до `2.1.322` запрещён до зелёного живого гейта на другой, явно проверенной версии и нового разрешения владельца.

## Выбранный подход

Добавить обязательный живой regression test, который проверяет реальное поведение выбранного CLI, а не только сформированные настройки.

Рассмотренные альтернативы:

1. **Обязательный живой гейт — выбран.** Автоматически блокирует relay rollout и повторное открытие admission после смены runtime при `EROFS`, отсутствии файла или неверном содержимом.
2. **Только ручной smoke.** Проще, но зависит от памяти исполнителя и снова может быть пропущен.
3. **Только unit-тест настроек.** Не проверяет дефектный компонент и на `2.1.322` был бы ложно зелёным.

Цена выбранного подхода — один короткий Haiku-запрос на relay-host при выкате. Сбой API, авторизации или модели считается красным гейтом: его нельзя молча пропускать, поскольку иначе проверка перестанет быть обязательной.

## Компоненты

### 1. `relay-agent/sandbox-write-live.test.mjs`

Тест на `node:test`:

- по умолчанию пропускается; живой запуск включается только `RELAY_LIVE_CLI_WRITE_TEST=1`;
- принимает проверяемый бинарь через `RELAY_CLAUDE_BIN`, по умолчанию `/opt/linkeon-agent/bin/claude`;
- создаёт новый случайный `fs_key` и изолированные scratch/output-каталоги через существующие `ensureSessionDirs`, `buildSandboxSettings` и `buildCliEnv`;
- запускает выбранный CLI с `--model haiku`, пустым MCP и минимальным набором опций из реального relay-запуска;
- просит одной Bash-командой записать разные известные строки в `$TMPDIR/probe.txt` и `/tmp/agent-output/<fs_key>/probe.txt`;
- завершается успехом только при нулевом коде CLI и точном совпадении содержимого обоих файлов на хосте;
- при таймауте завершает собственный процесс CLI и считается красным;
- не печатает OAuth-данные, содержимое пользовательских файлов, системный промпт или секреты relay;
- не отключает и не ослабляет sandbox, не использует `dangerouslyDisableSandbox` и не обращается к данным существующих пользователей.

Прямая проверка CLI используется намеренно вместо `/chat`: во время смены runtime штатный drain обязан отклонять новые HTTP-ходы. Unit-тесты `server-sandbox.test.mjs` по-прежнему проверяют передачу настроек от relay к CLI; новый тест закрывает следующий компонент — исполнение этих настроек реальным бинарём.

### 2. Обязательный запуск в `scripts/deploy-relay.sh`

После обычного `node --test *.test.mjs` и до изменения живых файлов remote-часть дополнительно запускает:

```bash
RELAY_LIVE_CLI_WRITE_TEST=1 node --test sandbox-write-live.test.mjs
```

Красный результат останавливает rollout до замены живого дерева. Запуск происходит на relay-host, где доступны сохранённая Claude-авторизация и `/opt/linkeon-agent/bin/claude`. На Mac и CI без явной переменной тест пропускается; принудительно включать его вне подготовленного relay-host нельзя.

### 3. Обязательная проверка при смене runtime

`relay-agent/README.md` фиксирует команду, которую скрипт смены `claude-runtime` обязан выполнить после атомарного переключения и **до** снятия drain:

```bash
RELAY_LIVE_CLI_WRITE_TEST=1 \
RELAY_CLAUDE_BIN=/opt/linkeon-agent/bin/claude \
node --test /home/dv/file-agent/sandbox-write-live.test.mjs
```

При красном тесте runtime возвращается на прежний сохранённый бинарь, health проверяется повторно и только затем admission открывается. Версии `2.1.280` и `2.1.322` жёстко не прошиваются в сам тест: он обязан работать и для следующей исправленной версии.

## Проверки реализации

1. **RED:** живой тест с `RELAY_CLAUDE_BIN=/opt/linkeon-agent/bin/claude-runtime-2.1.322` падает и диагностирует отсутствие хотя бы одного probe-файла/`EROFS`.
2. **GREEN:** тот же тест с `RELAY_CLAUDE_BIN=/opt/linkeon-agent/bin/claude-runtime-2.1.280` проходит, оба содержимых совпадают.
3. Обычный `node --test *.test.mjs` без переменной живого запуска не вызывает Claude и не требует авторизации.
4. Полный relay suite и `bash -n scripts/deploy-relay.sh` зелёные на test-ноде.
5. Проверяется, что deploy script запускает живой гейт после unit suite и до первого изменения живых файлов.
6. Никакого выката или повторной смены runtime без отдельного разрешения владельца непосредственно перед действием.

## Откат

Откат изменения тестовой инфраструктуры — revert коммита и штатный `deploy-relay.sh` после отдельного разрешения. Активный sandbox runtime этим изменением не переключается. Уже выполненный аварийный откат runtime на `2.1.280` сохраняется.

## Соответствие концепции

Продуктовое поведение ассистентов, профиль, приватность и объём данных пользователя не меняются. Тест создаёт только синтетический случайный `fs_key` и два файла с известным техническим содержимым. Наружу отправляется лишь короткая синтетическая инструкция существующему Claude provider; документы, идентификаторы и переписка реальных пользователей в тест не попадают. Sandbox не ослабляется, а проверяется в исходной restrictive-конфигурации.
