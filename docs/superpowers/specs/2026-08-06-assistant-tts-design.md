# Озвучка ответов ассистентов (TTS) — дизайн

**Дата:** 2026-08-06
**Статус:** утверждён, готов к планированию реализации

## Задача

Дать ассистентам Linkeon (Роману и остальным) возможность озвучивать текст по просьбе
пользователя. Сейчас такой возможности нет ни у одного ассистента: в системном промпте
Романа про голос нет ни слова, а эвристика `detectMediaIntent()` в `chat.service.ts`
ловит только картинки и видео.

Голос не должен быть жёстко прибит к ассистенту. Через API любой ассистент может взять
любой голос из каталога, а пользователь может назначить каждому ассистенту свой голос
вручную.

Что уже есть в проде и переиспользуется:

| Компонент | Где | Что даёт |
|---|---|---|
| Yandex SpeechKit TTS | `worker/src/tts/yandex.ts` | синтез ru, ключи в `worker/.env` |
| OpenAI `tts-1` | `src/tg-bot/tg-voice.service.ts` | синтез любых языков, отдаёт opus |
| `StorageService` | `src/common/services/storage.service.ts` | заливка в MinIO, публичный URL |
| `LanguageService` | `src/common/services/language.service.ts` | `resolveUserLanguage(userId)` |
| `CHAT_TOOLS` | `src/chat/chat-tools.ts` | реестр инструментов + биллинг |
| `{{smm_video:id=…}}` | `src/utils/customMarkdown.tsx` (фронт) | механизм карточек в чате |
| `sendVoice` | `src/tg-bot/tg-grammy.client.ts` | голосовые в Telegram |

## Принятые решения

| Решение | Выбор | Причина |
|---|---|---|
| Способ вызова | инструмент `generate_speech` у ассистента | ложится в готовый паттерн `chat-tools.ts`, работает во всех клиентах, позволяет озвучить произвольный текст |
| Провайдер | Yandex для `ru`, OpenAI `tts-1` для остальных | Yandex вчетверо дешевле на русском, но SpeechKit не покрывает de/fr/es/zh |
| Цена | 1000 токенов за каждую начатую 1000 символов | маржа положительная на обоих провайдерах, цена не зависит от языка |
| Синхронность | синхронный синтез, без очереди джоб | 1–3 с на типичном ответе; очередь как у видео была бы оверинжинирингом |
| Охват | веб → Telegram → Flutter, тремя фазами | Flutter в отдельном репозитории с релизом через сторы |
| Голос | параметр `voice` в API + выбор пользователя + дефолт ассистента | ассистенту доступен весь каталог, у пользователя остаётся контроль |
| Область выбора | свой голос каждому ассистенту | у ассистентов разные персоны и пол; один голос на всех стёр бы различия |

Отклонённые варианты: асинхронная джоба с поллингом (три лишних слоя ради двух секунд);
стриминг без хранения (аудио теряется при перезагрузке, не годится для Telegram, нет кэша);
ElevenLabs везде (на порядок дороже); только Yandex (фича только для русскоязычных).

## Архитектура

Новый модуль `src/speech/`:

```
src/speech/
├── providers/yandex.ts      synthesize(text, voice, lang) → Buffer (MP3)
├── providers/openai.ts      synthesize(text, voice, lang) → Buffer (MP3)
├── voices.ts                каталог голосов + дефолты ассистентов + resolveVoice()
├── speech.service.ts        оркестрация: язык → провайдер → голос → кэш → синтез → MinIO → биллинг
├── speech.controller.ts     GET /webhook/speech/:id, GET /webhook/speech/voices
├── speech.module.ts
└── migrations/001_speech_clips.sql

scripts/generate-voice-samples.ts   разовая генерация превью в MinIO
```

`resolveVoice()` выносится отдельной чистой функцией: у неё четыре уровня приоритета и
валидация на каждом, это самая ошибкоопасная логика модуля и её надо тестировать без
сети и БД.

Адаптеры провайдеров **копируются** из `worker/src/tts/`, а не выносятся в общий пакет:
воркеру нужен сырой LPCM под ffmpeg-пайплайн Remotion, API нужен готовый MP3. Общая
абстракция над двумя разными требованиями стоила бы дороже дублирования ~50 строк.
Осознанный компромисс; при третьем потребителе TTS решение пересмотреть.

### Таблица `speech_clips`

```sql
CREATE TABLE speech_clips (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      TEXT NOT NULL,
  assistant_id TEXT,
  cache_key    TEXT NOT NULL,
  url          TEXT NOT NULL,
  duration_sec NUMERIC(6,2),
  chars        INTEGER NOT NULL,
  provider     TEXT NOT NULL,
  voice        TEXT NOT NULL,
  lang         TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX speech_clips_user_key ON speech_clips (user_id, cache_key);
```

`cache_key` = `sha256(text + voice + lang)`, не хэш одного текста: тот же текст другим
голосом обязан дать другой клип. Колонка называется `cache_key`, а не `text_hash`, именно
чтобы это не забылось при чтении схемы.

`user_id` — именно `TEXT`, не `varchar(20)`: у email/OAuth-пользователей идентификатор
это UUID на 36 символов, а не телефон.

Таблица решает три задачи: кэш, устойчивый `id` для маркера в истории чата, аналитика
расхода по провайдерам и голосам.

**Миграцию на прод накатывать через `psql` с ручным `INSERT` в `schema_migrations`** —
`npm run migrate` на проде застревает на `base/001` и ничего после неё не применяет.

### Контракт инструмента

```
generate_speech(text: string, voice?: string)

→ { ok: true, kind: 'audio', clipId, audioUrl, durationSec, chars, voice, tokensSpent, cached }
→ { ok: false, error: 'insufficient_tokens', balance, required }
→ { ok: false, error: 'text_too_long', maxChars: 5000 }
→ { ok: false, error: <текст ошибки провайдера> }
```

`voice` — любой id из каталога, без привязки к персоне и полу ассистента. Роман может
озвучить реплику женским голосом, а в одном ответе сделать несколько клипов разными
голосами — диалог, сценка по ролям, разные персонажи. Единственное ограничение —
совместимость голоса с провайдером, выбранным по языку пользователя.

Ни язык, ни `assistantId` параметрами инструмента не являются. Язык берётся из
`LanguageService.resolveUserLanguage()`, идентификатор ассистента — из `ToolContext`, где
он уже есть. Иначе модель сможет подставить чужого ассистента и получить не тот голос, а
пользователь — не то списание в аналитике.

В описании инструмента для модели указать: инструмент вызывается, когда пользователь просит
озвучить, наговорить, прочитать вслух; для нескольких голосов вызывать инструмент по разу
на каждую реплику, передавая нужный `voice`; ссылку на аудио самому не выдумывать — плеер
появляется у пользователя отдельной карточкой; при ошибке передать текст ошибки, не
утверждая, что аудио «готовится». Полный список доступных голосов с описанием тембра
включить в описание инструмента, иначе модель будет выдумывать несуществующие id.

### Поток данных (веб)

```
пользователь: «озвучь это»
  → ассистент вызывает generate_speech
  → SpeechService: язык → провайдер → кэш → синтез → MinIO → speech_clips → списание
  → tool_result { kind:'audio', clipId } стримится на фронт
  → ChatInterface дописывает в текст маркер {{audio:id=<uuid>}}
  → customMarkdown.tsx рендерит <AudioClip clipId=…>
  → AudioClip тянет GET /webhook/speech/:id и играет url
```

Маркер, а не прямой URL — чтобы плеер оживал из сохранённой истории чата. Точно так же
сейчас работают `{{smm_video:id=…}}` и `{{smm_scenario:id=…}}`.

## Голоса и языки

Правило выбора провайдера ровно одно: `lang === 'ru'` → Yandex, иначе → OpenAI.

### Каталог голосов

`voices.ts` содержит полный каталог обоих провайдеров: ~15 голосов Yandex (`alena`,
`filipp`, `ermil`, `jane`, `omazh`, `zahar`, `madirus`, `dasha`, `julia`, `lera`, `masha`,
`marina`, `alexander`, `kirill`, `anton`) и 6 OpenAI (`alloy`, `echo`, `fable`, `onyx`,
`nova`, `shimmer`). Каждая запись — `{ id, provider, gender, langs, title, description }`,
где `title` человекочитаем для UI, а `description` (тембр в двух словах) уходит в описание
инструмента для модели.

Точный список Yandex-голосов сверить с актуальной документацией SpeechKit на момент
реализации: состав и поддержка эмоций там меняются.

### Цепочка разрешения голоса

Сверху вниз, первый непустой выигрывает:

1. параметр `voice` в вызове `generate_speech` — ассистент берёт любой голос из каталога;
2. выбор пользователя для этого ассистента — `profile_data.assistant_voices[assistantId]`;
3. дефолт ассистента из карты ниже;
4. дефолт по полу: `zahar` / `onyx` для мужского, `alena` / `nova` для женского.

Валидация обязательна на каждом уровне: голос не из каталога или несовместимый с текущим
провайдером не роняет вызов, а откатывается на следующий уровень с записью в warn-лог.
Модель регулярно выдумывает id, которых не существует, а пользовательский выбор, сделанный
в русском интерфейсе, окажется невалидным после переключения на английский.

админ-UI ради этого не окупаются. Пользовательские переопределения при этом хранятся в БД —
в `profile_data`, см. ниже.

### Хранение выбора пользователя

`profile_data.assistant_voices` — объект вида `{ "12": "filipp", "2": "alena" }`, ключ это
`assistantId`. Кладём в существующий JSONB рядом с `language`, отдельную колонку не заводим —
язык там уже живёт по тому же принципу. Пишется через `PUT /webhook/profile-update`.

`GET /webhook/speech/voices` отдаёт каталог, отфильтрованный по языку пользователя: в
английском интерфейсе Yandex-голоса показывать бессмысленно, их всё равно не выберет
провайдер.

### Превью голосов

Одна и та же короткая фраза на каждый голос синтезируется скриптом единожды при деплое и
лежит в MinIO статикой (`speech-samples/<voice>.mp3`). Пользователь слушает образцы
бесплатно и мгновенно, провайдеру за открытие настроек не платим. Скрипт идемпотентен:
пропускает голоса, для которых сэмпл уже загружен.

**Известные ограничения, принятые сознательно:**

1. Тембр одного ассистента в русском и английском разный — плата за двух провайдеров.
2. `ru` здесь — язык интерфейса пользователя, а не язык конкретной реплики. Русскоязычный
   пользователь, попросивший озвучить английскую фразу, получит её с русской артикуляцией.
   Детект языка по тексту не делаем: он ошибается на коротких строках и на смеси языков,
   а это самый частый случай в чате.

## Биллинг, кэш, ограничители

**Цена:** `required = ceil(chars / 1000) * 1000` токенов. Потолок 5000 символов за вызов,
то есть не дороже 5000 токенов — столько же, сколько одна картинка.

**Порядок операций** (отличается от `generate_image`): проверка баланса → синтез →
списание после успеха. За упавшего провайдера пользователь не платит.

**Кэш:** ключ `cache_key = sha256(text + voice + lang)`, область — один пользователь. Попадание
возвращает существующий клип за 0 токенов с `cached: true`. Кэш пер-юзер, а не глобальный,
чтобы не возникало вопросов, почему один получил бесплатно оплаченное другим.

**Ограничители:**

- текст > 5000 символов → `text_too_long`, без молчаливой обрезки: пусть ассистент сам
  решит, сократить или озвучить частями;
- не более 20 синтезов в минуту на пользователя (счётчик в Redis) — страховка от
  зацикливания модели, не от человека. Лимит именно 20, а не 10: сценка по ролям — это
  десяток вызовов подряд в одном ответе, и она не должна упираться в потолок;
- один ретрай при сетевой ошибке провайдера, дальше `ok: false`. Фолбэка «Yandex упал →
  идём в OpenAI» нет: разный тембр на повторе звучит как баг, а не как спасение.

**`duration_sec`** пишется оценкой (символы / 15 в секунду): ни Yandex, ни OpenAI
длительность не возвращают, а `ffprobe` в API-процессе ради подписи под плеером не нужен —
точное время покажет сам аудио-тег.

**Retention** для клипов не вводим: минута MP3 около мегабайта.

## Фазы

### Фаза 1 — бэкенд + веб

- модуль `src/speech/`, миграция `speech_clips`, каталог голосов и `resolveVoice()`;
- `generate_speech` в `CHAT_TOOLS` + обработчик в `executeTool`;
- `GET /webhook/speech/voices`, сохранение `assistant_voices` через `PUT /webhook/profile-update`;
- скрипт превью-сэмплов, запускается один раз перед выкаткой;
- фронт: обработка `tool_result` в `ChatInterface`, маркер `{{audio:id=…}}` в
  `customMarkdown.tsx`, компонент `AudioClip` (play/pause, прогресс, время, скачать);
- фронт: выбор голоса на карточке ассистента — селект с превью (кнопка прослушивания
  играет статический сэмпл) и пунктом «по умолчанию», который очищает переопределение;
- строки через `t()` во всех шести локалях. Названия голосов в каталоге не переводим —
  это имена собственные; переводим только подписи UI.

### Фаза 2 — Telegram

Бот на `tool_result` с `kind: 'audio'` скачивает MP3 из MinIO, конвертирует в OGG/opus
через системный `ffmpeg` (в API-процессе он уже доступен — его вызывает
`voice-avatar.service.ts`) и шлёт `sendVoice`.

Конвертация нужна для обоих провайдеров, хотя OpenAI умеет отдавать opus сразу: в хранилище
клип лежит одним каноническим MP3 для веба и мобилки, и Telegram работает с тем же файлом.
Держать по два формата на клип ради экономии секунды ffmpeg не стоит.

В этой же фазе автоозвучка ответов в боте переключается со своего пути на `SpeechService`.
Сейчас бот озвучивает всех ассистентов голосом `alloy`, из-за чего Роман в Telegram и Роман
в вебе звучали бы по-разному.

**Изменение для существующих пользователей бота:** автоозвучка в TG сейчас идёт мимо
токенов; после переключения она станет платной по общему тарифу.

Своего UI выбора голоса в боте не делаем: `profile_data.assistant_voices` общий, поэтому
голос, назначенный в вебе, применяется и в Telegram. То же касается Flutter-приложения.

### Фаза 3 — Flutter

Отдельный репозиторий `~/Downloads/linkeon_mobile`, релиз через сторы. Клиент разбирает тот
же маркер и играет URL через `just_audio`. Бэкенд эту фазу не ждёт.

Учесть: в мобилке ещё не начата локализация (нет `flutter_localizations`, ~858 строк
захардкоженной кириллицы), поэтому подписи плеера там появятся на русском.

## Тестирование

Юнит-тесты на чистую логику:

- расчёт цены с округлением вверх (999 → 1000, 1001 → 2000, 5000 → 5000);
- выбор провайдера по языку;
- `resolveVoice()` — все четыре уровня приоритета по отдельности и во взаимодействии:
  явный `voice` перебивает выбор пользователя, выбор пользователя перебивает дефолт
  ассистента, неизвестный ассистент падает на дефолт по полу;
- откат при невалидном голосе: выдуманный моделью id и Yandex-голос при английском языке
  оба должны уводить на следующий уровень, а не ронять вызов;
- формирование ключа кэша, включая то, что смена голоса даёт другой ключ — иначе
  пользователь получит старую озвучку прежним голосом.

Интеграционно — по одному прогону на провайдера с реальным ключом: MP3 валиден и не нулевой
длины.

**Каждый чек проверяется в обе стороны.** Тест на `insufficient_tokens` должен краснеть,
если убрать проверку баланса; тест кэша — если всегда синтезировать заново; тест выбора
провайдера — если захардкодить одного. Зелёный прогон сам по себе ничего не доказывает.

## Деплой

Только `bash ~/Downloads/spirits_back/scripts/deploy.sh` без флагов: test → smoke →
prod → smoke. Перед деплоем убедиться, что `YANDEX_SPEECHKIT_API_KEY`, `YANDEX_TTS_FOLDER_ID`
и `OPENAI_API_KEY` есть в `.env` **основного API** (сейчас `YANDEX_TTS_FOLDER_ID` лежит
только в `worker/.env`), что миграция накачена через `psql`, и что скрипт превью-сэмплов
отработал — иначе селект голоса откроется с неиграющими кнопками прослушивания.
