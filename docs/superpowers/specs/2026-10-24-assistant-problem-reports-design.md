# Ассистенты сообщают о сбоях в «Поддержку linkeon» — дизайн

**Дата:** 2026-10-24
**Статус:** дизайн согласован владельцем; план — `docs/superpowers/plans/2026-10-24-assistant-problem-reports.md`
**Репозиторий:** `spirits_back` + одна строка в релее (`~/file-agent/server.mjs` на 5.101.115.184)

## Задача

24.10.2026 в 11:12 UTC Кира дважды не смогла сделать видео (`veo-3.1-fast`, потом `veo-3.1`): Google снял Veo 3.1, API отвечал 404 «model is no longer available». Токены вернулись, Кира честно сказала пользователю, что не вышло, — а команда не узнала ничего. Заметил владелец сам, потому что пробовал со своего аккаунта.

Почему промолчали алерты:

- `QualityMonitorService` поднимает тревогу по видео в двух случаях: в тексте ошибки есть balance/quota/insufficient/not enough/exceeded или за 120 минут упало не меньше 5 роликов и не меньше половины. «Модель снята» не подходит ни под одно условие, две попытки — меньше порога.
- `HealthProbeService` проверяет postgres, neo4j, anthropic и openrouter; видео не проверяет. (Пробовать по `GET models/<id>` бесполезно: для снятой Veo он отвечал 200 — падает только `predictLongRunning`.)
- Сказать команде что-либо у ассистентов нечем. Такой инструмент есть только у ИИ-поддержки во вкладке «Поддержка» (`escalate_to_owner`).

Владелец: «если ассистент обнаружил проблему — нужно сразу сообщать поддержке linkeon в телегу».

Попутная находка. С 18.05.2026 в `.env` прода нет `TELEGRAM_SUPPORT_CHAT_ID` (до этого — id группы «Поддержка linkeon», …2318; 503 доставки). `TelegramNotifierService` с тех пор пишет в лог «telegram not configured — skipping» — около тысячи раз. Среди пропущенного — пять эскалаций ИИ-поддержки от живых людей: 12.07 (high), 15.08 (high, «со вчерашнего дня не может пополнить токены»), 15.08 (normal) и др. Ответ пользователя в тикете уже имеет обход через `sendTelegramAlert`, эскалация — нет.

## Решения владельца (24.10.2026)

- **Оба пути.** А — платформа сама сообщает о каждом сбое инструмента Linkeon. Б — у ассистента есть инструмент «сообщить в поддержку» для того, что видит только он.
- **Приватность.** В группу уходит только служебное: ассистент, что не получилось, текст ошибки, id пользователя (как в остальных алертах). Разговор, запрос пользователя и профиль не уходят.
- **Эскалации ИИ-поддержки** снова доходят до группы (пункт «Эскалации» ниже).

## Куда уходят сообщения

`sendTelegramAlert` (`src/common/telegram-alert.ts`) — во все чаты `TELEGRAM_CHAT_ID`: группа «Поддержка linkeon» (…2318) и личка …1972. В личке бот заблокирован; отказ виден в логе как `not delivered`. Что делать с личкой — решение владельца, не этой работы.

## Модуль `src/problem-report/`

- `problem-classify.ts` — `isUserSideToolError(result)`: чистая функция, «виноват не сервис».
- `problem-format.ts` — тексты сообщений: чистые функции, HTML-экранирование, обрезка.
- `problem-report.service.ts` — `ProblemReportService`:
  - `reportToolFailure({ userId, assistantId, tool, result })` → `{ supportNotified: boolean }`. Решает синхронно, отправляет без ожидания.
  - `reportFromAssistant({ userId, channel, assistantId, assistantArg, kind, summary })` → `{ ok: true }` или `{ ok: false, error: 'rate_limited' | 'bad_input', say }`.
  - Склейка, счётчики и лимиты — в памяти процесса. `linkeon-api` — один экземпляр, так же устроены `QualityMonitorService` и `activeTurns`. Рестарт обнуляет память; худшее последствие — одно лишнее сообщение после выката.
- `problem-report.module.ts` — зависит только от `CommonModule` (`PgService`).

Кто вызывает: оба контроллера `McpModule` — `McpController` (путь А) и `ProductsMcpController` (путь Б). Ассистента хода они берут у `ChatService` (`McpModule` уже импортирует `ChatModule`) и передают в сервис id, а имя сервис достаёт сам. Направление зависимостей: `McpModule → ChatModule, ProblemReportModule`; `ProblemReportModule → CommonModule`. Цикла нет.

Настройки (`.env`, у всех есть значения по умолчанию):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PROBLEM_REPORT_COOLDOWN_MIN` | 60 | пауза между сообщениями об одном и том же сбое |
| `PROBLEM_REPORT_USER_HOURLY` | 3 | Б: сообщений от одного пользователя в час |
| `PROBLEM_REPORT_USER_DAILY` | 10 | Б: сообщений от одного пользователя в сутки |
| `PROBLEM_REPORT_GLOBAL_DAILY` | 50 | Б: сообщений всего в сутки |

## А. Автосообщение о сбое инструмента

### Где

`McpController` (`/mcp`), обработчик `tools/call`. Сразу после `executeTool`: если `result.ok === false`, контроллер зовёт `reportToolFailure`. Если тот вернул `supportNotified: true`, в результат до сериализации добавляются два поля (см. ниже). `isError` и сама ошибка не меняются.

`supportNotified: true` — для любого сбоя: и когда сообщение уходит, и когда оно склеено с уже отправленным (команда в курсе в обоих случаях). Но только если Telegram настроен (`telegramConfigured()`): иначе сообщить команде нечем, и ассистент не должен говорить «команда в курсе».

Через `/mcp` идут все инструменты Linkeon у ассистентов веба, приложений и мини-аппа — то есть у всех, кто работает через релей (все, кроме Маши): `generate_image`, `generate_banner`, `edit_image`, `compose_image`, `upscale_image`, `generate_video`, `generate_speech`, `manage_routine`, `propose_calendar_event`, `read_calendar`, `calculate_human_design`.

### Что не сообщаем: виноват не сервис

- Нехватка токенов: `error === 'insufficient_tokens'`.
- Проверка ввода и неверные аргументы модели: пустой промпт или текст (`empty prompt`, `empty text`, `empty_text`), нет обязательного поля (`… required`, `requires …`, «… обязателен», «Укажи …», «Нужен …»), значение вне правил (`must be`, `at least`, `at most`, `supports at most`, `unsupported video model`, `supports mode`, `length must be`, `text_too_long`, «не должен быть пустым», «максимум …», «Проверьте …», «… в будущем …»), неверная ссылка (`ссылка не принята: …` — страж SSRF), файл (`bad mime type`, `file too large`), неизвестный город расчёта бодиграфа (`CITY_ID_ERROR`).
- Лимиты самого пользователя: `too many concurrent jobs`, `rate_limited`, `own voice not ready`.
- Чужое или несуществующее: `job not found`, `not your job`.

Всё остальное — сбой: ошибка провайдера (как у Киры), таймаут, `tool execution failed`, `unknown tool: …`, «Инструмент расчёта временно недоступен…», `… is not configured`, «Модель не вернула изображений…», `tts failed`, ошибка базы.

Список — одна таблица в `problem-classify.ts`: точные коды плюс регулярки. Каждая известная строка ошибки инструментов закреплена тестом со своим классом. Ошибка на этой границе стоит дёшево в одну сторону (лишнее сообщение склеится) и дорого в другую (молчание) — поэтому неизвестное считается сбоем.

**Сверка — с началом сообщения** (уточнено ревью 24.10). Обёртки провайдеров кладут чужой текст после своего префикса («Omni generate failed: …», «Yandex TTS 400: …», текст OpenAI как есть), и поиск подстроки где угодно глушил бы настоящий сбой провайдера («… supports at most 2 reference images»). Поэтому начала наших сообщений сверяются через `startsWith`, а сообщения с переменной частью — регулярками от начала строки. По той же причине сбоем остаются «Проверьте дату и время рождения: …» (так hd-tool оборачивает любое исключение расчёта) и «limit reached» без хвоста «: не больше …» (это и 429 провайдера озвучки). Добавлены как «не сбой»: `Invalid time value` (модель передала время не в ISO — иначе ассистент сказал бы «команда в курсе» про собственную опечатку), выдуманный моделью адрес картинки (но не ответ 4xx по её ссылке: обычно она ведёт в наше хранилище MinIO, и 403/404 оттуда — наш сбой, например сбитая политика бакета после пересборки), отказ модерации Gemini (`IMAGE_SAFETY`, `PROHIBITED_CONTENT` и т. п.; `IMAGE_RECITATION` — по-прежнему сбой).

### Склейка

- **Подпись сбоя** — инструмент плюс нормализованная ошибка: нижний регистр, URL → `<url>`, UUID и длинные шестнадцатеричные id → `<id>`, числа → `#`, пробелы схлопнуты, первые 160 символов. Ассистент в подпись не входит: снятая модель у Киры и у Романа — один сбой.
- Новая подпись или прошло не меньше `PROBLEM_REPORT_COOLDOWN_MIN` с последнего сообщения по ней → сообщение уходит сразу.
- Внутри паузы — только счётчик повторов и множество пользователей.
- Следующее сообщение по той же подписи несёт строку «С прошлого сообщения: ещё N раз у M пользователей» (M — разные пользователи среди повторов).
- Подписи, по которым ничего не было больше суток, из памяти удаляются.
- Тестовые аккаунты не исключаются: сбой Киры поймал как раз аккаунт владельца.

### Текст

```
🛠 <b>Кира: не получилось создать видео</b>
Ошибка: <code>Veo generate failed: This model models/veo-3.1-fast-generate-preview is no longer available…</code>
Пользователь: <code>7900xxxxxxx</code>
С прошлого сообщения: ещё 4 раза у 3 пользователей        ← только если были повторы
```

Что не получилось — по инструменту: `generate_image` «создать картинку», `generate_banner` «сделать баннер», `edit_image` «изменить картинку», `compose_image` «совместить картинки», `upscale_image` «улучшить картинку», `generate_video` «создать видео», `generate_speech` «озвучить текст», `manage_routine` «настроить рутину», `propose_calendar_event` «предложить событие в календарь», `read_calendar` «прочитать календарь», `calculate_human_design` «рассчитать бодиграф»; незнакомый — «выполнить `<имя>`». Ошибка — до 300 символов.

Аргументы инструмента (промпт видео, текст озвучки, название события) в сообщение не попадают: форматтер их не получает вообще.

### Кто «Кира»

`ChatService.activeAssistantFor(userId)` — ассистент самого свежего хода этого пользователя из `activeTurns`; ход там открыт и в пути релея, и у Маши. Имя: по числовому id — `agents.display_name`, иначе `agents.name`; по `custom:<uuid>` — `custom_agents.name`. Хода нет (вызов пришёл вне хода) или имя не нашлось — «Ассистент».

### Что получает ассистент

К результату с ошибкой добавляется:

```json
"supportNotified": true,
"supportNote": "Команда Linkeon уже получила сообщение об этом сбое. Скажи пользователю простыми словами, что не получилось и что команда в курсе. Срок починки не обещай."
```

Подсказка идёт в результате, а не в промпте релея: так она не зависит от ручного выката релея и доходит до любого клиента `/mcp` одинаково. Довод был и сильнее: до 24.10 12:41 UTC продолженные сессии релея получали замороженный снимок промпта и описаний инструментов (CLI 2.1.280 шлёт при `--resume` `prompt_snapshot`, проверено сессией spirits-front-4a). С этого момента там включён `--system-prompt-snapshot off` (коммит релея `a2718c9`), но результат инструмента остаётся самым надёжным местом.

## Б. Инструмент `report_problem`

### Где

Точка «Продуктов» `/webhook/mcp/products` (`ProductsMcpController`), в обоих каналах (`web`, `telegram`), рядом с `find_files`. Почему здесь, а не на `/mcp`:

- её получают все: ассистенты веба через релей (`productsRelayFields` — «шлётся ВСЕГДА, всем ассистентам»), Маша (локальный CLI) и TG-боты, когда в чате только владелец;
- пользователь и канал берутся из подписанного токена, модель их не подделает. На `/mcp` `userId` пишет модель.

Полное имя у модели — `mcp__products__report_problem`.

### Схема

- `assistant` (строка, обязательно) — твоё имя как ассистента;
- `kind` — `my_failure` (сломалось у меня) или `user_report` (пользователь говорит, что что-то в Linkeon не работает);
- `summary` (строка, обязательно) — 1–3 предложения, до 500 символов.

`userId` и `channel` из аргументов выбрасываются, как у остальных инструментов точки.

Имя в сообщении — ассистент хода из `activeTurns`, если ход есть (веб, Маша). Иначе (TG-бот) — аргумент `assistant`, обрезанный до 40 символов.

### Описание инструмента (когда звать)

Суть, которую несёт описание:

- Вызывай, когда не можешь выполнить просьбу пользователя из-за поломки, которую сам не исправишь:
  - `my_failure` — сломалось у тебя: программа или конвертация падает раз за разом, файл не обрабатывается из-за ошибки окружения, нужного модуля нет, инструмент вернул бессмыслицу;
  - `user_report` — пользователь говорит, что в Linkeon что-то не работает: оплата, кнопка, экран, не пришло видео.
- Не вызывай:
  - при ошибке инструмента Linkeon с `supportNotified: true` — команда уже знает;
  - при нехватке токенов;
  - при ошибке самого пользователя;
  - при отказе по соображениям безопасности;
  - повторно о той же проблеме в этом разговоре.
- В `summary` — что сломалось и что ты пробовал, своими словами. Без имени, телефона, почты, адресов и без пересказа разговора.
- После вызова скажи пользователю, что передал(а) проблему команде. Если вернулся `rate_limited` — предложи написать во вкладку «Поддержка».

В промпте релея — две строки в блоке `PRODUCTS_PROMPT`: явное исключение для `mcp__products__report_problem` из правила «только `mcp__linkeon__*`» (так же сделано для `manage_product` и `find_files`; без него модель может счесть инструмент запрещённым) и отсылка к описанию инструмента. Всё остальное, что нужно модели, — в описании. (Уточнено при планировании 24.10: первая редакция спеки считала, что промпт релея не меняется.)

### Лимиты

- на пользователя: `PROBLEM_REPORT_USER_HOURLY` в час, `PROBLEM_REPORT_USER_DAILY` в сутки;
- всего: `PROBLEM_REPORT_GLOBAL_DAILY` в сутки;
- окна скользящие: последний час и последние 24 часа;
- сверх — `{ ok: false, error: 'rate_limited', say: 'Сообщений в поддержку сейчас слишком много. Предложи пользователю написать во вкладку «Поддержка».' }`, в группу ничего не уходит;
- пустой `summary` или неизвестный `kind` → `{ ok: false, error: 'bad_input', say: 'Опиши проблему в summary (1–3 предложения) и укажи kind: my_failure или user_report.' }`;
- Telegram не настроен → `{ ok: false, error: 'not_configured', say: 'Передать команде сейчас нечем. Предложи пользователю написать во вкладку «Поддержка».' }`: ассистент не должен говорить «передал(а)», если передать было некуда.

Склейки по подписи у Б нет: одна и та же проблема в пересказе модели каждый раз звучит по-разному. Шум держат лимиты и правило «один раз за разговор».

### Текст

```
🙋 <b>Кира: у меня не работает</b>              ← my_failure
🙋 <b>Кира передаёт жалобу пользователя</b>      ← user_report
«Не получается собрать презентацию: LibreOffice падает при конвертации в PDF»
Пользователь: <code>7900xxxxxxx</code> · веб       ← telegram → «Telegram»
```

### Разрешение вызова

Без имени в `allowedTools` вызов в `-p` отклоняется:

- релей: `mcp__products__report_problem` дописывается в строку `PRODUCTS_TOOLS` в `~/file-agent/server.mjs`, плюс две строки в `PRODUCTS_PROMPT` (см. выше). Копия файла в репозитории (`relay-agent/server.mjs`) обновляется до живой версии с этой правкой. Выкат ручной (коммит в `~/file-agent`, `node --check`, `pm2 restart file-agent` в момент без дочерних `claude`); перед правкой — сверить `git log` и `git status` в `~/file-agent`: 24.10 там же работала сессия spirits-front-4a;
- Маша: `allowedTools` в `chat.service.ts`;
- TG-бот: `allowedTools` в `tg-router.service.ts` — только когда инструмент продуктов выдан (владелец в чате один).

Имя — константа рядом с `PRODUCTS_CLI_TOOL_NAME` в `src/products/products-cli-tool.ts`.

С 24.10 12:41 UTC на релее включён `--system-prompt-snapshot off` (`a2718c9`): продолженные сессии получают текущие описания инструментов, так что новый инструмент увидят и они, а не только новые разговоры.

## Эскалации ИИ-поддержки — снова в группе

`TelegramNotifierService.notifyEscalation`: если `TELEGRAM_SUPPORT_CHAT_ID` пуст, тот же текст с кнопкой «Открыть тикет» уходит через `sendTelegramPayload` (фанаут по `TELEGRAM_CHAT_ID`). Так уже сделано для ответа пользователя в тикете (`SupportService.notifyOwnerOfUserReply`); там ничего не меняем, чтобы ответ не ушёл дважды.

`notifyHealthAlert` не трогаем: обход дал бы около четырёх ложных сообщений в день о плановом обновлении OAuth (`anthropic healthy → degraded → healthy`). Возвращать ли `TELEGRAM_SUPPORT_CHAT_ID` в `.env` — решение владельца, не этой работы.

## Ошибки

- Отправка не задерживает и не роняет ответ инструмента: решение — синхронное и в памяти, отправка и поиск имени ассистента — без ожидания. Ошибка Telegram или базы — предупреждение в лог.
- Telegram не настроен (`telegramConfigured()` ложно, как на test) — текст сообщения пишется в лог одной строкой `problem-report: …`; склейка и лимиты работают как на проде.
- Не нашлось имени ассистента — «Ассистент».

## Соответствие концепции

- **§1 «Облачный ИИ — stateless-исполнитель, сервер — слепое реле»; §2.5 и §4.2.2 — что уходит наружу.** В Telegram уходит только служебное о сбое: какой ассистент, какой инструмент, текст ошибки, id пользователя. Разговор, запрос (промпт видео, текст озвучки), профиль не уходят — решение владельца 24.10. Соответствует.
- **Текст ошибки провайдера** в принципе может повторить кусок запроса (например, отказ фильтра безопасности). Обрезаем до 300 символов; известные тексты Google (Veo, Gemini) запрос не цитируют. Остаточный риск принят: адресат — внутренняя группа команды.
- **`summary` в Б пишет модель.** Ей запрещено включать личные данные и пересказ разговора; длина до 500, экранирование. Это просьба к модели, а не гарантия. Остаточный риск принят на тех же основаниях.
- **§1 «Прерывать — только по явной просьбе».** Пользователь не получает новых уведомлений: ассистент говорит «команда в курсе» только в ответ на уже случившийся у него сбой. Соответствует.
- **id пользователя** — существующая практика алертов («Дорогой ход», рост стоимости): ключ записи, а не данные профиля.

## Проверки

**До выката** — jest на ноде (сузить `--testPathPattern`), плюс `tsc -p tsconfig.build.json`: jest бэка типы не проверяет.

- Классификатор: строка ошибки Киры, «Модель не вернула изображений…», `tts failed`, «Инструмент расчёта временно недоступен…», `… is not configured`, `tool execution failed`, `unknown tool: x` → сбой; `insufficient_tokens`, `empty prompt`, «title обязателен», «Укажи ровно один способ…», `Veo length must be 4–60 seconds`, `too many concurrent jobs`, `text_too_long`, `rate_limited`, «ссылка не принята: …», `CITY_ID_ERROR`, «Проверьте дату рождения…» → не сбой.
- Склейка: первое сообщение сразу; повтор в паузе — без сообщения, со счётчиком; после паузы — сообщение со строкой «ещё N раз у M»; разные инструменты и разные ошибки не склеиваются; цифры и id в ошибке не плодят подписи.
- Формат: экранирование `<`, `>`, `&`; обрезка; имя по инструменту; незнакомый инструмент.
- `McpController`: сбой → `supportNotified` и `supportNote` в JSON результата и вызов отправки; не-сбой и успех → без полей и без отправки; ответ не ждёт отправки (отправка висит — ответ уходит).
- `ProductsMcpController`: `report_problem` в списке обоих каналов; `userId` из аргументов игнорируется; лимиты (четвёртое за час — `rate_limited`, в группу ничего); `bad_input`.
- `allowedTools` Маши и TG-бота содержат имя инструмента.
- `notifyEscalation` без `TELEGRAM_SUPPORT_CHAT_ID` → `sendTelegramPayload` с кнопкой; с ним — прежний путь.

**После выката** — прод, тестовый аккаунт, с OK владельца:

- Б: вызов `report_problem` на точке продуктов с подписанным токеном тестового аккаунта → одно сообщение в группе; в `summary` — пометка «проверка выката».
- А: вызов `ProblemReportService.reportToolFailure` из `dist` с синтетической ошибкой «проверка выката» → одно сообщение; немедленный повтор — тишина.
- Эскалация: вызов `notifyEscalation` из `dist` с пометкой «проверка выката» → сообщение с кнопкой в группе.
- Релей, после правки `PRODUCTS_TOOLS`: новый разговор тестового аккаунта с ассистентом, просьба сообщить в поддержку о выдуманной поломке с пометкой «проверка» → сообщение в группе.
