# Загрузки пользователя: «Медиа/Файлы», доступ ассистента, комментарии и удаление — дизайн

Дата: 2026-11-16
Статус: согласовано с владельцем по частям 16.11.2026; спека ждёт его ревью.
Основа: `2026-11-13-chat-upload-memory-design.md` («Память загрузок»: реестр `chat_uploads`, приватный bucket `linkeon-chat-uploads`, флаг `CHAT_UPLOADS_ENABLED`); рядом — `2026-11-11-relay-session-upload-directory-design.md` и `2026-11-11-account-deletion-cleanup-design.md` (адаптеры удаления).

## Задача

Требования владельца:
1. Каждый файл, загруженный пользователем, хранится и виден в панели переписки: картинки и видео — во вкладке «Медиа», остальное — во вкладке «Файлы».
2. Ассистент дотягивается до этих файлов всегда: в следующих ходах и в любой переписке пользователя.
3. Поработав с файлом, ассистент сам оставляет к нему комментарий, чтобы потом к файлу можно было быстро вернуться.
4. Пользователь может удалить свой файл через интерфейс.

Согласованные решения:
- **Доступ.** Ассистенту доступны все файлы пользователя из любых переписок. В панели каждой переписки показываются её собственные файлы.
- **Каналы.** Очередь 1: веб, оба приложения (Capacitor и Flutter), PDF, которые Маша разбирает через scan-document. Очередь 2: личка с Telegram-ботами.
- **Комментарий.** Ассистент пишет его сам после каждой работы с файлом.
- **Подход A.** Достраиваем «Память загрузок» и храним файлы приватно. Отклонены: B — публичный bucket, при нём файлы открываются любому, у кого есть ссылка; C — отдельная общая библиотека файлов, она даёт лишнюю работу с интерфейсом без пользы для требований.
- **Удаление отдельного файла** из панели входит в очередь 1.

## Что уже есть и чего не хватает (origin/main 16bb9736)

**Есть:**
- реестр `chat_uploads` (`src/chat/chat-uploads/migrations/001_chat_uploads.sql`) с полями: id, user_id, session_id, original_name, mime, size_bytes, sha256, storage_key, created_at;
- байты файлов в приватном bucket `linkeon-chat-uploads`;
- `ChatUploadsService.saveOriginals`, его вызывает только `/webhook/agent/upload-and-chat` — это веб и оба приложения;
- скачивание владельцем `GET /webhook/chat-uploads/:id` по JWT; ассистент скачивает по подписи `?exp&sig` (HMAC, срок 1 ч);
- блок «Earlier user uploads»: до 10 последних файлов сессии в каждом ходе, только имя и подписанная ссылка;
- `find_files` с `origin=upload`: ищет по всем перепискам пользователя, но по загрузкам — только по имени;
- удаление вместе с аккаунтом через конвейер `chat-upload.purge` (`chat-upload-account-deletion.adapter.ts`);
- флаг `CHAT_UPLOADS_ENABLED`, по умолчанию выключен. На проде флага нет, `chat_uploads` пуста.

**Не хватает:**
- **Панель.** Панель (`GET /webhook/chat/files`, `chat-files.service.ts` → `listForSession`, `SESSION_FILES_SQL`) читает только строки `sender_type='ai'`, а `extract.ts` принимает только «наши» абсолютные URL с расширением. Загрузки в панель не попадают ни при каком положении флага.
- **Превью во фронте.** Фронт (`ChatFilesPanel.tsx`, `MediaViewer.tsx`) показывает превью простым `<img src>` без авторизации, поэтому приватный адрес он не откроет.
- **PDF Маши.** Ход `scan-document` (`chat.controller.ts`, `@Post('scan-document')`) файл не сохраняет. Кроме того, у Маши в ходах нет блока загрузок: её отдельная ветка в `chat.service.ts` — «Маша-only путь (agent.id === 3)».
- **Комментарии.** Их нет нигде, как и инструмента, через который ассистент мог бы записать что-то о файле.
- **Загрузки как исходник.** Инструменты картинок (`misc.service.ts`: `fetchImageAsBase64` → `fetchMediaBytes`, до 8 МБ) берут исходник только по внешнему URL. Подписанная ссылка на загрузку не проверялась.
- **Telegram.** Файлы из бота лежат 7 дней в `~/.linkeon/tg-workspace` (`tg-bot.service.ts`, `downloadIncomingAttachments`), в реестр они не попадают. Инструмента `find_files` в Telegram нет.

## Дизайн

### 1. Хранение (очередь 1)

**Включение.** Включаем флаг `CHAT_UPLOADS_ENABLED=true` по чек-листу из CLAUDE.md бэка:
1. bucket `linkeon-chat-uploads` вписать в политику MinIO `smm-rw`;
2. добавить его в `BUCKETS` скрипта `minio-mirror.sh` (DR-зеркало на node-3);
3. поставить флаг в `.env`;
4. перезапустить API, когда нет живых ходов и звонков.

Порядок — сначала test, потом прод. Каждый шаг выполняется с OK владельца.

**Каналы очереди 1:**
- `upload-and-chat` — сохраняет файлы и сейчас, его не меняем;
- `scan-document` — добавляется вызов `saveOriginals` для PDF. Сессия та же, что у переписки с Машей: обычная `<userId>_3` или fresh-сессия «Чистого листа», если она активна. Точную привязку план сверяет с тем, как ключ сессии вычисляет `scan-document`. Сбой сохранения ход не прерывает — как в `upload-and-chat`.

**Миграция `002`** добавляет в `chat_uploads` поля (все nullable или с default, старые строки остаются валидными):
- `source text NOT NULL DEFAULT 'web' CHECK (source IN ('web','scan','telegram'))` — откуда пришёл файл, для пометки «из Telegram»;
- `thumb_key text NULL` — ключ миниатюры в том же приватном bucket;
- `note text NULL CHECK (char_length(note) <= 500)`, `note_updated_at timestamptz NULL`, `note_assistant_id text NULL` — комментарий ассистента (см. раздел 2).

**Миниатюры.** Для `image/*` при сохранении создаётся webp с длинной стороной не больше 480 px. Делается на `sharp`, переиспользуя `src/chat/chat-files/thumbnails.ts`. Ключ — `thumbs/<storage_key>.webp`, лежит в том же bucket. Если миниатюра не получилась (повреждённый файл, HEIC без кодека), сохранение файла всё равно проходит, `thumb_key` остаётся NULL, и фронт рисует значок. У видео миниатюр нет, показывается значок.

**Ничего не теряется.** Панель читает реестр, а не текст переписки. Поэтому файл, досохранённый после 20-секундного бюджета `saveOriginals`, и файл из хода с пустым ответом ассистента всё равно появляются в панели.

**Удаление файла.** `DELETE /webhook/chat-uploads/:id`, только владелец по JWT. Без валидного access-токена (нет его, истёк, refresh-токен, токен инструмента продуктов) ответ 401, сервис не вызывается: `apiClient` фронта обновляет токен и повторяет запрос только на 401. С валидным токеном на чужой или несуществующий id — 404 без раскрытия, существует ли запись. Успех — 204. Подпись ассистента (`exp&sig`) для удаления не принимается: удаляет только сам пользователь, ассистент — никогда. Порядок:
1. Удаляются объекты MinIO: оригинал и миниатюра. NotFound терпим. Любая другая ошибка даёт 502, строка остаётся, повтор безопасен.
2. `DELETE FROM chat_uploads WHERE id=$1 AND user_id=$2`. Вместе со строкой уходит и комментарий.
3. В `custom_chat_history` этого пользователя строка `📎 [<имя>](/webhook/chat-uploads/<id>)` заменяется на `📎 <имя> — <«файл удалён» на языке профиля, по умолчанию ru>`.

После удаления файл пропадает из панели, из блока загрузок и из `find_files`, а подписанные ссылки на него отдают 404.

**Сколько хранится.** Файл живёт, пока его не удалит пользователь или пока не удалён аккаунт (`chat-upload.purge`). Очистка переписки (`DELETE /webhook/chat/history`) файлы не трогает: они остаются в панели, и удалить их можно там.

**Удаление аккаунта.** Новых мест хранения ссылок не появляется: комментарий лежит в той же строке. Появляется новый вид объектов — миниатюры. Поэтому `chat-upload.purge` дополняется удалением `thumb_key`; его spec, snapshot и drift-guard держим зелёными, а pg-спеки гоняем на одноразовой БД. Номера коммитов, задевающих адаптер или каталог удаления, передаём сессии, которая ведёт удаление аккаунтов (перед её Gate D).

### 2. Доступ ассистента и комментарии

**Комментарий.** Новый инструмент `note_file` — на том же защищённом MCP-сервере `products`, что и `find_files`. Полное имя — `mcp__products__note_file`. Маше он отдаётся через локальный CLI (`products-cli-tool.ts`), Telegram получает его в очереди 2.
- Вход: `{ file_id: uuid, note: string, 1…500 символов }`.
- Владелец берётся из подписи токена хода, аргумента `userId` нет.
- Комментарий пишется только к загрузкам этого пользователя; чужой или несуществующий `file_id` — ошибка «файл не найден».
- Новый комментарий заменяет старый, в `note_assistant_id` записывается ассистент хода.
- Описание инструмента: «Поработав с загруженным пользователем файлом, оставь 1–3 предложения: что в нём и что вы решили или сделали. Важное из прежнего комментария сохрани. Не пиши в комментарий паролей, номеров документов и прочих чувствительных данных».

**Блок загрузок в каждом ходе.** `assistantBlock` выводит для каждого файла строку из `id`, имени, вида, даты и комментария. Если комментария нет, в строке стоит «нет — оставь его через note_file после работы с файлом». Подписанная ссылка остаётся только для ассистента, как и сейчас. Блок появляется и в ходах Маши, в её отдельной ветке.

**Поиск `find_files`:**
- по загрузкам ищется не только имя, но и комментарий: +3 очка за слово в имени, +2 за слово в комментарии;
- в результате для `origin=upload` поле `note` — это комментарий файла, и появляется поле `id`, чтобы передать его в `note_file`;
- описание инструмента сообщает про поиск по комментариям.

**Загрузки как исходник для картинок и видео.** В `misc.service.ts` (`fetchImageAsBase64` и места, где собираются `sourceImageUrl(s)`) адрес загрузки распознаётся в любом виде: относительный `/webhook/chat-uploads/<id>` или абсолютный на нашем домене, с подписью или без. Такой файл читается прямо из хранилища с проверкой, что он принадлежит пользователю хода. Ограничения прежние: не больше 8 МБ, только `image/*`.

Так работают `edit_image`, `upscale_image`, `compose_image` и `generate_video` в режиме image2video. В описаниях этих инструментов добавлено: «можно передать url загрузки пользователя из find_files или из блока загрузок».

**Границы.** Ассистент видит только загрузки пользователя текущего хода: владелец всегда берётся из токена хода.

### 3. Панель «Медиа/Файлы»

**Бэк.** `GET /webhook/chat/files` (`listForSession`) к файлам ассистента, как и раньше, добавляет загрузки этой сессии из `chat_uploads`. Порядок — от новых к старым, не больше 500 штук. Поля элемента:
- `key: upload:<id>`;
- `kind` по mime и расширению: image, video, document или audio;
- `name`, `ext`, `createdAt`;
- `url: /webhook/chat-uploads/<id>`;
- `thumbUrl: /webhook/chat-uploads/<id>/thumb`, если есть `thumb_key`;
- `stored: true`;
- новые поля `origin: 'upload'`, `source`, `note`.

Новый маршрут `GET /webhook/chat-uploads/:id/thumb` отдаёт миниатюру (`image/webp`, `inline`, `private, no-store`) только владельцу по JWT. Без валидного access-токена — 401 (`apiClient` фронта на 401 обновляет токен и повторяет запрос); подпись ассистента здесь не принимается. С валидным токеном чужой или несуществующий id, а также запись без миниатюры — 404.

**Фронт (`src/components/chat/files/`):**
- `chatFiles.ts`: в типы добавляются `origin`, `source`, `note`.
- Раскладка `splitTab` не меняется: image и video идут в «Медиа», остальное — в «Файлы».
- `ChatFilesPanel.tsx`, плитки загрузок:
  - превью и миниатюра загружаются запросом с JWT в blob (`URL.createObjectURL`), при размонтировании revoke;
  - пометка «загрузили вы» или «из Telegram»;
  - под плиткой комментарий, обрезанный до 2 строк;
  - действия: открыть, скачать (`openChatUpload` из `chatUploads.tsx`, уже с JWT) и «Удалить» с подтверждением «Удалить файл? Ассистенты больше не смогут его открыть». После удаления плитка убирается из списка.
- `MediaViewer.tsx`: показывает blob-источник для загрузок и полный комментарий.
- Локали: новые ключи на всех языках, текст пустой панели меняется на «…и которые вы загрузите». Правится `filesLocales.test.ts`, в нём `pt` проверяется целиком.
- Тесты, которые закрепляли прежнее поведение, правятся осознанно: `chat-files.service.spec.ts` (сейчас «только ai»), `ChatFilesPanel.test.tsx`, `MediaViewer.test.tsx`.

**Приложения.** Приложение на Capacitor использует тот же фронт и получает всё сразу. У Flutter-приложения своя вёрстка: хранение и доступ ассистента заработают через общий бэк, а показ загрузок в его интерфейсе — отдельная задача в репозитории `linkeon_mobile`. В эту спеку она не входит.

«Не сохранились» — старые файлы, которые жили только на релее, — показываются как раньше.

### 4. Telegram (очередь 2)

**Какие чаты:**
- только личка с ботом и только пользователи, привязанные к аккаунту Linkeon (`identity.getLinkeonIdByTgUserId`; непривязанным бот и сейчас не отвечает);
- группы не сохраняются: там файлы присылают разные люди, и чужим фото не место в кабинете владельца бота. В группах остаётся рабочая папка на 7 дней;
- боты продуктов для клиентов не меняются.

**Сохранение.** Каждое фото (самый большой размер) и каждый документ из лички, включая альбомы (`albumParts`), уходят в `saveOriginals` с `source='telegram'`. Сессия — `<ownerId>_<assistantId>` из конфигурации чата (`configs.ensurePrivateConfig`). Предел — 20 МБ, это ограничение Telegram (`MAX_ATTACHMENT_BYTES`).

**Где видно.** В веб-кабинете, в панели переписки с тем же ассистентом, с пометкой «из Telegram». Удаление — там же.

**Ассистент в Telegram** получает блок загрузок, `find_files` и `note_file`, а также загрузки как исходник для картинок. Как именно подключить инструменты к Telegram (`products-cli-tool.ts` и правило «TG — только владелец» для продуктовых инструментов), решает отдельный план очереди 2 после приёмки очереди 1.

**Удаление аккаунта.** Загрузки из Telegram лежат в `chat_uploads`, поэтому их покрывает `chat-upload.purge`. `tg-account-deletion.adapter.ts` при этом не меняется.

### 5. Выкат и проверки

**Порядок:**
1. Реализуется очередь 1.
2. Чек-лист и флаг на test, приёмка на test.
3. Чек-лист и флаг на проде, перезапуск API при нуле ходов — с OK владельца.
4. Приёмка владельцем.
5. Затем отдельный план и выкат очереди 2.

**Автотесты** (бэк — unit-тесты и pg-спеки на одноразовой БД; фронт — vitest под Node 22; всё гоняется на тест-ноде):
- миграция `002`;
- `saveOriginals` с миниатюрой и без неё (повреждённая картинка);
- сохранение из `scan-document`;
- `DELETE` загрузки: только владелец, 404 чужому, сбой MinIO даёт 502 и строка остаётся, переписывание строки в истории;
- маршрут `thumb`;
- `note_file`: только свои, длина, замена;
- поиск `find_files` по комментарию и поле `id`;
- блок загрузок с комментарием, в том числе у Маши;
- `misc.service`: исходник из загрузки, чужая загрузка отклоняется;
- `listForSession` с загрузками;
- фронт: плитки, blob-превью, удаление, локали;
- адаптер `chat-upload.purge` с миниатюрами.

**Живой проход** с тестового аккаунта 70000000000, в новой fresh-сессии:
1. Загрузить фото — оно появляется в «Медиа» с миниатюрой и пометкой.
2. Ассистент оставляет комментарий.
3. В новом сообщении спросить «где фото гостиной?» — ассистент находит файл по комментарию и делает по нему картинку через `edit_image`.
4. Удалить фото — оно исчезает из панели, ассистент его больше не открывает, а в переписке стоит «файл удалён».
5. Отдельно — PDF у Маши.

**Справка ассистентов.** В `src/platform-kb/articles/chat.ts` убрать фразу «Загруженное человеком туда не попадает» и описать загрузки, комментарии и удаление. Если подписи кнопок изменятся, перезапустить `scripts/sync-kb-labels.mjs`.

**После выката.** В отчёт идёт объём bucket `linkeon-chat-uploads` на проде и в DR-зеркале на node-3.

## Не делаем

- удаление файлов, созданных ассистентами, и комментарии к ним;
- правку комментария человеком;
- поиск по содержимому файлов (OCR и текст документов) — только имя и комментарий;
- общую библиотеку файлов вне переписок;
- интерфейс Flutter;
- группы Telegram и ботов продуктов;
- бэкфилл: старые загрузки нигде не сохранились;
- дедуп по sha256;
- шифрование (как и в базовой спеке).

## Риски и известные ограничения

- **Место.** Фото копятся: следим за объёмом bucket и зеркала. Автоочистки нет, это решение владельца.
- **Временная копия на релее.** После удаления файла его копия в `/tmp/agent-uploads/<fs_key>/` живёт до очистки `/tmp` (до 30 дней), как и сейчас. Доступа к ней через наши адреса нет, но удаление «мгновенно отовсюду» сейчас не гарантируется.
- **HEIC и редкие форматы.** Миниатюра может не получиться — тогда в панели будет значок. Сам файл и доступ ассистента к нему от этого не страдают.
- **Срок подписи.** Подпись для ассистента живёт 1 час, как и сейчас. В долгом ходе ссылку обновляет повторный `find_files`.
- **Комментарий как канал подсказок.** Комментарий пишет модель после чтения непроверенного файла и затем видит его в блоке загрузок каждый ход — это долгоживущий канал для подсказок из файла. Смягчение: ≤500 символов, чистка управляющих и bidi, одна строка в блоке, только свои файлы, текст виден пользователю.
