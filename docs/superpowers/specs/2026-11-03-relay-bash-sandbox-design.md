# Изоляция Bash ассистентов на релее (часть В «номер вне промптов»)

> Дата: 03.11.2026. Владелец: «Начать: спека и план», «Да, можно» (системные правки),
> «Интернет да, внутреннее нет», «А: песочница + запреты».
> Расширяет `2026-11-02-pii-out-of-prompts-design.md` (там это была «часть В»).

## Задача

CLI ассистентов (`claude --print`) на релее `dv@5.101.115.184` запускается под
пользователем `dv`, у которого `NOPASSWD: ALL`. Bash ассистентов ограничен только
PreToolUse-хуком со списком запрещённых шаблонов (обходится переформулировкой).
Ассистент может прочитать: `~/file-agent/sessions.json` (ключи с телефонами),
pm2-журналы, `~/.claude/.credentials.json`, ключи Gemini/OpenRouter/Qwen/Kimi из
окружения CLI, `~/.ssh/id_rsa`, файлы чужих проектов и папки других сессий
`/tmp/agent-output/<fs_key>` (каталог 0755 — список виден), а через `sudo` —
обойти любое ограничение. Кроме того, конфиги MCP с жетоном хода лежат в общем
`/tmp` и читаются любым ассистентом (`mcp__linkeon__*` можно вызвать от чужого
пользователя).

На проде (бэкенд) встроенные инструменты CLI по умолчанию выключены
(`--tools` без аргумента; максимум один вызов с `tools: 'Read'`), Bash там нет.
Поэтому спека касается только релея.

## Решение (подход А: штатная песочница Claude Code + запреты)

Песочница bubblewrap закрывает только Bash. Файловые инструменты (Read/Glob/
Grep/Write/Edit) ограничиваются отдельно — через `--allowedTools` (список
разрешённого, вместо `*`) и запреты в `permissions.deny` (запрет сильнее
разрешения, работает в `--print`). Имя пользователя в описании инструмента
userId в конструкции не участвует — пример из истории (истёк 26.10).

### Система релея (разово, с OK владельца; стенд — раньше)

1. Пакет `bubblewrap` (apt, 0.9.0) + профиль AppArmor `/etc/apparmor.d/bwrap`
   (даёт user namespaces; `unprivileged_userns_clone=1`,
   `apparmor_restrict_unprivileged_userns=1`). Профиль касается только
   `/usr/bin/bwrap`. Чужие проекты (smilebot, taler-monitor, cron dv) не трогаем.
2. Инструменты ассистентов — копия в `/opt/linkeon-agent` (read-only):
   python3 venv (`~/agent-env`), `bin/generate_image.sh`, скрипты расчётов
   (`hd_bodygraph.py`). Копия, не перенос: старые пути живут до полного отката.
3. `/tmp/agent-output`, `/tmp/agent-uploads` — права 0311: по имени папки можно
   зайти, перечислить чужие нельзя. Релей каталоги списком не читает (проверено
   по коду), сам ломать их не будет. Имена папок — непредсказуемые hex.
4. Новые каталоги, тоже закрыты от листинга:
   - `/tmp/agent-mcp` — конфиги MCP (0600);
   - `/tmp/agent-scratch/<fs_key>` — рабочий каталог хода.
   В ход создаются с 0700, после хода не чистятся (режим 0311 держит их от
   чужого листинга), чистка — по mtime > 7 дней.
5. Разовая уборка старых файлов ассистентов из корня `/tmp` в архив
   `~/linkeon-orphans-oldtmp-20261103.tar.gz` (по образцу 03.11:
   сверка числа записей до удаления папки).

### Код релея (выкат `scripts/deploy-relay.sh`, с OK)

1. Новый модуль `relay-agent/sandbox-policy.mjs`: по fs_key хода собирает
   `--settings` (JSON: песочница, запреты чтения/записи, список сети) и
   `cliEnv()` — окружение CLI по списку (см. 3).
2. Запуск CLI: аргумент `--settings <путь>` + `cliEnv()` вместо
   `process.env`. Рабочий каталог остаётся `/tmp` (транскрипты `--resume`
   продолжают лежать в `~/.claude/projects/-tmp`, путь релея не меняется).
   Для вложенного Bash HOME — `/tmp/agent-scratch/<fs_key>` (иначе, например,
   libreoffice/pip не смогут писать настройки). Учётка CLI — через
   `CLAUDE_CONFIG_DIR=~/.claude` (рискованное место: при баге CLI может не
   найти учётку — проверка первым пунктом на стенде).
3. `cliEnv()`: `PATH` (/opt/linkeon-agent/bin + системные), `HOME` (scratch),
   `TMPDIR` (scratch), `LANG/LC_*`, служебные `MCP_*`/`RUN_*`, переменные
   запасных провайдеров из `llm.providerSpawnEnv` (только выбранного),
   `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` (комментарий в
   `llm-fallback.mjs`: в CLI 2.1.280 скраб окружения Bash требует bwrap — проверка
   на стенде `env` из Bash: ключа провайдера нет). `GEMINI_API_KEY` и
   `OPENROUTER_API_KEY` не передаются (ни релею, ни ассистентам не нужны; пали
   в pm2 из `~/.bashrc` и `file-agent/.env`).
4. `--allowedTools`: для Read/Glob/Grep — свой `/tmp/agent-output/<fs_key>`,
   `/tmp/agent-scratch/<fs_key>`, `/opt/linkeon-agent` (read-only) и прочие
   разрешённые системные пути, если понадобятся (шрифты и т.п.) — по наблюдению
   первых дней. Write/Edit — свои папки. Не `(*)`. `permissions.deny`:
   `/home/dv/**`, `/tmp/agent-mcp/**`, `/tmp/agent-output`, `/tmp/agent-uploads`
   (свои по имени), `/etc/sudoers*`, `/proc/1/**` — запрет сильнее allowedTools.
5. Песочница в настройках: `enabled`, `allowUnsandboxedCommands: false`
   (отказ без обхода), записываемые пути — свои, запрещённые на чтение —
   `/home/dv`, `/tmp/agent-mcp`, `/etc/sudoers*`; `excludedCommands: ["sudo *"]`
   (требование sudo). Сеть — решение владельца 03.11 «В: прокси»: на релее
   squid на `127.0.0.1:8471` (bind только loopback, `acl localnet dst` со
   внутренними сетями → `http_access deny localnet`). Из песочницы открыт
   ТОЛЬКО этот адрес (`network.allowedDomains: ["127.0.0.1:8471"]`), выход
   наружу — через переменные окружения `http_proxy`/`https_proxy` (и капс) в
   чистом env CLI; `no_proxy` НЕ задаётся (иначе обход резки через localhost).
   Проверено разведкой 03.11: песочница пускает loopback лишь к разрешённым
   host:port, внешние адреса без прокси закрыты.
6. Конфиг MCP: каталог `/tmp/agent-mcp`, имя `<fs_key>-<ts>.json`, 0600,
   после хода удаляется (как сейчас). В промпте пути `~/agent-env`,
   `~/file-agent/bin`, `~/.bun/bin` — на `/opt/linkeon-agent`.
7. Переключатель: файл на релее (`~/file-agent/sandbox-mode`: `off | canary |
   on`), читается на каждом ходе — перезапуск не нужен. Канарейка — номер
   владельца (первая строка списка из scrub-скрипта). В журнал релея строка
   `sandbox: <режим>` (без номеров).
8. Ошибки инструментов с «sandbox» в тексте — строка `sandbox-fail` в журнал и
   сигнал в канал алертов. Автоматический возврат в `off` не делается (это дыра).

## Ход в режиме on

1. Релей создаёт `/tmp/agent-output/<fs_key>` и `/tmp/agent-scratch/<fs_key>`
   (0700).
2. Конфиг MCP и `--settings` — в `/tmp/agent-mcp` (0600).
3. CLI запускается с новым окружением, `--settings` и узкими allowedTools.
4. После хода конфиг и настройки удаляются; scratch живёт, чистка по mtime.

## Откат

Переключатель `off` — следующий ход по-старой схеме (старые пути не удалены).
Если CLI не видит учётку из-за `CLAUDE_CONFIG_DIR`/домашнего HOME — режим
остаётся `off`, правка кода, повтор. Откат системных правок (bwrap, права
каталогов) — только вручную по этой спеке.

## Проверка (до прод)

Стенд `file-agent-sandbox` (порты 3036/3037), режим `on` принудительно:
- тесты `sandbox-policy.mjs` на ноде (`relay-agent`, vitest/node);
- настоящий bwrap на релее: `bwrap --bind / / --dev-bind /dev /dev true`;
- из Bash хода: `env` — нет ключа провайдера; `sudo true` — нельзя;
  `cat ~/file-agent/sessions.json` — нельзя; `ls /tmp/agent-output` — пусто;
  `curl https://example.com` — ок; `curl http://127.0.0.1:3033/` — нельзя;
  `pip install` — ок; свой файл в `/tmp/agent-scratch` — ок;
  `/files/<fs_key>/…` — отдаётся;
- канарейка с номером владельца: живой ход, «норм» владельца; затем те же ходы
  на Qwen и Kimi (их запуск идёт тем же CLI);
- замер длительности хода до/после на стенде: добавка > 30 с — вопрос владельцу.

## Порядок выката (шаг с OK владельца)

1. Системные правки на прод-релее (bwrap, AppArmor, `/opt/linkeon-agent`, права
   каталогов, сбор и стирание `~/linkeon-orphans-oldtmp`).
2. Код релея через `deploy-relay.sh`, режим `off`.
3. Канарейка: `canary` на номере владельца.
4. `on`, наблюдение за журналом 2 дня.

## Не входит

- Чистка `~` и чужих проектов на коробке; журналы pm2 и архив с номерами на
  самой коробке остаются (из песочницы недоступны).
- `~/.ssh/id_rsa` релея (прочтение возможно root'ом) — ключ выкатывает владелец.
- На проде 17 из 23 `~/spirits_back/.env.bak*` доступны не только владельцу —
  предложение: `chmod 600` или удалить старые (с OK).
