# Память загруженных файлов и ссылок в разговорах — дизайн

**Дата:** 2026-11-13  
**Статус:** согласовано в диалоге с владельцем, ожидает review письменной спецификации

## Цель

Ассистент помнит исходные файлы пользователя и может позже ответить по их содержимому: в текущем чате, после ротации сессии и в новых разговорах. Ссылки на исходники доступны только владельцу аккаунта. Внешние ссылки из сообщений запоминаются только как адреса, без автоматического скачивания.

## Решения владельца

- Помнить файлы и в текущем, и в будущих чатах.
- Сохранять имя, ссылку и содержимое исходного файла.
- Внешние ссылки — только адреса.
- Исходные файлы открываются только владельцу аккаунта; ассистент получает отдельную короткоживущую ссылку на чтение.
- Выбран подход: постоянный реестр в Postgres + приватный MinIO.
- Владелец сознательно выбрал хранение **без дополнительного шифрования** (см. «Соответствие концепции»).

## Текущее состояние и пробел

- Байты multipart-загрузок остаются только в `/tmp/agent-uploads` на релее; в Postgres нет записи об исходном файле.
- `custom_chat_history` хранит имя и задание, но не исходную ссылку и не attachment metadata.
- Обычный `--resume` помнит файл через транскрипт Claude, но при ротации блок `User uploaded files` вырезается из переносимого хвоста.
- `find_files` ищет только файлы из ответов ассистента, а не исходные загрузки.
- Маленький текстовый файл вставляется прямо в prompt и тоже не получает собственной записи/ссылки.
- Публичной ссылки на исходную загрузку не существует.

## Архитектура

### Хранение

Новая таблица `chat_uploads`:

| Поле | Назначение |
|---|---|
| `id uuid` | ID загрузки |
| `user_id text` | Владелец (телефон или UUID email/OAuth) |
| `session_id text` | Логическая сессия чата |
| `original_name text` | Исходное имя файла |
| `mime text` | MIME-тип |
| `size_bytes bigint` | Размер |
| `sha256 text` | Контрольная сумма |
| `storage_key text` | Ключ объекта в MinIO |
| `created_at timestamptz` | Время загрузки |

Байты складываются в приватный bucket `linkeon-chat-uploads` **до вызова релея**. Пустой или упавший ответ ассистента не отменяет сохранение.

Маленький текстовый файл, который сейчас вставляется прямо в prompt, сохраняется как `text/plain` с той же записью и ссылкой.

Записи и байты удаляются при удалении аккаунта по существующей процедуре очистки. Автоматического срока хранения и ручного удаления отдельного файла в этот этап не входит.

### Ссылки и доступ

Для пользователя:

- `GET /webhook/chat-uploads/:id` с JWT и проверкой владельца записи;
- чужой пользователь получает 404, без раскрытия существования файла;
- история содержит `📎 [имя](/webhook/chat-uploads/<id>)`.

Для ассистента:

- отдельная ссылка `GET /webhook/chat-uploads/:id?exp=<unix>&sig=<hmac>`;
- подпись HMAC-SHA256 на `chat-upload:v1:<id>:<exp>` с `JWT_SECRET`;
- срок действия — 1 час, новая ссылка создаётся при каждом обращении;
- подписанная ссылка не выводится пользователю: она только для чтения моделью;
- публичного постоянного URL нет.

`ChatUploadsService` отвечает за сохранение, выдачу ссылок и проверку доступа. `ChatUploadsController` стримит файл с исходным content-type и content-disposition.

### Память в текущем чате

- Текущий multipart prompt остаётся прежним: пути на релее и задание.
- На следующих ходах бэкенд добавляет до 10 последних загрузок этой сессии: имя и короткоживущую ссылку на чтение.
- Это работает при обычном resume, после ротации и при холодном старте. Ротация больше не зависит от вырезанного upload-header: записи восстанавливаются из `chat_uploads`.
- Байты в prompt не подставляются: ассистент читает их по ссылке по необходимости.

### Поиск в новых чатах

`find_files` расширяется тремя источниками:

- `origin: "upload"` — исходные загрузки пользователя из всех его разговоров;
- `origin: "assistant"` — созданные ассистентом файлы, как раньше;
- `kind: "link"` — внешние ссылки из человеческих сообщений, только адрес.

Для исходной загрузки возвращаются два адреса: пользовательский через JWT и отдельный короткоживущий для ассистента. В prompt нового чата старые файлы не включаются автоматически — ассистент находит их по запросу пользователя по имени, дате или типу. Созданные ассистентом файлы и их существующие ссылки не меняются.

Внешние ссылки не скачиваются автоматически. Открытие по запросу подчиняется существующим правилам безопасности.

## Обработка ошибок

- MinIO недоступен: текущий ответ продолжается по прежнему relay-пути, а в поток добавляется событие `upload_persist_failed` с понятным пользователю текстом «Файл не сохранён для будущих разговоров».
- Байты загружены, а запись в Postgres не удалась: объект удаляется best-effort, ошибка логируется без публичного fallback.
- Не удалось выдать приватную ссылку: публичный URL не создаётся; чтение идёт только через JWT или валидную подпись.
- Просроченная или неверная подпись, чужой JWT — 404 без утечки существования записи.

## Тесты

На CI-ноде:

- запись сохраняется до вызова релея и остаётся при пустом/упавшем ответе;
- следующий вопрос в том же чате получает ссылку и позволяет прочитать исходник;
- после ротации ассистент снова находит файл и отвечает по содержимому;
- в новом чате `find_files` возвращает исходник и внешнюю ссылку как адрес;
- чужой JWT и просроченная/неверная подпись файл не открывают;
- маленький текстовый файл получает запись и ссылку;
- MinIO failure не прерывает текущий ответ и даёт `upload_persist_failed`;
- внешняя ссылка сама по себе не скачивается;
- существующие upload-session и `find_files` тесты остаются зелёными.

Живая приёмка на проде:

1. Загрузить документ и задать вопрос по нему.
2. Спросить о нём следующим сообщением.
3. Повторить вопрос после ротации.
4. Спросить о файле в новом чате через `find_files`.
5. Проверить доступ владельца, чужого пользователя и просроченной подписи.
6. Проверить, что внешняя ссылка сохранилась только как адрес.

## Миграция и выкат

- Добавляются таблица и приватный bucket; bucket включается в политику `smm-rw`.
- Код релея не меняется.
- Feature flag `CHAT_UPLOADS_ENABLED` по умолчанию выключен. После обычного `deploy.sh` и зелёного smoke включается на проде отдельным решением владельца, затем выполняется живая приёмка.
- Обратное восстановление старых загрузок в этот этап не входит: у части исходников нет байтов, а сессию по имени файла угадывать нельзя. Отдельный backfill возможен позже только для подтверждённых владельцев с сухим прогоном.
- Откат отключает реестр и подстановку в prompt; прежний путь загрузки продолжает работать, сохранённые файлы не удаляются.

## Соответствие концепции

§4.2.2 концепции требует хранить облачные данные шифрованными с ключом пользователя. Выбранная схема хранит исходники в приватном MinIO **без дополнительного шифрования**. Владелец явно выбрал этот вариант 2026-11-13 после обсуждения: доступ ограничен JWT владельца или короткоживущей подписью ассистента, публичной постоянной ссылки нет.

Это сознательное отклонение от концепции, а не утверждение о её выполнении. Требование «не отправлять новые данные наружу без необходимости» соблюдено: байты уже загружаются на сервер и в модель, а внешние ссылки не скачиваются автоматически.
