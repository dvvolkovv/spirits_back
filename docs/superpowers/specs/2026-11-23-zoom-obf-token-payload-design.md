# Сохранение OBF-токена в настройках Zoom-бота — дизайн

## Проблема

`AttendeeClient.createBot()` получает от `MeetingService` одноразовый токен
On-Behalf-Of (`obfToken`) для входа ассистента во встречу Zoom. В теле запроса
на создание бота поле `zoom_settings` сейчас задаётся дважды:

1. `{ obf_token: p.obfToken }`, если токен передан;
2. `{ sdk: 'web' }` для провайдера Zoom.

Второе свойство перезаписывает первое. Прямой вызов текущего клиента с
`provider: 'zoom'` и непустым `obfToken` подтвердил итоговое значение
`{"sdk":"web"}` без `obf_token`.

Существующий тест проверяет только `sdk: 'web'` и не передаёт OBF-токен,
поэтому дефект не обнаруживается тестовым набором.

## Цель и границы

При создании Zoom-бота передавать веб-адаптер и OBF-токен одновременно. Меняются
только сборка тела запроса в `AttendeeClient.createBot()` и его unit-тесты.

Не меняются OAuth, получение и хранение токенов, публичный контракт
`CreateBotParams`, маршрутизация моста, обработка ошибок, frontend и сценарий
Meeting SDK. Новые функции и рефакторинг остальных провайдеров не входят.

## Решение

В литерале запроса `zoom_settings` формируется ровно один раз. Его содержимое
собирается из двух независимых частей:

- для `provider === 'zoom'` — `sdk: 'web'`;
- для непустого `p.obfToken` — `obf_token: p.obfToken`.

Объект добавляется в тело, если присутствует хотя бы одна из этих частей.
Так сохраняются все текущие сочетания, включая защитное поведение для
нецелевого вызова с OBF без провайдера Zoom.

Итоговая матрица:

| Вход | Ожидаемый `zoom_settings` |
|---|---|
| Zoom без OBF | `{ sdk: 'web' }` |
| Zoom с OBF | `{ sdk: 'web', obf_token: '…' }` |
| Не Zoom без OBF | поле отсутствует |
| Не Zoom с OBF | `{ obf_token: '…' }`, как прежде |

## Соответствие концепции

Решение восстанавливает уже предусмотренную передачу существующего
одноразового токена в существующий сервис ботов. Новых данных, хранения,
журналирования токена, внешних получателей и изменений пользовательского
согласия не появляется. Тест использует искусственную метку вместо реального
токена.

## Проверка

Применяется TDD:

1. Добавить регрессионный unit-тест, который вызывает `createBot()` с
   `provider: 'zoom'` и `obfToken`, разбирает тело запроса и требует оба поля.
2. Запустить его до исправления и зафиксировать падение: фактическое значение
   содержит только `sdk: 'web'`.
3. Исправить сборку `zoom_settings`.
4. Повторить регрессионный тест, затем прогнать `attendee.client.spec.ts`,
   Zoom/meeting-набор и тесты `infra/meeting-bot` на CI-ноде.
5. Прогнать backend build на CI-ноде. Живая встреча и деплой в эту задачу не
   входят и выполняются отдельно.

Критерий приёмки: при Zoom с OBF тело запроса содержит оба значения, прежние
тесты остаются зелёными, а регрессионный тест на версии без исправления падает.
