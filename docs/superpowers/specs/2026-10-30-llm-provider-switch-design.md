# Переключатель модели по аккаунту и запасной Qwen на релее

Дата: 2026-10-30. Продолжение `2026-10-29-qwen-fallback-design.md` (запасной путь
`ClaudeCliService` на Qwen — на проде с 30.10, коммит 1c755905).

## Зачем

1. Владелец хочет проверить Qwen на себе: в админке выбрать для своего аккаунта
   «отвечать через Qwen» и поговорить с ассистентами — Романом, Кирой, Машей,
   своим TG-ботом.
2. Веб-чаты всех ассистентов, кроме Маши, идут через релей r.linkeon.io, а там
   запасного пути нет: протухни вход Claude на релее — молчат все веб-чаты.

## Решения владельца (30.10)

- Охват переключателя — все ассистенты, включая релей.
- Правка релея — отдельно от невыкаченной «части Б» (копия релея в main ушла от
  живого на ~237 строк): одна и та же небольшая правка кладётся и на живой релей
  (база 9ba7f53), и в копию `relay-agent/` в main.
- Автоматический запасной путь на релее — в этом же заходе.
- Списание — как обычно (стоимость хода от CLI, по прайсу Opus).

## Устройство

### 1. Настройка пользователя

Колонка `ai_profiles_consolidated.llm_provider text` — `NULL` (Claude, по
умолчанию) или `'qwen'`. Создаётся стартовой миграцией
`ALTER TABLE … ADD COLUMN IF NOT EXISTS llm_provider text` (без значения по
умолчанию и без индекса — мгновенно, без блокировок).

Отдельная колонка, а не ключ в `profile_data`: `profile_data` пишет сам
пользователь через обновление профиля, а этот выбор — только админу (он тратит
квоту владельца).

Сервис `UserLlmProviderService` (`src/common/services/user-llm-provider.service.ts`):
- `get(userId): Promise<'claude' | 'qwen'>` — один запрос по первичному ключу;
  сбой БД → `'claude'` и предупреждение в лог (ход не должен падать из-за настройки);
- `set(userId, provider): Promise<boolean>` — `'claude'` пишет `NULL`; `false`,
  если пользователя нет.

### 2. Админка

Ручки (класс `AdminController`, уже под `JwtGuard` + `AdminGuard`):
- `GET /webhook/admin/users/:userId/llm-provider` →
  `{ userId, provider, qwenConfigured }`; `qwenConfigured` — задан ли ключ Qwen на
  бэкенде (`readQwenFallbackConfig() !== null`).
- `POST /webhook/admin/users/:userId/llm-provider` с `{ provider: 'claude' | 'qwen' }`
  → то же тело; 400 на чужое значение, 404 — нет пользователя.

`:userId` — тот же идентификатор, по которому карточка пользователя уже ходит в
`/webhook/admin/users/:phone/activity` (телефон или UUID для входа по почте).

Фронт (`spirits_front`): в `UserActivityDrawer` — блок «Модель ответов» с выбором
«Claude (по умолчанию)» / «Qwen» и сохранением сразу. Если `qwenConfigured === false` —
подпись «ключ Qwen на сервере не настроен — ответы пойдут через Claude».

### 3. Какие ответы следуют настройке

Только ответы ассистентов пользователю:
- веб-чат через релей (все ассистенты, кроме Маши) — по `userId` хода;
- Маша (`chat.service`, локальный CLI) — по `userId` хода;
- TG-бот — по владельцу бота (`cfg.owner_user_id`), только основной ход ответа
  (`textWithCost`), не короткий вызов-привратник.

Фоновые задачи (консолидация профиля, задачи и т.п.), Виртуальный PM и
маркетолог (общеплатформенные отчёты) — не следуют: они остаются на Claude с
автоматическим запасным путём.

Пробные ходы мониторинга (`probe === true` в `chat.service`) настройке не следуют
никогда — они меряют Claude.

### 4. `ClaudeCliService`: принудительный Qwen

Новая опция `ClaudeCliOptions.provider?: 'qwen'`:
- ключ задан и нет `noFallback` → вызов сразу на Qwen (тот же путь, что запуск
  через открытое окно предохранителя), без попытки Claude; окно не трогает;
- ключа нет → обычный путь Claude, `logger.warn` «Qwen запрошен, но ключ не задан».

Событие `claude_cli_call`: у принудительного вызова `provider: 'qwen', fallback: false`
(сейчас `fallback` выводится из `provider` — станет отдельным признаком). В
`fallbackStats()` принудительные вызовы не считаются: там — только аварийные.

Если принудительный Qwen упал — ошибка как при сбое через окно, но первая часть —
`claude CLI не вызывался (выбран Qwen)`; окно предохранителя не трогается.

### 5. Релей

**Запрос.** Два новых необязательных поля формы `/chat`:
- `provider` — только значение `qwen` что-то меняет (принудительно Qwen);
- `noFallback` — `1`: только Claude, без запасного пути (пробы мониторинга).
Старый бэкенд их не шлёт — поведение прежнее.

**Ключ.** Файл `QWEN_KEY_FILE` (по умолчанию `/home/dv/file-agent/secrets/qwen.key`,
права 600) читается на каждом ходе: нет файла — Qwen на релее выключен целиком
(ни принудительный, ни запасной); сменить ключ можно без рестарта. Адрес и модели —
те же значения по умолчанию, что у бэкенда; переопределяются переменными
`QWEN_FALLBACK_BASE_URL` / `QWEN_FALLBACK_MODEL_*` процесса релея.

**Модуль `relay-agent/qwen-provider.mjs`** (чистые функции, тесты
`qwen-provider.test.mjs` под `node --test`):
- `readQwenConfig(env, readFile)` — конфиг или `null`;
- `qwenModelFor(requested, models)` — как в бэкенде (`default`/`opus`/
  `claude-opus-*` → max, `sonnet` → flash, `haiku` → 3.6-flash);
- `qwenSpawnEnv(baseEnv, cfg)` — как `qwenSpawnEnv` бэкенда (снимает `ANTHROPIC_*`
  и `CLAUDE_CODE_OAUTH_TOKEN`; `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_MAX_RETRIES=1`,
  `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `API_TIMEOUT_MS=300000`, модели);
- `pickProvider({ forced, cfg, breakerOpen, noFallback })` → `'claude' | 'qwen'`;
- `isAccessFailure(text, { isError, apiStatus })` — сбой доступа к Claude:
  отказ CLI — по тем же правилам, что `looksLikeCliRefusal` бэкенда (фраза отказа в
  начале текста, не длиннее 300 символов, без кириллицы: ложное срабатывание
  открывает окно для всех веб-чатов, а не портит один ход); `api_error_status`
  401/403/429/529; не сбой — ошибки длины контекста. Уведомление `cli_fatal` для
  одного хода по-прежнему решает прежний, непривязанный `FATAL_RE`;
- `mayFallback({ provider, cfg, noFallback, sentAnyText, riskyToolUsed })`.

Состояние в `server.mjs` (уровень процесса, как у бэкенда): окно предохранителя
5 мин (`QWEN_FALLBACK_BREAKER_MS`), закрывается успехом Claude, начатым после
открытия окна, и любым сбоем Qwen; исходы Qwen за 15 мин.

**Ход.**
1. Провайдер хода — `pickProvider`: принудительный `qwen` при ключе → Qwen; окно
   открыто, ключ есть, нет `noFallback` → Qwen; иначе Claude.
2. `runOnce(useResume, provider)` — тот же `claude` и те же аргументы; у Qwen —
   `--model qwenModelFor(...)` и окружение `qwenSpawnEnv`. `--resume` тот же: беседа
   продолжается между провайдерами в обе стороны (проверено 29.10).
3. В разборе `result`: если провайдер Claude и `isAccessFailure(...)` и
   `mayFallback(...)` — вежливое уведомление `cli_fatal` НЕ шлётся, ход помечается
   «сбой доступа»; иначе — как сейчас.
4. После хода: сбой доступа → открыть окно, `console.warn`, тот же ход на Qwen.
   Существующий повтор при временной ошибке (`transientHit`) остаётся; если и
   повтор упал временной ошибкой вида 429/529/401/403 и `mayFallback` — вместо
   уведомления «временный сбой» ход идёт на Qwen.
5. Qwen упал → окно закрыть; пользователю — те же уведомления, что сейчас
   (`cli_fatal` / `transient`), ход `failed` — токены не списываются.
6. `mayFallback` ложно, если пользователю уже ушёл хоть один кусочек ответа или
   модель вызвала хоть один инструмент с последствиями — любой, кроме `Read`,
   `Glob`, `Grep`, `WebSearch`, `WebFetch` (запись в TalerID, продукты, генерация
   картинок и видео, Bash/Write/Edit): повтор выполнил бы его второй раз.

**`done`** получает `provider: 'claude' | 'qwen'` и `fallback: boolean`.

**`/health`** получает `qwen: { enabled, ok, failed, windowMs, breakerOpenUntil }`.

### 6. Бэкенд ↔ релей

`chat.service`, ход через релей:
- настройка пользователя `qwen` (и не проба) → `fd.append('provider', 'qwen')`;
- проба → `fd.append('noFallback', '1')`;
- из `done` — `provider`/`fallback` в `chat_quality.props` (`provider`, `fallback`).

### 7. Мониторинг

Запасной путь не должен прятать сбой:
- пробы (синтетика `chat_streaming`, пинг Маши) — `noFallback`, меряют только Claude;
- `RelayQwenMonitorService` (не `ClaudeHealthService` — отдельный сервис, своя
  таблица антиповтора `monitor_alert_state`, компонент `relay_qwen_fallback`)
  раз в 15 минут читает `${AGENT_URL}/health`.

  **Отбой — определение.** Окно предохранителя на релее закрывается само
  через `breakerMs` (5 мин) независимо от того, ответил ли Claude хоть раз —
  поэтому «окно закрыто и за 15 мин ответов Qwen нет» (первая редакция этого
  параграфа) даёт ложный отбой ночью при лежащем Claude и редких ходах: окно
  истекает раньше, чем случается следующий ход. Верный критерий отбоя —
  **Claude ответил после последнего открытия окна, и за окно статистики (15
  мин) не было аварийных ходов на Qwen.** Соответственно `/health.qwen` несёт
  не только `breakerOpenUntil`, но и `lastOpenedAt`/`lastClaudeOkAt`
  (`qwen-provider.mjs`, `createQwenBreaker().stats()`); бэкенд не сравнивает
  `breakerOpenUntil` со своими часами (релей сам обнуляет истёкшее поле), а
  судит «активен ли запасной путь» по `breakerOpenUntil > 0 || ok+failed > 0
  || (lastOpenedAt есть и lastClaudeOkAt < lastOpenedAt)`.

  Алерты: «🟠 Релей: Claude недоступен — ассистенты отвечают через запасной
  Qwen (ответов N, ошибок M за 15 мин)» по той же схеме антиповтора, что алерт
  CLI; если сам Qwen тоже не отвечает (`ok: 0, failed > 0`) — отдельный текст
  «🔴 Релей: Claude недоступен, запасной Qwen тоже не отвечает» (иначе люди
  решат, что всё работает через Qwen, пока он молчит); «🟢 Релей: Claude снова
  отвечает» — по критерию отбоя выше. Принудительные ходы (настройка
  пользователя) в этот счёт не входят — релей считает в `/health` только
  аварийные.

  **Выключатель.** `RELAY_QWEN_MONITOR=off` в `.env` → `check()` сразу
  возвращает `unknown`, не читает `/health` и не пишет в БД. Нужен на
  test.linkeon.io: там `AGENT_URL` указывает на боевой релей (своего стенда
  нет) — без выключателя test дублировал бы алерты прода.

## Настройки

| Где | Что |
|---|---|
| бэкенд `.env` | `QWEN_FALLBACK_API_KEY` — уже на проде |
| релей | файл `/home/dv/file-agent/secrets/qwen.key` (600) или путь в `QWEN_KEY_FILE` |
| бэкенд + релей, окружение процесса Qwen | `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=0` — явно. `=1` прятал бы ключ от подпроцессов инструментов, но на Linux требует bubblewrap: без `bwrap` (нет ни на проде, ни на релее) CLI падает сразу — так 30.10 после выката d4be19f8 сломался весь путь на Qwen. У бэкенда Bash нет; на релее ключ доступен Bash ассистента наравне с прочими секретами на диске — нужна песочница для Bash, отдельная задача |
| бэкенд `.env` (test) | `RELAY_QWEN_MONITOR=off` — выключает алерт мониторинга релея там, где `AGENT_URL` указывает на боевой релей |
| релей, `.gitignore` | `secrets/` — каталог с файлом ключа живёт внутри git-дерева релея |

## Тесты

- Бэкенд (jest, на ноде): `UserLlmProviderService` (get/set, NULL, сбой БД);
  админ-ручки (валидация, 404, `qwenConfigured`); `ClaudeCliService` с
  `provider: 'qwen'` (один spawn с env Alibaba, без ключа — Claude + warn,
  событие `fallback: false`, окно не трогается, `fallbackStats` не растёт);
  `chat.service` — поля `provider`/`noFallback` в запросе к релею и разбор `done`;
  `tg-router` — настройка владельца уходит в основной ход, не в привратника;
  `ClaudeHealthService` — алерт релея по `/health` (открыто/закрыто/недоступен).
- Релей (`node --test`): модуль `qwen-provider.mjs` целиком; существующие тесты
  релея — зелёные.
- Фронт (vitest): блок «Модель ответов» в карточке — показ, сохранение, подпись
  без ключа.
- Живая проверка релея — НЕ на сервере релея: порт 3033 и `sessions.json` там
  прибиты в коде, а `sweepRuns` при старте второго экземпляра убил бы ходы живого.
  Пропатченная живая версия (база 9ba7f53) поднимается временно на ноде
  (`dv`, `claude` 2.1.312, Node 22) с пустым `CLAUDE_CONFIG_DIR` и ключом во
  временном файле: обычный ход → `done.provider = 'qwen'`, `fallback: true`;
  `noFallback=1` → прежнее уведомление `cli_fatal`; `provider=qwen` →
  `fallback: false`. После — стенд снимается целиком.

## Выкат

1. Ключ на релее — файлом (с OK владельца).
2. Релей — вручную по рецепту (файлы рядом → `node --check` → `node --test` →
   коммит в git релея → `pm2 restart file-agent`, когда нет живых ходов → `/health`).
   Старый бэкенд новых полей не шлёт, поэтому релей можно выкатывать первым.
3. Бэкенд и фронт — `deploy.sh` (с OK).
4. В админке — Qwen на аккаунте владельца; владелец пишет Роману, Маше, своему
   TG-боту; в `chat_quality`/`claude_cli_call` — `provider: 'qwen'`.

## Вне охвата

- Невыкаченная «часть Б» релея — своим выкатом.
- Фоновые задачи по настройке пользователя.
- Отдельный ключ/квота под принудительный режим: принудительные ходы тратят ту же
  квоту Token Plan, что запасной путь.
