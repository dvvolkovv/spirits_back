## Решения

1. **ElevenLabs.** Имя нового клона — без идентификатора: `linkeon-<8 hex случайных>` (связь — по `user_voice.elevenlabs_voice_id`, имя нигде не читается). Существующий голос переименовать через API ElevenLabs (`POST /v1/voices/{voice_id}/edit`, поле `name`) — разовым скриптом с сухим прогоном, на проде, с OK. Кроме голосов из `user_voice` скрипт видит сирот — клоны аккаунта (`category=cloned`) с именем строго `user_<номер|uuid>` без строки в `user_voice` (перечень — `GET /v2/voices` постранично; в выводе только число и `voice_id`, имён нет) — и переименовывает их тоже, отдельным счётчиком.
2. **Голосовые документы.** Новый ключ — `documents/<fsKey>/<docId>.md`, где `fsKey` — тот же солёный хэш пользователя, что у папок релея (`RELAY_FS_SALT`, функция части Б). Существующие 20 ссылок: разовый скрипт `scripts/migrate-voice-document-keys.ts` — копия объекта под новый ключ и замена адреса везде, где он хранится: `custom_chat_history` (только строки старше часа — как у переноса ссылок), `voice_calls.transcript` и `summary`, `voice_call_jobs`, `action_plans`, `tasks`, `task_events`. Сухой прогон, журнал и откат — как у `scripts/backfill-chat-files.ts`. **Удаление старых объектов — отложенное:** `--apply` их не удаляет, а пишет в журнал «скопирован, ссылок на старый ключ в базе нет»; удаляет отдельный `--delete-old <журнал>` — объекты, записанные в журнале как «можно удалять» или «скопирован», и только если новая копия на месте, а ссылок на старый ключ в базе нет. Когда запускать `--delete-old` — решает владелец; ссылки, уже отправленные в чаты встреч на внешних площадках, после удаления перестанут открываться.
3. **Тест версии ассистента.** `fs_key` уходит на релей всегда (и при `linkeonTools: false`) — папка хода по солёному хэшу, как в обычном чате.
4. **VPM.** Номера в заметке заменить словами («тестовые и служебные аккаунты, включая аккаунт владельца»); фильтр тестовых аккаунтов в запросах — как есть.
5. **Релей: старые папки, загрузки и транскрипты (вариант В).** Разовый скрипт `scripts/relay-scrub-phone.mjs` на релее (через stdin, в дерево релея не кладётся), по каждому номеру из `sessions.json` — все его сессии вместе: содержимое `/tmp/agent-output/<старый ключ>` переезжает в `/tmp/agent-output/<fs_key>` (занятое имя не перезаписывается — «(прежний)»; пустая старая папка удаляется), загрузки `<старый ключ>_<имя>` → `<fs_key>_<имя>`; сразу за ними в транскриптах: строка «Current user phone …» → «Current user: identifier omitted.», пути старых папок и загрузок (свои и соседних сессий номера) → новые, остальные вхождения номера владельца → его `fs_key`. `fs_key` — из карты прода (`scripts/relay-fs-key-map.ts`, только с `RELAY_FS_SALT`), запасной — из строки «Output directory» хода после части Б; тестовый стенд ходит в тот же релей с теми же ключами и своей солью — его ходы узнаются по карте стенда (тот же помощник с `.env` стенда), сессия с ходами прода и стенда переезжает под `fs_key` прода; с картой `--apply` сверяет её по всем сессиям и при незнакомом `fs_key` отказывает. Не трогаются: блоки `thinking` (подпись — правка ломает `--resume`), ключи JSON, общие старые папки (ключи длиннее 48 знаков обрезались в одну папку на несколько сессий — в их транскриптах только строка и `userId`), сессии без `fs_key`, сироты, номера других пользователей — только счёт. Номер с идущим ходом (свежий транскрипт или живой `claude --resume`) — вторым заходом; таблица переносов (по `fs_key`, без номера) — до переноса; запись атомарная, права, владелец и mtime прежние; журнал и вывод — без номеров. Канарейка — `--sessions-file` со всеми ключами одного (тестового) номера, приёмка — живой ход через `--resume` в её сессии; потом все (`--only-phones` — только поэтапно после канарейки: сортировка по цифрам может дать живого пользователя). `--list-residual` — список сессий, где номер остаётся (рассуждения, пути общих папок, без `fs_key`), для решения владельца убрать их транскрипты (следующий ход — свежая сессия). `--finish` удаляет карты и таблицу, только когда делать нечего; остался только принятый остаток — удаление вручную с OK владельца, со счётчиками. **Порядок: п. 6 — до применения** (перенос ссылок в MinIO берёт файлы по старым путям); после переноса старые `/files/<номер>_…` дают 404, в том числе из кэшей браузеров и Telegram, — принято. Рестарт релея не нужен.
6. **Старые ссылки `/files/<номер>_…`.** Расширить `backfill-chat-files.ts`: для ссылок, файла которых нет (их прежний прогон пропустил), заменить номер (или uuid) в адресе на `fsKey` пользователя (ссылка остаётся мёртвой, но без номера); для существующих — как раньше (копия + замена); ответ релея неясен — не трогать. Наш релей узнаётся по хосту (`new URL`: схема, регистр, порт) — адрес в любом написании идёт через пробу у релея. Ссылки `/files/<номер|uuid>_…` под чужим хостом и без хоста маскируются так же, без вопроса релею, но только если id в ссылке — владелец строки (первая часть `session_id`): того же вида бывают живые сторонние адреса; остальные не трогаются и только считаются. Сухой прогон пишет кандидатов в маску (404 и чужие ссылки владельца) с хэшем вместо id в `.dry-run.txt` — ложные 404 видно до `--apply`. Пути на диске релея `/tmp/agent-output/<номер>_…` и `/tmp/agent-uploads/<номер>_…`, которые модель повторяла в ответах (на проде 76 сообщений в 13 сессиях, последнее 12.10), — тоже. Все `sender_type`, строки старше часа. Сухой прогон с разбивкой по причинам и отдельными счётчиками; журнал и откат.
7. **Справка `how-it-works`.** Список поставщиков: добавить Alibaba Cloud (Qwen) и Moonshot AI (Kimi); Moonshot AI вправе обучаться на присланном (как на лендинге). OpenRouter не называть: в коде он запасной путь фоновых задач, но ключа на проде нет — путь мёртв. Строка о поставщиках короткая — в самом длинном варианте статьи (стор) остаётся ≥ 250 байт до предела 5 КБ под будущую строку про номер. Строка про номер — только после выката 1–6 и в точной формулировке: «Номер телефона нейросетям не передаётся; ИИ-поддержке видны имя и почта, чтобы помочь с аккаунтом». **Вычитка владельцем — до слияния.**

**Разовые скрипты (1, 2, 6) — общее.** Журналы и списки содержат ключи и адреса с номерами: права 600 (скрипты ставят umask 077), `.missing.txt` — только при `--apply`; удалить журналы после окна отката. Солёный хэш — только на `RELAY_FS_SALT` (без запасного `JWT_SECRET`: его меняют); без неё скрипт отказывается работать. В консоль — сообщение и код ошибки, без объекта (у ошибок S3 и axios в нём метаданные и заголовки).

## Не входит

- Журналы релея с ключом сессии `<номер>_<агент>_<язык>` (наш сервер, нейросетям не уходит; Bash модели на релее — часть В) — отдельно.
- Ключи сессий в бэкенде (`${userId}_…`) — внутренние, нейросетям не уходят.

## Соответствие концепции

§4.2.2 — обработка без лишних данных: номер и идентификатор аккаунта не уходят поставщикам нейросетей и голоса; справка ассистентов говорит правду.

## Релей (п. 5): порядок запуска

Каждый шаг — с OK владельца. Во ВСЕ запуски скрипта — обе карты: `--fs-key-map ~/.relay-fs-key-map.tsv --stand-map ~/.relay-fs-key-map-stand.tsv`.

0. Слить, `deploy.sh`. На проде — `ts-node` и `RELAY_FS_SALT`; на ноде — соль стенда в `~/spirits_back/.env`, CI-клон на коммите слияния.
1. Прод: п. 6 (ссылки `/files/<номер>_…` → MinIO) — сухой прогон, применение. **До шага 6**; после переноса старые `/files/<номер>_…` — 404, в том числе из кэшей браузеров и Telegram, — принято.
2. Релей: файлы не от `dv` в `/tmp/agent-output`, `/tmp/agent-uploads` — посчитать (`find … ! -user dv | wc -l`) и при необходимости `chown -h dv:dv`.
3. Карты трубой, без записи на мак (`set -o pipefail`, `TS_NODE_TRANSPILE_ONLY=1`): ключи `sessions.json` релея → `scripts/relay-fs-key-map.ts` на проде → `~/.relay-fs-key-map.tsv`; те же ключи → помощник на ноде с `DOTENV_CONFIG_PATH` стенда → `~/.relay-fs-key-map-stand.tsv` (`umask 077`). В stderr — «соль — RELAY_FS_SALT»; пустая карта — стоп.
4. Скрипт на релей (`~/relay-scrub-phone.mjs`, 600), сухой прогон. Стоп: совпало 0, расхождений больше 0, «--apply откажет», неканоничные строки, ошибки.
5. Канарейка: `--sessions-file` со ВСЕМИ ключами тестового номера — сухой (все пропуски 0), затем `--apply`; приёмка — живой ход на проде через `--resume` в её сессии (ответ пришёл, старый файл открывается по новому пути и по `/files/<fs_key>/…`).
6. Всё: `--apply` отвязанно (`setsid nohup … &`), стоп — `pkill -INT` (номер доделывается). `--only-phones` — только поэтапно после канарейки: сортировка по цифрам может дать живого пользователя.
7. Через 15+ минут — второй заход.
8. Сухой «0»: к переносу и к записи 0, отложено 0, ошибок 0.
9. Остаток — решает владелец: `--list-residual` (id сессий CLI и причины), затем `--retire-residual <каталог>` — сухой, потом `--apply`. Каталог — в домашнем, вне `~/.claude/projects`, на той же файловой системе, 700; переносятся только окончательные причины (рассуждения, пути непереносимых папок, без `fs_key`, неоднозначные, битые и неканоничные строки с номером); живой `claude --resume <id>` и транскрипт моложе часа — пропуск; «появились снова» — не трогать. Следующий ход такой сессии — свежая сессия («stale resume … — сброс и переигрыш»). Срок хранения каталога — решает владелец, по умолчанию удалить через 30 дней.
10. `--finish`: код 0 — карты и таблица удалены. Если держит только принятый остаток (к переносу и к записи 0, ошибок 0) — удалить вручную с OK владельца, записав счётчики.
11. Уборка: скрипт, файл канарейки, логи, список остатка.

**Дополнения итогового ревью скрипта релея (02.11):** (1) п. 6 бэка — до шага канарейки (она тоже переносит файлы), а не только до полного применения; (2) канарейка должна реально переносить файлы: в её сухом прогоне «папок к переносу» или «загрузок» > 0 — иначе вторая канарейка на номере с файлами (например, номер владельца — с его OK); (3) после полного применения и второго захода 1–2 часа смотреть журнал релея («временный сбой», «API Error», «stale resume», «Invalid signature») против обычного фона; при росте — `pkill -INT -f relay-scrub-phone.mjs`; (4) срок хранения каталога остатка — решает владелец (по умолчанию 30 дней; на релее Bash модели от того же `dv` с sudo видит и его — короче лучше); (5) комментарий в `relay-agent/server.mjs` релея «старые папки не переносятся» после переноса станет неверным — поправить при следующем выкате релея.

## Выкат (каждый шаг — с OK владельца)

Код (1–4, 6-скрипт, 7-текст, скрипт релея и карта fs_key) → `deploy.sh` → разовые скрипты на проде: голос (1), документы (2), ссылки (6) — сухой прогон (для ссылок — просмотр `.dry-run.txt`), затем применение → карты fs_key прода и стенда (трубой на релей) → скрипт релея (5): сухой прогон, канарейка (`--sessions-file`), применение, второй заход, сухой «0», `--list-residual` (решение владельца об остатке), `--finish` → проверка: счётчики 0 → строка справки (7) — отдельным выкатом после вычитки → удаление старых объектов документов (`--delete-old`) — когда решит владелец → журналы скриптов удалить после окна отката.

## Тесты

Модульные: имя клона без id; переименование голосов (сухой прогон, сироты из перечня аккаунта, `--apply`) с замоканным axios; ключ документа без id; `fs_key` в `agentReply` при `linkeonTools: false`; заметка VPM без цифр номеров; права журналов (600), umask и соль в скриптах; карта fs_key — jest с тестовой солью (без `RELAY_FS_SALT` — отказ). На живом SQL (`*.pg.spec.ts`): перенос документов (сухой прогон, замена, журнал, `--apply` не удаляет, `--delete-old` удаляет ровно записанные и повторно — ничего, откат, строки моложе часа) и скрипт ссылок (сухой прогон, замена, чужие хосты и пути релея, владелец строки, журнал, откат). Скрипт релея — на синтетическом релее (перенос с конфликтами, пути в транскриптах, thinking и ключи не тронуты, общие папки, сверка карты прода и стенда, второй заход по таблице, канарейка, `--list-residual`, `--finish`, сигналы, объём). Справка — тест текста и запаса размера.
