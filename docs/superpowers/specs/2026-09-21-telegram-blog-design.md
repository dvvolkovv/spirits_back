# Автоматический блог Linkeon в Telegram — дизайн

Дата: 2026-09-21
Статус: согласован, готов к планированию реализации

## Задача

Вести Telegram-канал Linkeon автоматически: публиковать новинки продукта и
«реальные кейсы, которые можно решать» — каждый пост это картинка плюс история.
Канал универсальный: работает и на привлечение новых пользователей, и на
удержание текущих, и как витрина для B2B.

## Решения, принятые на брейншторме

| Вопрос | Решение |
|---|---|
| Цель канала | Все три сразу; контент делится на рубрики, а не затачивается под одну воронку |
| Источник кейсов | Синтетика: агент сочиняет историю, тему берёт из агрегатов востребованности ассистентов. Тексты чужих диалогов не читаются |
| Источник новостей | Гибрид: `backlog_items → done` плюс еженедельный разбор git-лога обоих реп |
| Апрув | Кнопками в Telegram, в личке владельца |
| Ритм | 3 поста в неделю (пн/ср/пт), новость вытесняет кейс |
| Язык | Только русский; схема хранит язык канала, второй канал включается строкой в БД |
| Визуал | Единый фирменный стиль |
| Куда встраиваем | Отдельный модуль `src/blog/` в `spirits_back` |
| Управление | Вкладка «Блог» в админке — полное управление; кнопки в Telegram остаются как быстрый апрув |

Отклонённые варианты:

- **Надстроить SMM-модуль.** Весь его конвейер упирается в цепочку
  `smm_campaign → smm_scenario → smm_video`; пост-картинку пришлось бы протаскивать
  фиктивным видео, а биллинг начал бы списывать токены с «пользователя Linkeon».
  SMM — живой клиентский продукт, ломать его ради своего блога плохой размен.
- **Скрипт по крону на релее.** Быстрее запустить, но это тот же класс решений,
  который уже дважды молча отставал от git на недели (product-runner,
  synthetic-runner): мимо `deploy.sh`, без апрува кнопками, без истории в БД.

## Что переиспользуем

Разведка показала, что большая часть рельсов уже есть:

- `misc.service.generateBanner` — генерация фона по промпту (Imagen с фолбэком на
  Nano Banana) плюс **программное наложение текста поверх**. Именно поэтому берём
  баннер, а не голый `generateImage`: модели плохо рендерят кириллицу, буквы «плывут».
- `tg-grammy.client` — отправка в Telegram. Второй бот и второй токен не нужны.
- `tg-bot.service` — роутинг `callback_query` и инлайн-клавиатуры уже используются
  в `/assistants` и во встречах; кнопки под черновиком это ещё один обработчик,
  а не новый механизм.
- Релей `AGENT_URL` (`https://r.linkeon.io`) — тот же путь, которым ходят чат-ассистенты.

Воркер (`worker/src/`) не трогаем: его паблишер умеет только `sendVideo`, а
генерация картинок там дублирует бэкендовую.

## Архитектура

Модуль `src/blog/`, четыре сервиса с узкими зонами ответственности. Модуль ничего
не знает про пользователей, кампании и биллинг SMM.

### BlogTopicService — откуда берутся темы

Три входа, все пишут строки в одну очередь (`blog_post` в статусе `idea`):

1. **Бэклог.** Переход `backlog_items` в `status='done'`. В `backlog.service` уже
   есть точка авторассылки по закрытому тикету — туда же вешается создание темы.
   Рубрика `news`, `topic_key = backlog:<uuid>`.
2. **Git.** Воскресный проход по логу `spirits_back` и `spirits_front` за неделю.
   Агент отбирает пользовательски значимое и отбрасывает техническое.
   Рубрика `news`, `topic_key = commit:<sha-диапазон>`.
3. **Статистика.** Еженедельный агрегат: какие ассистенты и сценарии реально
   востребованы. Отдаёт подсказку темы, не текст. Рубрика `case`,
   `topic_key` — нормализованная тема.

Агрегат считается по счётчикам обращений к ассистентам. Тексты сообщений не
читаются ни на одном шаге — это условие задачи, а не оптимизация.

### BlogEditorService — тема в пост

Ходит на релей с промптом редактора, получает `{ title, body, imagePrompt }`.

- **Текст ≤ 1000 символов.** У Telegram подпись к фото обрезается на 1024; пост
  «картинка + история» не должен разъезжаться на два сообщения.
- **Сессия релея — новая на каждый пост.** Длинные сессии у нас глючат
  (посторонний текст в ответе), а память по `sessionId` тут не нужна: чтобы
  редактор не повторялся, в промпт передаются заголовки последних 20 постов.
- Одна ссылка-CTA на пост, без markdown-верстки сверх того, что переживает
  Telegram-подпись.

### BlogImageService — иллюстрация

Обёртка над `generateBanner`: `imagePrompt` от редактора плюс фиксированный
стилевой хвост (палитра, манера, формат 1:1), заголовок накладывается программно.

Фолбэк при отказе генерации: ретрай с упрощённым промптом, затем карточка на
фирменном фоне **без обращения к модели**. Пост выходит, качество проседает —
канал не замолкает и не ждёт Google. Это не теоретический риск: Google снял
`imagen-4.0-ultra`, а `IMAGE_RECITATION` роняет запрос молча, без строки в логе.

### BlogPublisherService — отправка

`sendPhoto` в канал через `tg-grammy.client`. Сохраняет `tg_message_id` и ссылку
на пост.

**Захват атомарный:** `UPDATE blog_post SET status='publishing' WHERE id=$1 AND
status='approved' RETURNING *`. В Telegram идёт только выигравший захват. Без
этого два тика крона или ретрай после таймаута дают в канал два одинаковых поста.

## Данные

Одна таблица `blog_post`. Отдельной «очереди идей» нет: идея — тот же пост без текста.

```sql
CREATE TABLE blog_post (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  rubric         text NOT NULL CHECK (rubric IN ('news','case')),
  source         text NOT NULL CHECK (source IN ('backlog','git','stats','manual')),
  source_ref     text,
  topic_key      text NOT NULL,
  lang           text NOT NULL DEFAULT 'ru',
  title          text,
  body           text,
  image_prompt   text,
  image_url      text,
  status         text NOT NULL DEFAULT 'idea'
                   CHECK (status IN ('idea','drafting','pending_review','approved',
                                     'publishing','published','rejected','failed')),
  slot_at        timestamptz,
  published_at   timestamptz,
  tg_message_id  bigint,
  tg_url         text,
  attempts       int NOT NULL DEFAULT 0,
  last_error     text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_blog_post_status_slot ON blog_post (status, slot_at);
CREATE INDEX idx_blog_post_topic_created ON blog_post (topic_key, created_at DESC);
```

Настройки, которыми управляют из админки, лежат в БД — одной строкой:

```sql
CREATE TABLE blog_settings (
  id            int PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  channel_chat_id text,
  slot_days     int[] NOT NULL DEFAULT '{1,3,5}',   -- ISO: пн, ср, пт
  slot_hour_msk int  NOT NULL DEFAULT 10,
  image_style   text NOT NULL DEFAULT '',
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

Миграция кладётся в `src/blog/migrations/001_blog.sql`. **Применяется вручную
через psql с записью в `schema_migrations`:** прод-раннер миграций застрял на
`base/001` (падает на `CREATE TYPE payment_status_enum`) и ничего после него не
докатывает. Файл в `migrations/` сам по себе ничего не доказывает.

### Машина состояний

```
idea → drafting → pending_review → approved → publishing → published
                        │                          │
                        │ «переписать»             │ телеграм не принял 3×
                        ↓                          ↓
                     drafting                    failed
                        │ «в мусор»
                        ↓
                     rejected
```

`drafting → failed` — редактор или картинка не дались после ретраев. В личку
падает не черновик, а сообщение об отказе с причиной: иначе «ничего не пришло»
читается как «сегодня просто нет темы».

### Дедупликация

Для новостей ключ — идентификатор бэклог-итема или диапазон коммитов, повтор
физически невозможен. Для кейсов — нормализованная тема: если кейс с таким
`topic_key` выходил за последние 90 дней, тема пропускается и берётся следующая.
Без этого синтетические кейсы пойдут по кругу примерно на третий месяц.

### Приоритет рубрик

Новость всегда вытесняет кейс — новости скоропортящиеся. Если новостей больше
трёх за неделю, лишние ждут следующего слота, но не дольше двух недель:
протухшая новость выбрасывается автоматически, а не публикуется задним числом.

## Расписание и апрув

- **Слоты публикации:** пн/ср/пт, 10:00 МСК.
- **Подготовка черновика:** за сутки до слота, чтобы на апрув были полдня, а не пять минут.
- **Пополнение очереди тем:** воскресенье — git-дайджест и агрегат по ассистентам.

Воскресенье несёт две задачи, и порядок между ними важен: сначала пополнение
очереди тем, потом подготовка черновика к понедельничному слоту. Иначе первый
пост недели готовится из вчерашнего остатка очереди.

Черновик уходит в личку владельцу картинкой с подписью и клавиатурой:
`blog:ok:<id>` / `blog:redo:<id>` / `blog:no:<id>`. Обработчик встаёт рядом с
существующими в `tg-bot.service`.

Telegram id получателя берётся из `BLOG_APPROVER_TG_ID`, без обращения к
`tg_user_identities`. Первоначальная редакция спеки предполагала поиск по
связке с фолбэком на переменную — от него отказались: связка ведёт от
telegram-аккаунта к аккаунту Linkeon, а на тестовом стенде один и тот же
человек привязан к другому аккаунту (UUID почтовой регистрации, не телефону),
так что поиск по телефону не нашёл бы ничего и всё равно свалился бы в
фолбэк. Одна явная переменная понятнее, чем поиск, который по факту никогда
не срабатывает.

**Правка текста реплаем.** Ответ реплаем на сообщение-черновик заменяет текст
поста, дальше он идёт на публикацию как есть. Нужно ради опечатки в одном слове
не гонять полную регенерацию. Обязательная оговорка: в личке бот сейчас роутит
любой текст ассистенту, поэтому обработчик должен явно проверять, что
`reply_to_message.message_id` совпадает с черновиком в `pending_review` — иначе
правка уедет в чат с ассистентом.

**Молчание не публикует.** За час до слота — напоминание. К слоту без решения
слот пропускается, пост остаётся в `pending_review` и участвует в следующем.
Канал лучше промолчит день, чем выложит непрочитанное.

## Админка

Вкладка «Блог» в `AdminPage` (`?tab=blog`) — по тому же шаблону, что остальные
разделы: раздел пишется в URL и переживает F5. Три экрана:

- **Очередь** — всё, что ещё не вышло: темы без текста, черновики на апруве,
  запланированные посты со слотом. Действия по каждому: одобрить, отклонить,
  переписать заново, править текст на месте, перегенерировать картинку,
  передвинуть слот. Плюс «добавить тему руками» — это же закрывает сценарий
  «кидаю сырую идею одной строкой, агент разворачивает в пост».
- **Архив** — опубликованное со ссылкой на пост в канале и отдельно `failed`
  с причиной. Чтобы «почему на той неделе вышло два поста вместо трёх» имело
  ответ в интерфейсе, а не в логах.
- **Настройки** — дни и час слотов, chat id канала, стилевой хвост для картинок.

Эндпоинты `/webhook/admin/blog/*` под существующим админским гардом, по образцу
соседних разделов.

### Две панели управления расходятся

Управление теперь в двух местах, и это нужно закладывать, а не чинить потом:

- **Устаревшая кнопка в личке.** Пост одобрен в админке, а в Telegram висит
  старое сообщение с кнопками. Обработчик сверяет текущий статус: если пост уже
  обработан — отвечает `answerCallbackQuery` с пояснением и перерисовывает
  сообщение, ничего не публикуя. Атомарный захват при публикации прикрывает
  тот же случай снизу.
- **Две вкладки админки правят один черновик.** `updated_at` работает как версия:
  запрос с несовпадающей версией получает 409, вместо того чтобы молча затереть
  чужую правку.

## Обработка отказов

| Отказ | Поведение |
|---|---|
| Релей не ответил | 2 ретрая с паузой → `failed` + сообщение в личку. Известный сценарий «временный сбой связи с моделью»: ход висит ~7 минут |
| Картинка не сгенерилась | Ретрай с упрощённым промптом → карточка на фирменном фоне без модели. Пост выходит |
| Telegram не принял | До 3 попыток → `failed` + алерт. Интервал равномерный (тик крона раз в 5 минут), не экспоненциальный: ретрай живёт в БД, а не в памяти вызова, поэтому переживает рестарт процесса. Неудачная отправка возвращает пост в `approved`, а не в `failed` — иначе его никто бы не подобрал |
| Процесс умер между захватом и отправкой | Пост зависает в `publishing`; сторож в кроне возвращает его в `approved` через 10 минут |
| Два тика крона на одном посте | Атомарный захват `WHERE status='approved'`; проигравший ничего не делает |

## Среды и выкат

- `BLOG_ENABLED` — рубильник уровня деплоя. Намеренно остаётся в env, а не в
  админке: если модуль начнёт чудить, гасить его через ту же админку, которая
  может быть частью проблемы, — плохая идея. На проде включается после полного
  цикла на тесте с живым апрувом.
- `BLOG_APPROVER_TG_ID` — запасной получатель апрувов, если связки в
  `tg_user_identities` нет.
- Канал, слоты и стиль картинок живут в `blog_settings`, правятся из админки.
  **Строка на тесте и на проде своя**, как и токены ботов: общий токен один раз
  уже увёл бы боевого бота молча.
- Работа затрагивает оба репозитория (`spirits_back` — модуль и API,
  `spirits_front` — вкладка админки). Выкат только через
  `bash ~/Downloads/spirits_back/scripts/deploy.sh` без флагов
  (test → smoke → prod → smoke).

## Тестирование

Unit-тесты (jest в `spirits_back`):

- переходы машины состояний, включая недопустимые;
- выбор слота и вытеснение кейса новостью;
- выброс новости старше двух недель;
- дедупликация кейсов по `topic_key` в окне 90 дней;
- обрезка текста под лимит подписи;
- разделение «реплай на черновик» и «обычный текст ассистенту»;
- фолбэк картинки при отказе генерации;
- атомарный захват: второй вызов публикации не отправляет ничего;
- нажатие устаревшей кнопки в Telegram по уже обработанному посту не публикует
  и не меняет статус;
- правка черновика с устаревшей версией получает 409.

Фронт (`spirits_front`): рендер очереди по статусам, переключение раздела через
`?tab=blog`, обработка 409 при конфликте правок.

Прогоны — на тестовой ноде в CI-клоне (`~/ci/spirits_back`), не на маке.
Свою работу мерить дельтой: полный прогон `npm test` на бэке красный by design.
Отдельно нужен `tsc --noEmit`: jest на бэке собран с `isolatedModules` и типы не
проверяет — типовая ошибка проходит прогон зелёной.

Живая проверка: на тестовом стенде полный цикл от темы до поста в тестовом
канале, с реальным нажатием кнопок.

## Чего в первой версии нет

- Второго языка и второго канала (схема готова, включение — строка в БД).
- Метрик и аналитики по постам: сколько просмотров собрал пост, откуда пришли.
- Видео-постов: только картинка плюс текст.
- Автопостинга без человека: апрув обязателен всегда.
