# Совместимый каталог загрузок сессии релея

Дата: 2026-11-11
Статус: дизайн для внутреннего багфикса; выкат релея только с отдельным OK владельца

## Контекст и подтверждённая причина

В боевом транскрипте релея ассистент получил два корректных полных пути к DOCX в `/tmp/agent-uploads/<fs_key>_<имя>.docx`. Файлы были успешно переименованы релеем и переданы в промпт, то есть загрузка не потерялась.

Вместо использования полных путей ассистент построил каталог `/tmp/agent-uploads/<fs_key>` и выполнил в нём `glob('*.docx')`. Такого каталога в плоской схеме нет. Попытка восстановиться перечислением `/tmp/agent-uploads` после включения sandbox закончилась `Permission denied`: корень намеренно имеет режим `0311`, чтобы один разговор не видел чужие файлы. Ассистент ошибочно сообщил, что исходные документы недоступны, и вызвал `report_problem`.

Повторный ход с теми же правилами sandbox использовал полные пути и успешно прочитал оба DOCX. Это исключает физическую потерю файлов и общий запрет чтения собственных загрузок. В истории того же разговора похожая ошибка интерпретации путей уже встречалась до sandbox, поэтому исправление только текста промпта недостаточно надёжно.

## Цель и критерии успеха

Новые загрузки с валидным серверным `fs_key` должны одновременно:

1. иметь точный полный путь в промпте;
2. находиться в существующем каталоге `/tmp/agent-uploads/<fs_key>/`, поэтому сценарий `glob('*.docx')` по этому каталогу тоже работает;
3. не ослаблять изоляцию чужих разговоров;
4. не требовать перемещения или удаления старых файлов.

Если серверный `fs_key` отсутствует или невалиден, `turnFsKey` использует legacy fallback из `sessionId`. Такой ключ может быть предсказуемым, поэтому для него вложенный каталог создавать нельзя: загрузка остаётся в прежней плоской схеме. Это также сохраняет работу `relay-scrub-phone.mjs` и `maskRelayPaths`, которые знают только плоские legacy-пути.

Старые плоские пути `/tmp/agent-uploads/<fs_key>_<имя>` остаются читаемыми: на них ссылаются существующие транскрипты `--resume`.

## Рассмотренные подходы

### Выбран: каталог сессии для новых файлов

Релей создаёт `/tmp/agent-uploads/<fs_key>` и помещает новые файлы туда только при наличии вложений и валидного серверного `fs_key`. Экспортированный предикат `isValidFsKey` из `paths.mjs` применяет существующее правило `^[0-9a-f]{32}$` и используется также в `turnFsKey`/`legacyTurnFsKey`, поэтому невалидное значение не может пройти gate даже при совпадении с `sessionId`. Старые файлы не мигрируют, а новые fallback-загрузки остаются плоскими. В sandbox разрешаются и новый каталог сессии, и прежний плоский префикс.

Плюсы: устраняет наблюдавшуюся ловушку детерминированно, не зависит от интерпретации подсказки моделью, сохраняет обратную совместимость и не создаёт предсказуемые каталоги для legacy. Минусы: после выката одновременно существуют две схемы хранения, поэтому legacy-разрешение нельзя убирать без отдельной миграции.

### Отклонён: только уточнить промпт

Минимальная правка, но не даёт функциональной гарантии: полные пути уже были в промпте, и модель всё равно выбрала неверный каталог.

### Отклонён: симлинки или отдельный манифест

Дублируют состояние, требуют правил очистки и дают новые гонки, хотя собственный каталог решает ту же задачу напрямую.

## Архитектура и поток данных

Изменения ограничиваются `relay-agent/`:

- `paths.mjs` получает единый помощник построения каталога загрузок сессии и его создания с режимом `0700`;
- `server.mjs` создаёт этот каталог до `renameSync` только для multipart-запроса с валидным серверным `fs_key` и сохраняет новые файлы в нём в режимах sandbox `on`, `canary` и `off`; без вложений каталог не создаётся, а без серверного `fs_key` назначением остаётся прежний корень;
- имя файла внутри каталога сохраняет существующий безопасный формат `<fs_key>_<base><ext>`: меняется только родительский каталог, правила санитизации и ограничения длины не переписываются;
- `sandbox-policy.mjs` добавляет `Read/Glob/Grep` для `/tmp/agent-uploads/<fs_key>/**` и сохраняет `/tmp/agent-uploads/<fs_key>_*` для старых файлов;
- промпт по-прежнему содержит фактический полный путь каждого успешно переименованного файла и исходное имя отдельно.

Выдача созданных файлов, `/tmp/agent-output`, `/tmp/agent-scratch`, MCP и транскрипты не меняются.

## Обработка ошибок и безопасность

- Каталог создаётся до первого `renameSync`; ошибка создания прерывает ход до запуска модели и не маскируется как «файл не найден».
- Текстовый ход без вложений не обращается к каталогу загрузок: новая ошибка `EEXIST`/`EACCES`/`ENOSPC` не может его сломать, пустые каталоги не создаются.
- В общем `finally` удаляются только оставшиеся исходные `req.files[*].path`, записанные Multer. `ENOENT` после успешного `renameSync` игнорируется, поэтому уже принятые файлы не удаляются; другие ошибки логируются только кодом.
- Общий корень `/tmp/agent-uploads` остаётся `0311`; перечисление чужих загрузок не разрешается.
- Каталог сессии создаётся `0700`; непредсказуемый `fs_key` и узкий `--allowedTools` сохраняются. Вложенный каталог для предсказуемого legacy `sessionId` не создаётся, включая зарезервированный ключ `mcp`.
- Старые файлы не перемещаются, не перезаписываются и не удаляются.
- Повторная загрузка того же имени сохраняет текущую семантику `renameSync`; отдельные правила дедупликации в задачу не входят.
- Ошибки кодировки `originalname` и падение LibreOffice под sandbox — независимые проблемы, в этот патч не входят.

## Проверки

1. Красный тест реального Express-хендлера с multipart-загрузкой двух DOCX: до исправления `/tmp/agent-uploads/<fs_key>` отсутствует, после — содержит оба файла; содержимое совпадает с загруженным.
2. Тот же тест читает захваченный prompt: оба полных пути указывают на существующие файлы внутри каталога сессии.
3. Тест эквивалентного сценария модели: перечисление `*.docx` по каталогу `<fs_key>` возвращает оба документа.
4. Тест `buildSandboxTools`: разрешены новый каталог и прежний плоский префикс; чужой `fs_key` не добавляется.
5. Существующие тесты имени файла, traversal, длины имени, lifecycle и все relay-тесты остаются зелёными.
6. Отдельные тесты без серверного `fs_key` и с невалидным `fs_key`, равным `sessionId`: предсказуемый legacy `sessionId` и `mcp` сохраняют плоский путь, вложенный каталог не создаётся, `allowedTools` содержит прежний префикс. Это исключает регрессии изоляции, scrub/mask, equality-gate обхода и deny-каталога `mcp`.
7. Тест JSON-хода без вложений: заранее созданный конфликтный файл `<uploadDir>/<fs_key>` не мешает успешному ходу и не заменяется каталогом.
8. Тест принудительного `EEXIST` при multipart: хендлер возвращает 500 до spawn, а оба исходных Multer-temp удаляются; конфликтный файл, созданный тестом, остаётся нетронутым.
9. Живая проверка после согласованного выката: тестовый разговор загружает два DOCX, затем повторно открывает их по полному пути и через каталог сессии; отдельно проверяется чтение одной старой плоской загрузки.

## Выкат и откат

Сборка и тесты — на тестовой ноде. Релей выкатывается только `scripts/deploy-relay.sh <BASE_SHA> <TARGET_SHA>` после отдельного OK владельца и проверки отсутствия живых ходов по правилам скрипта.

Чтобы откат не закрыл новые файлы старой политикой, нужны два независимо откатываемых этапа:

1. **Expand:** добавить `Read/Glob/Grep(/tmp/agent-uploads/<fs_key>/**)` и тесты политики, не меняя место хранения. Выкатить и проверить, что обычная плоская загрузка работает.
2. **Use:** создавать каталог и помещать в него новые файлы. Выкатить после успешного первого этапа.

Если второй этап откатывается, предыдущее дерево уже содержит разрешение нового каталога, поэтому и старые, и новые пути остаются доступны всем файловым инструментам. Если откатывается первый этап, новых каталогов ещё не существует.

Откат не требует удаления каталогов или переноса файлов. Полные пути из транскриптов остаются на диске. Убирать legacy-разрешение плоского префикса можно только в отдельной будущей миграции после проверки всех живых транскриптов.
