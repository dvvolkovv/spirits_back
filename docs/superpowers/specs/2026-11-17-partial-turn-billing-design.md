# Списание за оборванный ход — за то, что успело прийти

**Дата:** 17.11.2026
**Пункт бэклога:** 85841119 («Токены расходуются без понятной связи с результатом»), часть «частичный ответ, оборванный сбоем».
**Ветка:** `feat/partial-turn-billing` (от `fix/insights-backlog-1116`).

## Решение владельца

До 17.11 действовало прежнее решение: ход без финального ответа (`done.failed`
от релея) не тарифицируется вовсе, а релей пишет человеку «Токены за этот ход не
списаны». 16–17.11 владелец его развернул:

- частичный ответ, оборванный сбоем, — **списывать за то, что успело прийти**;
- касается всех четырёх видов обрыва с частичным результатом (см. ниже);
- сумма — **по фактическому расходу хода**, той же формулой, что у обычного хода.

## Как сейчас

- Релей (`relay-agent/server.mjs`) отдаёт в `done` поля `failed` и `failReason`.
  Причины, после которых человек мог что-то получить:
  - `transient_after_partial` — связь с моделью оборвалась посреди ответа (часть текста уже ушла);
  - `max_turns` — задача не уложилась в три захода, большая часть работы сделана;
  - `preempted` — человек сам отправил новое сообщение, ответ прерван;
  - `transient_after_write` — связь оборвалась после действия (картинка, запись в календарь и т. п.).
  Остальные причины — сбой до ответа: `cli_fatal`, `transient`, а на бэке
  `cli_fatal_text`, `relay_draining`, `relay_superseded`.
- На первые три релей дописывает служебную реплику (`notice`) с обещанием
  «Токены за … ход не списаны»; у `transient_after_write` такого обещания нет.
- Бэк при `failed` обнуляет списание:
  - веб-ход — `persistResponse` в `streamUniversalAgent` (`textCost = turnFailed ? 0 : …`, `addTokenTask` под `!turnFailed`);
  - ход с файлом — `persistUploadTurn` (то же самое).
- Голосовые вызовы (`agentReply` через `generateAgentReplyWithCharge`) уже
  списывают по расходу хода независимо от `failed`, а служебные реплики релея в
  их текст не попадают. Их не трогаем.
- Попутное расхождение: индикатор «N токенов» под ответом в вебе считает расход
  и у хода, за который ничего не списали (`tokensUsed` в `streamUniversalAgent`
  не смотрит на `turnFailed`). В загрузке индикатор при сбое — 0.

## Решение

### 1. Правило — в одном модуле

Новый `src/chat/partial-billing.ts`:

```ts
/** Обрывы, после которых человек мог что-то получить (решение владельца 17.11.2026). */
export const PARTIAL_BILLED_REASONS: ReadonlySet<string>;
// 'transient_after_partial', 'max_turns', 'preempted', 'transient_after_write'

export interface TurnDelivery {
  failed: boolean;
  failReason: string;
  /** Символы текста МОДЕЛИ, ушедшие человеку (delta/text/result), — без служебных реплик релея. */
  modelChars: number;
  /** Файлы хода, ушедшие человеку (outputFiles релея). */
  files: number;
}

export interface BillingDecision {
  billable: boolean;
  /** Списано за оборванный ход — причина обрыва, иначе undefined. */
  partial?: string;
}

export function billingDecision(d: TurnDelivery): BillingDecision;
```

- `failed === false` — `billable: true` (как сейчас).
- `failed === true`, причина из `PARTIAL_BILLED_REASONS` и `modelChars > 0 || files > 0` — `billable: true, partial: failReason`.
- Иначе — `billable: false`.

Служебная реплика релея («ответ оборван…») «пришедшим» не считается: она
приходит и тогда, когда модель не успела сказать ни слова.

### 2. Веб-ход (`streamUniversalAgent`)

- В обработчике потока считать текст модели отдельно от служебных реплик:
  ветки `delta`/`text` и `result` пополняют `modelText`, ветка `notice` — нет.
  Файлы — по `pendingFiles` (outputFiles релея).
- Решение `billingDecision(...)` принимается один раз по итогам потока и
  используется везде:
  - индикатор «N токенов» в `end`: `billable ? расход : 0` (заодно чинит расхождение выше);
  - `persistResponse`: `textCost = billable ? charge.tokens : 0`;
  - `addTokenTask`, `alertTurnCostFloor`, сторож роста стоимости — под `billable` вместо `!turnFailed`.
- Расход — прежняя формула `computeSdkCharge` (счёт CLI → usage → длина). У
  оборванного хода длина для запасного пути — длина `modelText`, а не всего
  текста со служебной репликой.
- В метаданные списания (`token_consumption_tasks.metadata`) — `partial: <причина>`.
- Журнал: `billing[partial:<причина>:<source>]: tokens=… …` уровнем warn;
  несписанный сбой — по-прежнему `billing[skipped:<причина>]`.
- Телеметрия `chat_quality`: `failed: true` и `fail_reason` остаются (для
  мониторинга ход неудачный), добавляется `partial_billed: true`.
- Остальное без изменений: обучение профиля (как сейчас идёт и у оборванного
  хода), строка истории, приписка пробы (`guestCarryConsumed` — только успех).

### 3. Ход с файлом (`ChatController.uploadAndChat` → `persistUploadTurn`)

- Контроллер так же считает `modelChars` (ветки `delta`/`text`/`result`, без
  `notice`) и файлы хода (`pendingFiles`) и передаёт их в `persistUploadTurn`.
- Индикатор `shown` в `end` — по тому же решению.
- `persistUploadTurn`: `textCost = billable ? charge.tokens : 0`, `addTokenTask`
  и сторожа — под `billable`, метаданные и журнал — как в вебе
  (`billing[upload:partial:<причина>:<source>]`). Длина для запасного пути —
  текст модели.
- Отказ CLI, долетевший текстом (`looksCliFailure` → `cli_fatal_text`), и
  исходы шлагбаума (`relay_draining`, `relay_superseded`) в список не входят —
  не списываются.

### 4. Служебные реплики релея

Из реплик `preempted`, `transient_after_partial` (два места) и `max_turns` в
`relay-agent/server.mjs` убирается фраза «Токены за … ход не списаны» — она
перестаёт быть правдой. Замены вида «списано за сделанное» нет: в сборке из
магазина нельзя говорить о деньгах (Apple 3.1.1), а релей не знает, какая у
человека сборка. Реплики сбоев без ответа (`cli_fatal`, `transient`) не
меняются — там «не списаны» остаётся правдой.

Комментарии в бэке, которые ссылаются на старое правило («ход без финального
ответа пользователю не выставляется — решение владельца», «и она должна
оставаться правдой»), переписываются под новое.

## Выкат

Порядок важен: **сначала релей без обещаний, потом бэк со списанием.** Иначе
будет окно, когда релей пишет «не списаны», а бэк уже списывает.

1. Правка реплик релея (раздел 4) вливается в `fix/insights-backlog-1116` до
   выката релея этой ветки и уезжает тем же `deploy-relay.sh` — после выката её бэка.
2. Списание (разделы 1–3) — отдельный выкат бэка `deploy.sh` после того, как
   релей с новыми репликами работает. Каждый шаг — с OK владельца.

Откат: бэк откатывается без релея (вернётся «не списывать»; реплики без
обещания — честны и при старом бэке).

## Тесты

- `partial-billing.spec.ts` — таблица: успех; каждая из четырёх причин с текстом,
  с файлами, без того и другого; причины вне списка с текстом
  (`cli_fatal`, `transient`, `cli_fatal_text`, `relay_draining`, `relay_superseded`).
- Веб-ход (по образцу `chat.relay-drain.spec.ts`):
  - `transient_after_partial` с текстом и расходом в `done` → одна строка
    `token_consumption_tasks` с `partial`, индикатор в `end` = списанному, `chat_quality` с `partial_billed: true`;
  - `preempted` до первого слова (только `notice`) → без списания, индикатор 0;
  - `cli_fatal` с текстом → без списания;
  - `max_turns` без `usage` и без стоимости → списание по длине текста модели, служебная реплика в длину не входит;
  - обычный успешный ход — как раньше.
- Ход с файлом: `transient_after_partial` с текстом → списание с `partial`, `shown` = списанному;
  `preempted` без текста → 0.
- Релей: в репликах четырёх причин нет «не списан»; у `cli_fatal`/`transient` осталась.

## Соответствие концепции

Концепция (`linkeon-launcher/docs/superpowers/specs/2026-08-04-launcher-assistant-concept-design.md`,
§2.5): наружу — минимум, без ложных обещаний, деньги — решение владельца.

- **Деньги:** правило списания меняется по прямому решению владельца (16–17.11).
- **Без ложных обещаний:** релей перестаёт обещать «не списаны» там, где
  списываем; где не списываем — обещание остаётся и верно.
- **Магазинная сборка:** новых слов о деньгах человек не видит.
- **Новых потоков данных нет:** считаем по тому, что уже приходит в `done`.

## Не входит

- Telegram-боты: свой CLI и свой биллинг, к релею отношения не имеют.
- Голосовые вызовы: уже списывают по расходу хода.
- Возврат или доначисление за прошлые оборванные ходы.
- Реплики `cli_fatal`/`transient` в сборке из магазина всё ещё упоминают токены — давнее, отдельная правка.
