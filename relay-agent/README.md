# relay-agent — AI-relay ассистентов (r.linkeon.io)

Код лежит здесь, **а работает на другом сервере**: `5.101.115.184`
(`r.linkeon.io`), каталог `/home/dv/file-agent`, под PM2 процессом
`file-agent`.

## Что это

Через него отвечают все ассистенты Linkeon, кроме Маши. Прод-бэк ходит
сюда за ответом: `AGENT_URL` в `src/chat/chat.service.ts` и
`src/chat/chat.controller.ts`, по умолчанию `https://r.linkeon.io`.

На каждый запрос `server.mjs` поднимает **Claude Code CLI**
(`claude --print --output-format stream-json`) и стримит ответ обратно
NDJSON-ом. Отсюда же берутся файлы, которые ассистент создал за сессию.

## Почему код появился в репозитории только сейчас

Каталог заводили как времянку, а он стал боевым: правился прямо на
сервере, и единственной защитой был ручной бэкап перед каждой правкой.
К моменту переноса рядом с `server.mjs` лежало **27 файлов вида
`.bak*`** — по ним не видно ни что менялось, ни зачем, и откат
превращался в гадание по датам.

## Как файлы попадают пользователю

Всё, что ассистент кладёт в `/tmp/agent-output/<ключ папки>/`, уезжает в
событии `done` списком `outputFiles`, а бэк превращает его в ссылки вида
`https://r.linkeon.io/files/<ключ папки>/<имя>`. Ключ папки — `fs_key` от
бэка (32 hex от HMAC ключа сессии, без номера телефона; `paths.mjs`,
`turnFsKey`), у ходов без него — санитизированный `sessionId`, как до
26.10.2026. Загрузки называются `<ключ папки>_<имя>`.

Отдаётся то, что создано или изменено **за этот ход** (сверка со снимком
папки на его старте). С 06.08 по 11.08.2026 отдавалась вся папка с
признаком `fresh` у каждого файла; `bac27cb` вернул «только новое» —
эта заметка тогда не обновилась.

Плюс файлы прошлых ходов той же сессии, чей `done` до бэкенда не дошёл
(`undelivered-files.mjs`). Бэкенд мог уйти раньше конца хода — рестарт
API при выкате, обрыв связи: claude доделывает ход и кладёт файлы на
диск, но список в `done` писать некому. 20.10.2026 так пропала справка:
на «что молчишь?» ассистент ответил «файл прикреплён ниже», а ссылки не
было. Теперь такие файлы откладываются (в памяти, до 7 дней; рестарт
релея их забывает) и уходят со следующим ходом сессии, если ещё лежат
на диске.

  сервер `linkeon` подключается в конфиг хода из `linkeon_token` бэка
  (`linkeon-mcp.mjs`), как `products` и `talerid`. До 26.10.2026 боевой
  файл держал общий `MCP_SECRET` прода; с 06.08 по 07.10.2026 он лежал

## Правка и официальный выкат

Рабочий каталог на сервере — самостоятельный git-репозиторий с собственной историей. Изменения сначала коммитятся и пушатся здесь, в `spirits_back/relay-agent/`. `scripts/deploy.sh` релей **не разворачивает**; для него есть отдельный официальный путь:

```bash
bash scripts/deploy-relay.sh <BASE_SHA> <TARGET_SHA>
```

`BASE_SHA` — коммит, чьё содержимое `relay-agent/` соответствует живому релею; `TARGET_SHA` — проверенный коммит для выката. Скрипт собирает оба дерева из git, прогоняет syntax-check и все `*.test.mjs` в staging на relay-host, сверяет изменяемые живые файлы с базой и останавливается при несогласованной правке.

Nginx `location /files/` проксируется в Express, а не читает `/tmp/agent-output/` через `alias`: корневой каталог имеет режим 0311, сессионные — 0700, поэтому прямой доступ от `www-data` даёт 403. При выкате скрипт идемпотентно заменяет прежний alias на proxy к `127.0.0.1:3033` с маркером `LINKEON-RELAY-FILES-PROXY`, скрывает CORS-заголовок upstream и добавляет один свой через `always`. Права каталогов ослаблять не нужно.

Весь remote critical rollout защищён неблокирующим `flock` на `/tmp/linkeon-relay-deploy.lock`: блокировка берётся **до первого remote rm/mkdir/archive** и удерживается через финальный health/release. Target/base собираются локально и одним tar-потоком передаются в ту же SSH-критическую секцию. Второй overlapping rollout завершается ошибкой до удаления shared STAGE/BASE_DIR или изменения marker/файлов приложения. Путь переопределяется через `RELAY_DEPLOY_LOCK_FILE` (для изолированных тестов).

Если `/health` не содержит `inflight`, это legacy relay, а не безопасный ноль: старый процесс не понимает drain marker. Перед его созданием скрипт добавляет помеченный `return 503` в существующий `location /chat` `/etc/nginx/conf.d/parking.conf` (путь переопределяется через `RELAY_NGINX_CONF`), делает graceful `nginx -s reload` и проверяет `/chat=503` при доступном `/health`. Перед reload запоминаются PID текущих Nginx workers; replacement ждёт, пока именно эти старые процессы завершат принятые соединения и исчезнут, поэтому legacy uploads тоже дожидаются без kill. Nginx gate держится через replacement/restart и снимается только после успешного upgraded-relay health; при rollback — только после rollback health. Сначала удаляется relay marker (Nginx продолжает блокировать новые ходы), затем снимается Nginx gate и проверяются `/chat` + `/health`, поэтому admission не открывается в незащищённое окно.

Перед ожиданием завершения ходов скрипт атомарно создаёт `/tmp/linkeon-relay-drain` вне дерева приложения. `drain-gate.mjs` проверяет этот файл при **каждом** новом `POST /chat` и отвечает 503. Файл переживает PM2 restart; `/health` остаётся доступен. `inflight.mjs` считает каждый принятый `/chat` с middleware до response `finish`/`close`, а health отдаёт это число полем `inflight`. Скрипт ждёт нуля **и у принятых запросов, и у PM2 children**, поэтому upload, принятый непосредственно перед marker и ещё не породивший child, тоже завершается до замены. Marker удерживается через drain, замену файлов, restart и health, а снимается только после успешного health. Пути marker/ожидания переопределяются через `RELAY_DRAIN_FILE` и `DRAIN_WAIT_SECONDS` (по умолчанию 1800 секунд).

При сбое после замены скрипт восстанавливает прежние файлы из `BASE_SHA`, перезапускает PM2 и проверяет rollback health при всё ещё закрытом admission. Только успешный rollback health снимает marker. Если восстановление или его health не удалось, marker намеренно остаётся: непроверенный код не начинает принимать новые ходы молча. Уже существующий marker скрипт не перезаписывает и не снимает — сначала разобраться с аварийным/чужим drain.

Секреты и файлы режима релея скрипт не переносит. Ручной `scp`/`mv` и рестарт в обход этого пути не использовать. Если живой relay-agent менялся вместе с backend, его выкат и health обязаны завершиться **до живого backend E2E**, иначе E2E может пройти против старого кода.

## Обязательная проверка записи при смене sandbox runtime

Любой rollout нового `/opt/linkeon-agent/bin/claude-runtime` обязан после атомарного переключения и **до снятия drain** запустить живой test записи:

```bash
RELAY_LIVE_CLI_WRITE_TEST=1 \
RELAY_CLAUDE_BIN=/opt/linkeon-agent/bin/claude \
node --test /home/dv/file-agent/sandbox-write-live.test.mjs
```

Тест создаёт уникальный `fs_key` и проверяет точное содержимое probe-файла и в scratch (`/tmp/agent-scratch/<fs_key>`, по абсолютному пути — sandbox CLI переопределяет TMPDIR подпроцессов), и в `/tmp/agent-output/<fs_key>`. Он не использует `/chat`, поэтому работает при закрытом admission и не затрагивает пользовательские сессии.

Красный результат запрещает открывать admission: вернуть прежний сохранённый runtime, проверить его `--version` и `/health`, затем снять drain. Нельзя заменять эту проверку чтением sandbox-настроек или прогоном только unit-тестов: CLI 2.1.322 при корректных настройках возвращал `EROFS` для обоих разрешённых каталогов. Sandbox не отключать и не ослаблять.

Тот же гейт уже встроен в `scripts/deploy-relay.sh` после обычного `node --test *.test.mjs` и до изменения живых файлов. Сбой модели, авторизации или API также останавливает rollout; молча пропускать живой test нельзя.

## Секрет бэка (`X-Agent-Secret`)

Релей проверяет все пути, кроме `/health` и `/files/*` (и `OPTIONS`-preflight) — заголовок `X-Agent-Secret` должен совпасть с одной из строк файла `relay-secrets` (рядом с `server.mjs`, права 600, не в git; путь переопределяется переменной `RELAY_SECRETS_FILE`). Режим — файл `relay-auth-mode` (путь — `RELAY_AUTH_MODE_FILE`): `log` (пропускать и писать «отказ был бы») или `enforce` (401). Оба файла перечитываются раз в 30 с, рестарт не нужен.

Файлы переписывать атомарно — во временный файл рядом и `mv` на место, а не редактировать существующий: `mv` на той же файловой системе — одна операция, читающий процесс не увидит файл наполовину записанным.

Смена секрета без простоя: добавить новую строку в `relay-secrets` → заменить `RELAY_SECRET` в `.env` бэка → `pm2 restart linkeon-api` при нуле живых ходов → удалить старую строку. Значения не печатать: передавать трубой `ssh … | ssh …`.
