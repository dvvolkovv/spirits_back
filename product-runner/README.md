# linkeon-product-runner

Агент Linkeon на VM клиентского продукта. Забирает задания long-poll'ом,
гоняет `claude -p` в чекауте продукта, коммитит, деплоит и откатывает при
красном health-check.

Соединение всегда инициирует эта машина. Linkeon не хранит SSH-ключей от
клиентских VM и не ходит сюда сам.

## В пакете ДВЕ программы, и живут они на разных машинах

| | точка входа | где работает | что делает |
|---|---|---|---|
| раннер продукта | `dist/index.js` | ВНУТРИ контейнера продукта | правит код продукта по ходам из кабинета |
| агент хоста | `dist/host/index.js` | на машине продуктов, ВНЕ контейнеров | заводит новые продукты: docker, vhost, чекаут |

Общий пакет — потому что общие `api.ts`-подобные приёмы, общий tsconfig и общая
сборка. Общего процесса у них нет: это два разных юнита с разными токенами и
разными конфигами, и перепутать их установку — значит поставить агента хоста
внутрь контейнера, где нет докера.

Дальше сначала про раннер, потом отдельным разделом — про агента хоста.

## Установка на VM продукта

```bash
sudo mkdir -p /opt/linkeon-product-runner
sudo rsync -az --exclude node_modules --exclude .git \
  ./ root@<vm>:/opt/linkeon-product-runner/
ssh root@<vm> 'cd /opt/linkeon-product-runner && npm ci && npm run build'
```

`rsync` без `--delete` — сознательно: с `--delete` он уже сносил `.env`
воркера на этом проекте.

## Конфиг

`/etc/linkeon-product-runner.env`:

```
LINKEON_URL=https://my.linkeon.io
RUNNER_TOKEN=<из scripts/products-register.sh, показывается один раз>
CHECKOUT_PATH=/home/dv/selyanska
CLAUDE_BIN=/usr/bin/claude
```

`CLAUDE_BIN` задаётся явно: бэкенд Linkeon зовёт `/usr/bin/claude`, а не тот
`claude`, что первым найдётся в `PATH` интерактивного шелла — на серверах это
разные бинари.

## Запуск

```bash
# Подставить фактический путь к node: /usr/bin/node есть не на всякой машине.
# На тестовой ноде node стоит под nvm, и юнит с захардкоженным путём падает
# с status=203/EXEC — проверено установкой.
sed -e "s|__NODE__|$(command -v node)|" \
    -e "s|__NODE_BIN__|$(dirname "$(command -v node)")|" linkeon-product-runner.service \
  | sudo tee /etc/systemd/system/linkeon-product-runner.service >/dev/null
sudo systemctl daemon-reload
sudo systemctl enable --now linkeon-product-runner
journalctl -u linkeon-product-runner -f
```

Раннер намеренно живёт под systemd, а сам продукт — под PM2. В образце
`selyanska` агент жил дочерним процессом бота, из-за чего `pm2 restart`
убивал его посреди ответа. Разные супервизоры разрывают эту связь:
`pm2 restart` продукта раннера не касается.

## Проверка

```bash
# heartbeat дошёл до Linkeon
psql "$DATABASE_URL" -c 'SELECT slug, runner_seen_at FROM products'
```

`runner_seen_at` обновляется на каждом опросе, даже когда заданий нет.
Молчание дольше порога означает, что раннер мёртв, а не что ходов не было.

## Агент хоста продуктов

Второй юнит из этого же пакета. Стоит на машине продуктов (`139.59.210.42`) и
разворачивает новые продукты: создаёт чекаут в `/srv/products/<slug>`,
поднимает контейнер, заводит vhost, отчитывается в Linkeon.

**Живёт вне контейнера, и иначе нельзя.** Раннер сидит внутри контейнера
продукта, а агенту хоста нужны сам Docker, `/etc/nginx/sites-products`,
`systemctl reload nginx` и `/root/.secrets/claude-oauth-token`. Изнутри
контейнера ничего этого нет — по построению: доступ контейнеров к хосту
закрыт `scripts/product-host-harden.sh`.

Отсюда же — `User=root` в юните. Пользователь в группе `docker` ничего бы не
дал: членство в этой группе и так равносильно root, а nginx, `/srv/products` и
секрет Claude требуют root и помимо докера.

### Установка

Одной командой, с прод-машины или ноутбука:

```bash
bash scripts/product-host-agent-install.sh root@139.59.210.42
```

Скрипт раскладывает код в `/opt/linkeon-host-agent`, собирает, подставляет в
юнит путь к node, поднимает `linkeon-host-agent.service` — и **доказывает, что
агент работает**, а не просто «зелёный».

У ssh-цели нет умолчания намеренно: этот скрипт настраивает саму машину, и
запуск без аргумента не должен уезжать на хост с живыми продуктами.

Что он проверяет ДО первого изменения на машине:

- есть node, есть npm (на тестовой ноде `/usr/local/bin/node` оказался
  симлинком в чужой `~/.nvm`, где npm рядом не лежал — сборка падала уже после
  раскладки кода);
- найденный node запускается от того пользователя, от которого пойдёт юнит;
- на машине есть всё, что зовут хостовые шаги: `docker`, `git`,
  `product-vhost`, `/srv/products`, `/etc/nginx/sites-products`, образ
  `linkeon-product:base`, секрет Claude. Нет чего-то — агент стартует и
  провалит КАЖДОЕ задание, то есть поломка вылезет у клиента, а не при
  установке. Для стенда, где агента ставят ради проверки самой установки, —
  `ALLOW_INCOMPLETE_HOST=1`, список пропущенного печатается;
- не стоит ли на машине второй агент хоста под другим именем;
- конфиг: `LINKEON_URL` под https и `HOST_TOKEN` той же формы, которую
  требует `HostGuard` (не короче 32 символов, печатный ASCII без пробелов).
  Ловится и файл в CRLF: хвостовой `\r` даёт вечный 401, неотличимый от
  неверного токена.

Ставить поверх работающего агента скрипт откажется, если тот за последние
десять минут брал задание: `systemctl restart` посреди провижининга убивает
вместе с агентом и его `docker run`, подчистка не отрабатывает, и на хосте
остаётся полусозданный продукт. Десять минут — это серверный срок заведения.
Осознанно поверх — `FORCE=1`.

### Конфиг

`/etc/linkeon-host-agent.env` — заводит его владелец, скрипт туда не пишет
(правит только права на 600 root):

```
LINKEON_URL=https://my.linkeon.io
HOST_TOKEN=<то же значение, что PRODUCT_HOST_TOKEN в .env бэкенда>
```

**`HOST_TOKEN` обязан совпадать с `PRODUCT_HOST_TOKEN` бэкенда.** Не совпал —
агент не получит ни одного задания, и это ЕДИНСТВЕННАЯ поломка схемы, которая
снаружи выглядит как «кнопка „Новый продукт“ не работает»: в кабинете продукт
висит в `provisioning`, через десять минут его хоронит реаппер с формулировкой
про истёкший срок, а на машине продуктов процесс агента при этом жив и здоров.

### Как отличить «агента не пускают» от «заданий нет»

Никак — если смотреть на то, на что смотрят обычно:

```
$ systemctl status linkeon-host-agent      # при НЕВЕРНОМ токене
● linkeon-host-agent.service - Linkeon product host agent
     Active: active (running) since ...
```

`active (running)`, ноль перезапусков, ни одной ошибки. Агент не падает на
401 сознательно: Linkeon может быть просто на выкате, и падать на каждый
сетевой моргок ему нельзя — он один на всю машину.

Отличие видно в журнале, и только там:

```bash
journalctl -u linkeon-host-agent --since -2min -o cat
```

- **пусто** — агента пускают, заданий нет. Успешный пустой опрос не печатает
  ничего, поэтому молчание здесь и есть «всё в порядке»;
- **`[host] опрос не удался: опрос отклонён: HTTP 401`** раз в девять секунд —
  токен разошёлся с бэкендом;
- `[host] фатально: …` и `systemctl is-failed` = `failed` — сломан конфиг
  (см. ниже).

Активная проверка, не полагающаяся на отсутствие строк, — последний шаг
скрипта установки: он берёт токен из `/proc/<pid>/environ` (то есть тот, что
systemd реально отдал процессу, со всеми кавычками и пробелами) и стучится им
на сервер. `201` — пускают, `401` — нет.

Проба идёт на маршрут **завершения со случайным uuid**, а не на опрос. Опрос
ЗАБИРАЕТ задание: проба на нём в момент, когда клиент нажал «Новый продукт»,
увела бы задание в никуда — агент его уже не получит, отчитаться о нём некому,
и через десять минут продукт похоронит реаппер. Завершение по неизвестному id
не меняет на сервере ничего (`AND status = 'running'` не находит строки) и
оставляет ровно одну строку в логе бэкенда: «отчёт об успехе по незапущенному
заданию … — продукт не тронут». Увидев её после установки — это проба, а не
авария.

Чего эта схема **не** закрывает: со стороны сервера живого агента от мёртвого
не отличить. У раннера для этого есть `products.runner_seen_at`, у агента
хоста аналога нет — маршрут опроса ничего не отмечает. Пока это так,
единственный признак «агент на связи» живёт на самой машине продуктов.

### Что делать нельзя

**Перезапускать агента, пока он разворачивает продукт.** `systemctl restart`
убивает control-group целиком вместе с `docker run`; подчистка при этом не
вызывается, и слаг, порт и каталог остаются занятыми — повтор из кабинета
упрётся в «контейнер уже есть». Сначала `journalctl -u linkeon-host-agent -f`,
и только на тишине — рестарт.

### Цикл падений виден, и это настроено, а не само

В юните стоит `Restart=always` — без него единственный агент машины умирает от
любой неперехваченной ошибки, и продукты перестают заводиться у всех клиентов
сразу. Но `Restart=always` на сломанном конфиге (пустой `HOST_TOKEN`,
неподставленный путь к node) даёт перезапуск раз в пять секунд годами, причём
`systemctl status` всё это время показывает `active (running)`: процесс же
только что стартовал.

Умолчания systemd тут не спасают — `StartLimitIntervalSec=10s` при
`RestartSec=5` не срабатывает никогда (два перезапуска в окно — меньше пяти).
Поэтому в юните окно растянуто до 120 секунд: пять падений подряд, и юнит
уходит в `failed`, где его видно. Проверено обоими способами — с пределом юнит
за 30 секунд становится `failed` с `NRestarts=5`, без предела через 45 секунд
он всё ещё `activating` с `NRestarts=8` и будет так до конца времён.

Риска «сдался на ровном месте» здесь нет: агент НЕ падает ни от лежащего
Linkeon, ни от неверного токена, ни от проваленного задания — всё это
обрабатывается внутри цикла. Ненулевым кодом он выходит только на сломанном
конфиге, то есть на поломке, которая сама не починится.

### Повторная проверка живого агента

```bash
systemctl is-failed linkeon-host-agent          # должно быть "active", не "failed"
systemctl show -p NRestarts --value linkeon-host-agent   # растёт — цикл падений
journalctl -u linkeon-host-agent --since -5min -o cat    # пусто — норма
```

Или просто прогнать скрипт установки ещё раз: он идемпотентен и заканчивается
теми же проверками.

## Подпроект в корне репозитория — обязательный шаг

`product-runner/` лежит в корне `spirits_back` рядом с `worker/`, `voice-host/`
и `relay-agent/`. У всех них свои `package.json` и `tsconfig.json`, и каждый
обязан быть исключён из `tsconfig.build.json` бэкенда:

```json
"exclude": ["node_modules", "test", "dist", "scripts", "tests",
            "worker", "voice-host", "product-runner", "**/*spec.ts"]
```

Без этого файлы подпроекта попадают в сборку бэкенда, общий корень исходников
поднимается на уровень выше, и весь вывод уезжает в `dist/src/`. pm2 запускает
`dist/main.js`, не находит его и уходит в цикл перезапусков: стенд отвечает
502, а двухфазный деплой останавливается на PHASE 1.

Эта поломка случалась трижды — с `worker`, `voice-host` и `product-runner`.
Проверка `tsc --noEmit -p tsconfig.json` её не показывает: это другой конфиг,
и он ничего не выводит. Единственная проверка, которая ловит, —
`npm run build` с последующим `ls dist/main.js`.
